`docs/` 全体を検査し、結果を報告する。**修正はユーザーの承認を得てから**行う。

**最初に `docs/RULES.md` を必ず読む。** 判定はすべてあの文書が正。このスキルは検査手順だけを持つ。

## A. 配置ルール違反（最優先）

内容が正しい文書に書かれているかを検査する。**リンク切れや表記ゆれより重い問題**として扱う。ここが崩れると、docs 全体が信用できなくなる。

### A-1. `domain/` へのインフラ混入

`docs/domain/*.md` の全文を読み、次を探す。

| 検出対象 | 具体例 |
|---|---|
| 製品名・サービス名 | Supabase, Firebase, Postgres, MySQL, Redis, S3, AWS, Vercel |
| ライブラリ名 | expo-*, React Query, Prisma, Zustand |
| DB 構造 | テーブル名, カラム名, 型, SQL, インデックス, RLS |
| API の形 | エンドポイント, HTTP メソッド, ステータスコード |
| 実現方式 | キャッシュ, バッチ, ポーリング, cron, トリガー, WebSocket |
| 画面の作り | コンポーネント名, 画面レイアウトの指定 |

**判定**: その記述から技術用語を消して意味が通じなくなれば違反。
**例外**: `関連` 節などから `adr/XXXX` を**リンクとして**参照するのは違反ではない。

### A-2. `adr/` へのドメイン知識の漏れ

`docs/adr/*.md` の「決定」節を読み、次を探す。

- 状態の意味・遷移条件・タイミングを**定義**している記述
- 業務上の判断基準（「◯◯のときは△△とみなす」）
- 機能の有無

**判定**: その ADR を読んで、`domain/` を見ずに業務ルールを初めて知れてしまうなら漏れている。
**あわせて確認**: 各 ADR の `関連:` に、ドメイン文書か機能へのリンクがあるか。**1 つもない ADR は要注意**として報告する（技術内部で閉じた決定なら例外）。

### A-3. `features.md` への詳細ルール混入

状態遷移・条件分岐・入力仕様などが書かれていないか。機能名と一行説明を超えていれば違反。

### A-4. `overview.md` への技術の混入

「前提」節にスタック名を 1 行書く以外に、技術名や選定理由が出ていないか。

### A-5. `operations.md` への決定の混入

選定の理由・検討した代替案が書かれていないか。

**判定**: その記述を書き換えたとき、意思決定そのものが変わるなら ADR の内容。変わらない（同じ決定を別のやり方で実行するだけ）ならここでよい。

### A-6. `glossary.md` への定義の書き写し

用語の意味が書かれていないか。ここは索引であり、意味は `domain/` が正。

**判定**: 「一次情報」列を消したとき、用語の意味が分からなくなるのが正しい状態。分かってしまうなら定義が漏れている。
**あわせて確認**: `docs/domain/*.md` の「用語の区別」表に出てくる概念が、`glossary.md` に 1 行ずつ存在するか。**日本語だけ増えてコード上の名前が無い概念**を報告する。

### 報告の仕方

違反は必ず **該当箇所 → なぜ違反か → どこへ移すか → 移した先での書き方** をセットで示す。「違反です」だけでは直せない。

## B. 構造の整合

1. **リンク・参照**: `adr/XXXX`・`domain/xxx.md` 形式の参照や相対リンクが実在するファイルを指しているか。
2. **目次との一致**: `docs/README.md` の構成ツリーと実ファイルが一致するか。
3. **一次情報の重複**: 同じ事実が 2 つ以上の文書で**定義**されていないか（リンクはよい、再掲は違反）。`docs/README.md` の一次情報表が、確定した事実に対して埋まっているか。
4. **ADR の健全性**: 採番が連続しているか（`_template.md` は対象外）、`関連:` の参照先が実在するか、廃止（superseded）された ADR を正として参照している箇所がないか、「検討した代替案」が空の ADR がないか。
5. **プレースホルダの残留**: 記入済みの文書に `{{...}}` や雛形のままの HTML コメントが残っていないか。`domain/_template.md`・`adr/_template.md` は対象外。

## C. ステータスの同期

1. `[保留]` の付いた記述が `docs/open-questions.md` に登録されているか。
2. `open-questions.md` で解決済みの論点が、本文で `[保留]` のまま残っていないか。
3. 印のない断定的な記述が放置されていないか。

## D. コードとの乖離（実装が存在する場合のみ）

1. ADR で定めた依存方向・配置ルールに違反した import がないか。
2. 実装済みの機能と `docs/features.md` が整合しているか。
3. `domain/` に書かれたルールと実装の挙動が食い違っていないか（気づいた範囲でよい）。

## 報告形式

3 段階に分けて列挙する。

| 区分 | 中身 |
|---|---|
| **違反** | 配置ルール違反（A）・事実の矛盾・リンク切れ。**最優先で直す** |
| **軽微** | 目次の抜け・表記ゆれ・ステータス印の欠落 |
| **未着手** | まだ書かれていないだけのもの。**問題として数えず、区別して報告する** |

- それぞれ該当ファイルと行、修正案を添える。
- 問題がなければ「問題なし」と明確に報告し、検査した項目の一覧を添える。
- **違反の自動修正はしない。** 移動先と書き換え案を示し、承認を得てから直す。
