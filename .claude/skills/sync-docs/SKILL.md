これまでの会話で決まったことを `docs/` に反映する。

**最初に `docs/RULES.md` を必ず読む。** 配置の判定はすべてあの文書が正。このスキルは手順だけを持ち、ルールは再掲しない。

## 原則

- **勝手に決めない。** 会話で合意していないことを補完して書かない。曖昧なら `[提案]` を付けるか、ユーザーに聞く。
- **承認を得てから書く。** 振り分け案を先に見せる。
- **迷ったら分割する。** 1 つの発言に「ルール」と「実現方式」が混ざっていることは多い。**混ざったまま 1 か所に書かない。**

## 手順

### 1. 現状を読む

- `docs/RULES.md`（配置ルール）
- `docs/README.md`（目次・一次情報の所在）
- 会話の話題に関係する `docs/domain/*.md`・`docs/adr/*.md`・`docs/features.md`・`docs/open-questions.md`

### 2. 会話から「決まったこと」を拾う

これまでの会話を見返し、docs にまだ書かれていないものを列挙する。

拾う対象:

| 種類 | 例 |
|---|---|
| 仕様の決定 | 状態・条件・タイミング・境界値・「しないこと」 |
| 機能の増減 | 作ると決めた／作らないと決めた |
| 技術的な決定 | ライブラリ選定・実装方式・構成 |
| 未決として残ったもの | 「あとで決める」「一旦保留」 |

拾わない対象:

- **その場限りの作業の話**（「このファイルを直す」「テストを流す」）
- **すでに docs に書かれていること**
- **ユーザーが疑問を投げただけで、結論が出ていないもの** → これは `[保留]` 候補として扱う

### 3. 振り分ける（このスキルの中核）

拾った各項目について、`RULES.md` の「判定の 3 ステップ」を適用する。

**必ず「② 技術を全部入れ替えたとき、この記述は書き換えが必要か？」を各項目に対して明示的に問う。** 頭の中で済ませず、判断理由を振り分け案に書く。

**1 つの発言を分割すべきケース（頻出）**

> 「予定日を過ぎたら自動でおしまいにする。バッチは持たず、読み取り時に判定する」

これは 2 つの決定が混ざっている。分けて書く。

| 分割後 | 行き先 | 理由 |
|---|---|---|
| 予定日の終わりを過ぎたプランは「おしまい」として扱う | `domain/plan.md` | 技術を入れ替えても変わらない |
| 書き込みを伴わない読み取り時判定で実現する。バッチを持たない | `adr/XXXX` | 技術を入れ替えたら変わる |

### 4. 書く前の配置チェック（自己検査）

振り分け案を提示する前に、**各項目の文面を自分で検査する**。ここを飛ばさない。

**domain/ に書く文面**

- [ ] 製品名・サービス名・ライブラリ名が含まれていないか
- [ ] テーブル名・カラム名・API のパスが含まれていないか
- [ ] 「キャッシュする」「バッチで」「トリガーで」など実現方式の語がないか
- [ ] **その文面から技術用語を消して、意味が通じるか**（通じないなら書き方が間違っている）

**adr/ に書く文面**

- [ ] ドメインのルールを**定義**していないか（参照ならよい）
- [ ] 「この ADR を読んで、業務ルールを初めて知れてしまう」状態になっていないか
- [ ] `関連:` にドメイン文書か機能へのリンクがあるか

**features.md に書く文面**

- [ ] 状態遷移・条件分岐など詳細ルールが混ざっていないか

引っかかったら、`RULES.md`「NG → OK の書き換え例」に倣って**書き直してから**提示する。

### 5. 振り分け案を提示して承認を得る

次の形で見せる。**ファイルを触る前に。**

```
反映案：

[1] docs/domain/plan.md  ＜追記＞
    「期限は、日付が入っている間は設定できない」[確定]
    理由: 条件のルール。技術を入れ替えても変わらない

[2] docs/adr/0023-bottom-sheet.md  ＜新規＞
    ボトムシートは …… を採用する
    理由: 技術を入れ替えたら変わる決定
    関連: domain/plan.md

[3] docs/open-questions.md  ＜追記＞
    「通知の時刻を何時にするか」[保留]
    理由: 会話で結論が出ていない

この振り分けでよいですか？
```

判断に迷った項目は、勝手に決めずに**振り分け案の中で明示的に質問する**。

### 6. 書き込む

承認された内容を反映する。

**既存文書への追記**

- 該当箇所に統合する。**同じ事実を別の節に重ねて書かない。**
- 既存の記述と矛盾する場合は、上書きせずユーザーに確認する。
- ステータス印（`[確定]` / `[提案]` / `[保留]`）を必ず付ける。

**domain/ の新規作成**

- `docs/domain/_template.md` をコピーし、`docs/domain/<英語スラッグ>.md` として作る。

**ADR の新規作成**

- 採番は `docs/adr/` の既存ファイルの最大番号 + 1（4 桁ゼロ埋め）。`_template.md` は採番対象外。
- 形式は `docs/adr/_template.md` に従う。ステータスは `採用 [提案→要承認]`。
- **「検討した代替案」を必ず埋める。** 会話で代替案が議論されていなければ、書く前に調査するか、ユーザーに「他に検討した案はありますか」と聞く。**空の ADR は作らない。**
- 既存の決定を覆す場合は、**旧 ADR のステータスを「廃止（superseded by ADR-XXXX）」に更新**し、新 ADR の `関連:` に旧番号を書く。旧 ADR を消さない。

### 7. 初回のみ: プロダクト名を確定させる

テンプレートから作った直後の 1 回だけ必要。`{{プロダクト名}}` がまだ残っているかで判定する。

1. 会話でプロダクト名と一行説明が決まっていれば、`{{プロダクト名}}` `{{一行説明}}` を**全ファイル一括置換**する（`CLAUDE.md`・`README.md`・`docs/` 配下）。
   - **`docs/domain/_template.md` と `docs/adr/_template.md` は雛形なので置換しない。**
2. ワークスペースファイルをリネームする。

   ```bash
   git mv '{{プロダクト名}}.code-workspace' '<プロダクト名>.code-workspace'
   ```

   ファイル内のコメントにある `{{プロダクト名}}` の説明行も削除する。
3. まだ名前が決まっていなければ**置換しない**。プレースホルダのまま残し、次回に回す。

### 8. 周辺を同期する（忘れやすい）

- [ ] `docs/README.md` の構成ツリー（ファイルを新規作成した場合）
- [ ] `docs/README.md` の**一次情報の所在**表（新しい事実を確定させた場合）
- [ ] `docs/open-questions.md`（`[保留]` を書いた場合は登録、決着した場合は「解決済み」へ移動）
- [ ] 決着した項目の**本文側の `[保留]` を `[確定]` に更新**（open-questions だけ消さない）
- [ ] `CLAUDE.md`（決定がコーディング規約・依存方向・テスト方針に関わる場合、ADR 番号付きで反映）

### 9. 報告

書いた内容を差分の要点として報告し、判断を保留した項目があれば再提示する。

## してはいけないこと

- **会話にない内容を「一般的にはこう」で補完する。**
- 承認前にファイルを書き換える。
- 1 つの内容を複数の文書に重ねて書く（一次情報は 1 か所）。
- 混ざった内容を分割せずに片方の文書へ押し込む。
- 代替案の検討なしに ADR を作る。

すべて日本語で書く（ADR はである調）。
