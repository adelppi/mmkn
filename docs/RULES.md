# 配置ルール — どこに何を書くか

**この文書は docs/ 全体の書き方の正。** `/sync-docs` は書く前に、`/check-docs` は検査時に、必ずここを読む。

文書の役割が混ざると「どこを読めば正しいか」が曖昧になり、人も AI も判断を誤る。以下は好みの問題ではなく、**破ってはいけないルール**として扱う。

---

## 1. 配置の判定

書きたい内容が出てきたら、この順に判定する。

```
① 「作るか / 作らないか」の話か？          → features.md
② 技術を全部入れ替えても、その記述は残るか？
      残る   → domain/     （どう動くか）
      変わる → adr/        （どう作るか）
③ まだ決まっていないか？                    → open-questions.md
④ 決定ではなく「実行のしかた」か？          → operations.md
⑤ 概念とコード上の名前の対応か？            → glossary.md
```

④⑤ は ②で adr/ に振り分けられたものの中から、さらに分かれる。**決定と手順が同じ文書に同居すると、手順を直すたびに ADR が書き換わる**（ADR は覆るまで変えない記録）。名前の対応表を分けるのは、`domain/` に英語識別子を持ち込まないため。

### ② が唯一にして最強の判定基準

> **実装技術をまるごと別のものに入れ替えたとき、その記述は書き換えが必要か？**

- **書き換え不要** → ドメインのルール。`domain/` に書く。
- **書き換えが必要** → 技術的決定。`adr/` に書く。

迷ったらこの問いに戻る。

---

## 2. `docs/domain/` — インフラを持ち込まない

ドメイン文書は「**このプロダクトが何をするか**」を、実現手段から完全に切り離して書く。

### 書くもの

状態 / 遷移条件 / タイミング / 境界値 / 例外ケース / **起きないこと**

### 書いてはいけないもの

| 禁止 | 例 |
|---|---|
| 製品名・サービス名 | Supabase, Firebase, Postgres, Redis, S3, AWS |
| ライブラリ名 | expo-notifications, React Query, Prisma |
| DB 構造 | テーブル名, カラム名, 型, SQL, インデックス |
| API の形 | エンドポイント, HTTP メソッド, リクエスト形式 |
| 実現方式 | キャッシュする, バッチで回す, ポーリングする, トリガーで発火する |
| 画面の作り | コンポーネント名, レイアウト, 画面遷移の実装 |

### 判定テスト

> **その記述から製品名・テーブル名を消したとき、意味が通じなくなるか？**
> 通じなくなるなら、それはドメインではなく実装の話。

### NG → OK の書き換え例

| NG（domain に書かれていた） | なぜ NG | OK |
|---|---|---|
| `records` テーブルの `version` カラムが一致しなければ更新を弾く | DB 構造が前提 | 後から届いた変更は失敗し、失敗したことが操作者に伝わる<br>（実現方式は `adr/0005`） |
| 収支は表示のたびに再計算せず、キャッシュから読む | 実現方式が混入 | 収支は保存せず、導出するたびにその時点の記録から計算する |
| `@paralleldrive/cuid2` で参加コードを生成する | ライブラリが混入 | 参加コードはグループ作成時に生成し、変更・再生成しない<br>（形式は `adr/0002`） |
| Discord のチャンネル ID から Group を引く | 製品名が混入 | 外部サービス上の「場」と Group の対応を持つ |
| `POST /payments` で作成し 201 を返す | API の形が混入 | 支払者・負担者・金額・通貨・発生日で支払いを記録できる |

### グレーゾーンの扱い

「同時編集」「外部サービス連携」「通知」など、技術と密接に見える概念でも、**ユーザーから見た振る舞い**として書けば domain に属する。実現手段を書き始めた瞬間に adr の内容になる。

| 内容 | 置き場 |
|---|---|
| 2 人が同時に同じ記録を直したとき何が起きるか | `domain/` |
| 楽観ロックか、悲観ロックか | `adr/` |
| 外部サービスのアカウントを何に使い、何に使わないか | `domain/` |
| OAuth か、連携コードを人が運ぶか | `adr/` |
| 清算案の送金件数をどこまで保証するか | `domain/` |
| 貪欲法か、厳密に最小を求めるか | `adr/` |

## 3. `docs/adr/` — ドメイン知識を漏らさない

ADR は「**なぜその技術・方式を選んだか**」だけを書く。ドメインのルールは **参照するだけ**で、定義しない。

### 書くもの

技術選定 / 実装方式 / 決定の理由 / 制約 / 検討した代替案と不採用の理由

### 書いてはいけないもの

- 状態の意味・遷移条件・タイミングの**定義**
- 機能の有無
- 業務上の判断基準（「◯◯のときは△△とみなす」）

### 判定テスト

> **ADR の「決定」節を読んで、ドメインのルールを "初めて知る" ことができてしまうか？**
> できるなら、ドメイン知識が ADR に漏れている。

### NG → OK の書き換え例

| NG（adr に書かれていた） | なぜ NG | OK |
|---|---|---|
| 端数は負担者の先頭から 1 単位ずつ配る。実現は Member の ID 順で行う | 前半がドメインの定義 | `domain/record.md`「負担額の配分」の順序を、Member の ID による並びで実現する |
| 記録は Member なら誰でも編集できる。この判定を RLS で担保する | 制約の定義がドメイン | `domain/record.md` の編集の前提条件を、ドメイン層のエンティティが判定する |
| 清算案は保存せず表示のたびに導出する。導出は貪欲法で行う | 前半がドメインの定義 | `domain/settlement.md` の清算案の導出を、収支の絶対値が最大の負と正を順に相殺する貪欲法で行う |

### 必須リンク

**すべての ADR は `関連:` に、その決定が支えるドメイン文書か機能へのリンクを持つ。**
リンクが 1 つもない ADR は、ドメインを内側に抱え込んでいる疑いがある（純粋に技術内部で閉じた決定は例外）。

## 4. `docs/features.md` — 一覧に徹する

### 書くもの

機能の有無（持つ／持たない）の一覧。持たないものは**理由とセット**で。

### 書いてはいけないもの

- 動作の詳細ルール（状態・条件・タイミング）→ `domain/`
- ライブラリ・実装方式 → `adr/`

### NG → OK

| NG | OK |
|---|---|
| 支払いの記録 … 金額は正の整数。負担者に均等配分し、端数は先頭から 1 単位ずつ配る | 支払いの記録 … グループ外への支払いと、その負担者を記録する（詳細: `domain/record.md`） |

「持たないもの」の**理由の本体はここに置く**。他の文書からは、再掲せずここへリンクする。

---

## 5. `docs/overview.md` — 技術を書かない

ビジョン / ターゲット / 提供価値 / コアループ / 前提。

- コアループは**遷移の詳細を書かず**、`domain/` へリンクする。
- 「やらないこと」は考え方の軸だけ書き、完全な一覧は `features.md` へリンクする。
- 「前提」に技術スタックを 1 行書くのは可。ただし**選定理由は書かない**（`adr/` が正）。

---

## 6. `docs/open-questions.md` — 未決だけを置く

- 本文に `[保留]` を書いたら、必ずここにも登録する。
- 決着したら、**本文の `[保留]` を `[確定]` に更新してから**、ここを「解決済み」へ移す。本文を直さずここだけ消さない。
- 技術的な決定として決着したものは ADR 番号を記録する。

---

## 7. 一次情報は 1 か所だけ

**ある事実の「正」は 1 文書にだけ置く。他の文書は再掲せず、リンクする。**

- 同じルールを 2 か所に書いた時点で、片方が必ず古くなる。
- 引用したくなったら、代わりに `（`domain/record.md` を正とする）` と書く。
- 「どの事実がどこにあるか」は `docs/README.md` の一次情報表で管理する。**新しい事実を確定させたら、この表に 1 行足す。**

---

## 8. ステータス印

すべての記述に付ける。印のない断定的な記述は「誰も合意していない」と見なす。

| 印 | 意味 |
|---|---|
| `[確定]` | 議論で合意済み |
| `[提案]` | 叩き台。要確認 |
| `[保留]` | 詳細が未確定（`open-questions.md` で詰める） |

---

## 9. `docs/operations.md` — 手順だけを置く

ADR が「何をどうするか」を決め、この文書が「それをどう実行するか」を持つ。

### 書くもの

コマンドの実体 / 実行の順序 / 失敗したときに確認する場所 / 診断の手順 / 環境変数の置き場

### 書いてはいけないもの

- **選定の理由・代替案の検討** → `adr/`
- 業務ルール → `domain/`

### 判定テスト

> **その記述を書き換えたとき、意思決定そのものが変わるか？**
> 変わるなら ADR の内容。変わらない（同じ決定を別のやり方で実行するだけ）なら、ここ。

| 内容 | 置き場 |
|---|---|
| なぜマイグレーションを CI で適用するか | `adr/` |
| 適用が途中で止まったとき、どこを見るか | `operations.md` |
| なぜ Preview デプロイを持たないか | `adr/` |
| 手元で開発サーバーをどう起動するか | `operations.md` |

---

## 10. `docs/glossary.md` — 索引に徹する

日本語の概念と、コード上の英語識別子の対応表。

### 書くもの

用語 / コード上の名前 / 一次情報へのリンク。それと命名の規約。

### 書いてはいけないもの

- **用語の意味の定義** → `domain/`。ここに書き写した時点で、一次情報が 2 か所になる（§7）

### 判定テスト

> **この表から「一次情報」列を消したとき、用語の意味が分からなくなるか？**
> 分からなくなるのが正しい。分かってしまうなら、定義を書き写している。

---

## 違反を見つけたときの直し方

1. **消さずに移す。** 内容そのものは価値があるので、正しい文書へ移動する。
2. **移した先で書き直す。** domain へ移すなら技術語を落とす。adr へ移すなら「〜を実現する」の形にする。
3. **元の場所にはリンクを残す。** ただし内容は再掲しない。
