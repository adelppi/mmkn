## 環境変数

**この一覧がこの事実の一次情報（正）。** 区分の定義と、分ける理由は `adr/0003` を正とする。

### アプリが実行時に読む（ホスティング環境）

| 値 | 用途 |
|---|---|
| DB の接続文字列 | データアクセス。Supavisor の transaction mode（`adr/0005`） |
| 認証基盤の URL と anon key | 認証・セッション管理（`adr/0012`） |
| Discord の署名検証用公開鍵 | Interaction の署名検証（`adr/0006`） |

### リリースの自動処理が読む（GitHub の秘密情報）

| 値 | 用途 |
|---|---|
| 本番 DB の接続文字列 | マイグレーションの適用（`adr/0011`） |
| Discord の Bot Token | スラッシュコマンドの登録（`adr/0006`） |
| Discord の Application ID | 同上 |
| ホスティングの操作用トークン | デプロイ（`adr/0011`：デプロイも GitHub Actions から行う） |
| ホスティングの組織 ID とプロジェクト ID | 同上。**どのプロジェクトへ送るかを決める** |

### 手元の作業だけが読む（ローカルのみ）

| 値 | 用途 |
|---|---|
| ローカル DB の接続文字列 | 開発サーバー・永続化テスト・クライアント間整合・E2E |
| 診断コマンドが使う値 | 下記「診断」 |

### E2E を回すときだけ立つ（手元と CI）

| 値 | 用途 |
|---|---|
| 偽の認証への切り替え | E2E の間だけ、アプリが繋ぐ先を偽の認証にする（`adr/0010`「E2E が使う認証基盤」） |
| Discord の署名検証用公開鍵 | E2E が自分で署名するための鍵に差し替える（`tests/e2e/support/discord-key.ts`） |

**この 2 つは人が設定しない。** E2E の設定（`playwright.config.ts`）が、起動するアプリにだけ渡す。

**アプリが実行時に使わない値をホスティング環境に置かない**（`adr/0011`）。Discord の Bot Token とホスティングの操作用トークンがこれにあたる。

**偽の認証への切り替えをホスティング環境に置かない。** 置くと、本物のログインを通らずに任意の識別子でログインできる状態になる（`adr/0010`「E2E が使う認証基盤」の代償）。

テンプレートはこの 3 区分で分けて用意する。実体は**リポジトリ直下の `.env.example`**。値は空。**`.env.local` はコミットされない**（`.gitignore`）。

| 区分 | 置き場所 | 設定する場所 |
|---|---|---|
| アプリが実行時に読む | ホスティング環境 | Vercel のプロジェクト設定 |
| リリースの自動処理が読む | CI の秘密情報 | GitHub の Actions secrets |
| 手元の作業だけが読む | ローカルのみ | `.env.local` |

**上の 3 つの表は「値」を用途で並べたものであり、変数名を 3 組に分けろという意味ではない。** 名前は用途ごとではなく**読むコードごとに 1 つ**であり、同じ名前が環境ごとに違う値を持つ。DB の接続文字列は 3 区分すべてに現れるが、変数名はいずれも `DATABASE_URL` である（`adr/0005`）。区分が違えば置き場所が違うため、同じ名前でも値は衝突しない。

**用途ごとに別名を作らない。読むコードが存在しない変数を先に作らない。** 名前を増やすと、どれが実際に読まれているか分からなくなる（`adr/0003` が言う「設定したのに動かない」の別の形）。

## 手元の準備

```
npm ci        依存を入れる
npm run dev   開発サーバーを起動する
```

Postgres を使うものは、これに加えて次が要る。

```
docker compose up -d --wait   Postgres を起動する（Healthy になるまで待つ）
docker compose down           止める（データは残る）
docker compose down -v        止めて、データも捨てる
```

定義は**リポジトリ直下の `docker-compose.yml`**。`127.0.0.1:5432` にだけ bind し、利用者名・パスワード・DB 名はいずれも `mmkn`。**手元専用であり秘密情報ではない**ため、接続文字列は `.env.local` に次の形で書ける。

```
DATABASE_URL=postgresql://mmkn:mmkn@127.0.0.1:5432/mmkn
```

**手元の `DATABASE_URL` に本番を書かない**（`adr/0011`・`.env.example`）。永続化テストは回るたびに DB の中身を空にするため、接続先を間違えるとそこにあるデータを消す。**接続先がループバック以外なら永続化テストは落ちる**（`src/infra/db/test-support.ts`）。一度きり別の接続先を指したいときは `DATABASE_URL=… npm run test:db` で上書きする（実際の環境変数が `.env.local` より優先される）。

マイグレーションを適用する。

```
npm run db:generate   スキーマ定義から SQL を生成する（src/infra/db/migrations/ に出る）
npm run db:migrate    生成済みの SQL を DATABASE_URL の DB に当てる
```

**生成した SQL はコミットする**（`adr/0005`）。`db:generate` の出力を見てから PR に含める。永続化テストは**コミット済みの SQL をそのまま当てる**ため、生成し忘れるとテストが落ちる。

**本番（Supabase）とメジャーバージョンを合わせてある。** ずれると、本番でだけ通らない SQL に手元で気づけない。本番のバージョンは診断（下記「診断」）で確認する。

永続化テストとクライアント間整合と E2E は、この Postgres を使う（`adr/0010`）。**単体テストだけは何も起動せずに回る状態を保つ。**

E2E はこれに加えてブラウザが要る。**一度入れれば以降は要らない。**

```
npx playwright install chromium   E2E が使うブラウザを入れる
```

## テストの回し方

| 回すもの | いつ | コマンド |
|---|---|---|
| 単体テスト | 手元で随時。外部依存なし | `npm run test:unit` |
| 永続化 | Postgres を起動してから | `npm run test:db` |
| クライアント間整合 | Postgres を起動してから | `npm run test:parity` |
| E2E（Playwright） | 手元では必要なときだけ。CI では main へのマージ時 | `npm run test:e2e`（Postgres とブラウザを先に用意する） |
| Storybook | 手元で表示を確認するとき | `npm run storybook`（CI は `npm run build:storybook`） |

種別ごとの対象と置き場は `adr/0010` を正とする。単体テストは対象の隣（`*.test.ts`）に、**永続化テストも対象の隣（`*.db.test.ts`）**に置く。名前を分けてあるのは、`npm run test:unit` の対象から外して**単体テストが何も起動せずに回る状態を保つ**ためで、設定も別（`vitest.config.ts` と `vitest.config.db.ts`）。

Storybook も対象の隣（`presentation.stories.tsx`）に置く（`adr/0009`「配置と命名」）。**スナップショット比較は持たない**ため、CI が確かめるのはビルドが通ることだけで、表示そのものは手元で目で見る（`adr/0010`「Storybook」）。設定は `.storybook/`。

クライアント間整合だけは `tests/client-parity/` に置く。**`adapter/web` と `adapter/discord` の両方を import するため、対象が 1 つの層に定まらない**（`adr/0010`）。設定も別（`vitest.config.parity.ts`）で、永続化テストと同じくローカル Postgres を使う。**run のたびに DB の中身を空にする。**

E2E も `tests/e2e/` に置く（設定は `playwright.config.ts`）。ランナーが違うため、他のテストとはコマンドも分かれている。

- **起動するのはビルドしたアプリで、開発サーバーではない。** ポートは 3100 で、手元の開発サーバー（3000）と重ならない
- **接続するのはローカル Postgres で、回るたびに中身を空にする。** 接続先がループバックでなければ、そこで落ちる（`src/infra/db/test-support.ts`）
- **認証は偽のものに差し替わる**（`adr/0010`「E2E が使う認証基盤」）。**本物の認証基盤には繋がない**ため、認証の環境変数は要らない
- Discord のエンドポイントへ投げる Interaction は、E2E が自分で署名する。鍵は `tests/e2e/support/discord-key.ts` にあり、**秘密情報ではない**（守るものが無く、使うのは起動したアプリだけ）

## リリース

main にマージすると、GitHub Actions が 4 段階で走る（`.github/workflows/main.yml`）。**何をどの順で走らせるかと、その理由は `adr/0011` を正とする。** ここには持たない。

**Vercel の Git 連携による自動デプロイは、リポジトリ直下の `vercel.json` で切ってある**（`adr/0011`：Preview を持たず、デプロイも GitHub Actions から行う）。**この設定を外すと、main への push で二重にデプロイが走る。**

### 走らせる前に用意するもの

**GitHub の秘密情報に、上記「リリースの自動処理が読む」の値をすべて登録しておく。** 1 つでも欠けると、その段でリリースが止まる。

| 段 | 欠けると止まるもの |
|---|---|
| 2. マイグレーション | 本番 DB の接続文字列 |
| 3. デプロイ | ホスティングの操作用トークン・組織 ID・プロジェクト ID |
| 4. コマンド登録 | Discord の Bot Token・Application ID |

### 途中で失敗したときの確認

| どこで止まった | 状態 | やること |
|---|---|---|
| 1. E2E | 本番は変わっていない | 直して再度マージする |
| 2. マイグレーション | 本番のスキーマが中途半端な可能性がある | 適用状況を診断で確認してから対処する |
| 3. デプロイ | **スキーマだけ新しく、コードが古い** | 前方のみのマイグレーション（`adr/0011`）を守っていれば古いコードでも動く。デプロイを再実行する |
| 4. コマンド登録 | Web は正常、Discord だけ古い定義 | 登録の差分を診断で確認し、再実行する |

### スキーマを壊す変更を出すとき

**2 回のリリースに分ける**（`adr/0011`）。列の改名なら、1 回目で新しい列を足して両方に書き、2 回目で古い列を落とす。

## 診断

設定が正しいかを自力で確かめる手段。**テストは偽実装と手元の Postgres で回るため、本番の設定が正しいかは別に確かめる必要がある**（`adr/0005`・`adr/0006`）。

| 診断 | 見るもの | コマンド |
|---|---|---|
| DB 疎通 | 本番 DB に接続できるか。Supavisor の transaction mode で prepared statement の無効化が効いているか | まだ無い |
| マイグレーション適用状況 | コミット済みの SQL のうち、どこまで本番に当たっているか | まだ無い |
| RLS の網羅 | 全テーブルで RLS が有効か。**テーブルを追加したときの付け忘れがここで出る**（`adr/0005`） | `npm run test:db`（`src/infra/db/schema.db.test.ts`） |
| Discord コマンドの登録状況と差分 | 何が登録されているか。ソース上の宣言との差 | `npm run discord:diagnose` |
| Discord エンドポイント疎通 | 届くか。**署名不正に 401 を返すか** | `npm run discord:diagnose -- <URL>` |
| セッションの署名方式 | 認証基盤が非対称鍵で署名しているか。**外れても壊れず、遅くなるだけなので検査では出ない**（`adr/0008`「セッションの検証」） | 下記 |

### セッションの署名方式

**画面の移動が理由なく遅くなったときに見る。** 検証を署名だけで済ませられるのは、認証基盤が非対称鍵で署名している間だけである。対称鍵に戻ると、検証は認証基盤への往復に戻る。**壊れないため、テストにも型検査にも出ない。**

```
curl -s "$SUPABASE_URL/auth/v1/.well-known/jwks.json"
```

- `keys` に `"alg": "ES256"`（または `RS256`）の鍵が入っていれば、非対称鍵で署名している
- `{"keys":[]}` が返るなら対称鍵に戻っている。**認証基盤の設定で署名鍵を非対称のものへ移す**
- 読むのは `SUPABASE_URL` だけ。**鍵は公開されているものなので、秘密情報を渡さずに確かめられる**

### Discord

```
npm run discord:diagnose                          登録状況と、宣言との差分
npm run discord:diagnose https://mmkn.example     加えてエンドポイントの疎通
npm run discord:register                          差分があれば登録する
npm run discord:register -- --force               差分が無くても登録し直す
```

- 読むのは `DISCORD_APPLICATION_ID` と `DISCORD_BOT_TOKEN`（`.env.local`）。**この 2 つはホスティング環境に置かない**（上記「環境変数」）
- **登録する内容の正はソース上の宣言**（`src/adapter/discord/definitions.ts`）。診断も登録も同じ宣言を読むため、宣言を直せば両方に効く（`adr/0006`）
- **グローバル登録は反映まで最大 1 時間かかる**（`adr/0006`）。「登録した」と出たあと、すぐにクライアントへ出ないのは正常
- 疎通で確かめられるのは**署名不正に 401 を返すこと**までである。正しい署名を作るには Discord 側の秘密鍵が要り、こちらには無い。**正しい署名での往復は E2E が見る**（`adr/0010`「E2E の範囲」）
- **差分があるのに登録が失敗したら、Discord 側は古い定義のまま動く。** Web は正常であり、巻き戻しは要らない（`adr/0011`）

### ログを見るとき

障害の報告を受けたら、ホスティング環境のログを**相関 ID** で絞る（`adr/0014`）。記録の中身はログに出していないため、そこから先は DB を見る。

## 通貨表の更新

通貨の一覧と最小単位の桁数は、`src/domain/money/currency-table.ts` にコミットした表として持つ（`adr/0016`）。**生成器も定期実行も無い。表は人が直接編集する。**

### いつ直すか

**知らせは来ない。** ISO 4217 の改定に気づく仕組みを持たない（`adr/0016`）ため、直す場面は次のどちらかで訪れる。

| きっかけ | 何が起きている |
|---|---|
| **使いたい通貨が弾かれたと報告される** | 表に無い。新設された通貨か、書き写しの漏れ |
| 改定を知って、自分で確かめにいく | 上記以外に契機は無い |

**桁数の変更は、どちらのきっかけにも現れない**（`adr/0016`「改定に追随する仕組みを持たない」）。表を触る用事ができたときは、**ついでに桁数の差分も見ておく。** それがこの決定で唯一できる緩和である。

### 直す手順

1. 表の先頭に書かれた**取得元と公表日**を見る。取得元は `adr/0013`「取得元の形」に記録がある（維持機関が現行・廃止済みの一覧を XML で配っている）
2. 公表データと表を突き合わせ、**差分を手で当てる**
   - **新設された通貨** … 行を足す
   - **桁数が変わった通貨** … 桁数を直す。**過去の記録の解釈が変わる。** 影響する記録があるかを先に確かめる
   - **削除された通貨** … **行を消さず、廃止の印を立てる。** 桁数はそのまま残す。消すと既存の記録が読めなくなる（`domain/money.md`「廃止された通貨」）
   - **最小単位の桁数を持たないコード** … 入れない（`domain/money.md`「最小単位を持たない通貨コードは扱わない」）
3. 表の先頭の**公表日を、今回突き合わせた版に更新する**
4. `npm run test:unit` を回す。コードの重複と桁数の形は単体テストが見る（`adr/0016`）。**値が ISO 4217 と一致することはテストされない。そこはレビューが見る**
5. 通常どおり PR にして main へマージする。リリースに乗る

**行が消える差分を作らない。** これは自動でも手動でも変わらない唯一の禁止事項で、当てると既存の記録が読めなくなる。

**通貨の追加・廃止は、この手順でしか起きない。** 実行環境の更新では変わらない。

## 実装着手時に必ず確かめること

**決定済みだが、前提が外れると影響が大きく、確認が安いもの。** 未決ではないため `open-questions.md` には置かない。

| 確認すること | 外れたときの影響 | 決定の記録 |
|---|---|---|
| 認証基盤が保存する Discord のユーザー ID と、スラッシュコマンドで届くユーザー ID が同一か | Discord 側が丸ごと動かない | `adr/0012` |
| 同じ外部アカウントで再ログインしたとき、認証基盤が同じ user を返すか（実アカウント 1 件で 2 回ログインする） | 同じ人が毎回別の User になる | `adr/0012` |
| 最後の 1 つのログイン手段を削除しようとしたときに、認証基盤が拒むか | 拒まないなら mmkn 側で止める必要がある | `adr/0012` |
| ホスティング環境で、応答を返したあとの処理継続が Discord の follow-up に間に合うか | 一律 deferred が成立せず、Discord の返信が届かない | `adr/0003`・`adr/0006` |
| 認可画面をまたぐログイン手段の追加が実際に成立するか（自動化しないため手動） | ログイン手段を増やせない | `adr/0012`・`adr/0010` |
| **入口が期限切れのトークンを更新し続けるか**（下記「確かめ方（セッションが切れないこと）」）。**入口に手を入れた PR では毎回** | しばらく使っていると勝手にログアウトされる | `adr/0008` |

**上から 5 行は、外部サービスの管理画面での作業（Vercel のプロジェクト・Discord のアプリケーション・Google の OAuth クライアント）が済んでいないと確かめられない。** 最後の 1 行は、デプロイした環境で本物のログインができるようになってから通す。

### 確かめ方（セッションが切れないこと）

**入口（`proxy.ts`）が期限切れのトークンを更新し続けているかを、人が確かめる。** 入口は、更新するものが無いリクエストを素通しする（`adr/0008`「どのリクエストで更新するか」）。**素通しの条件を広げすぎると、更新の機会そのものが消える。**

**E2E では確かめられない。** E2E は偽の認証を使い、そこにはトークンの期限が無い（`adr/0010`「E2E が使う認証基盤」）。

**入口に手を入れた PR では、毎回これを通す。**

1. デプロイした環境で、本物のログインを済ませる
2. ブラウザの開発者ツールで、認証基盤の cookie（名前が `sb-` で始まるもの）の値を控える
3. **アクセストークンの寿命を越えるまで待つ**（認証基盤の設定。既定は 1 時間）。**タブを閉じてよい**
4. 記録一覧を開き、続けてタブ（記録 / 収支 / 精算）を切り替える
5. **見えることを確かめる。** ログイン画面に飛ばされたら、更新が起きていない
6. 控えた cookie の値と見比べる。**値が変わっていれば更新され、書き戻されている**

**4 のタブの切り替えは、先読みと一緒に確かめるためにある。** 3 つのタブは見ている間に他の 2 つを先に取りにいく（`adr/0009`「直前に見たものを取り直さない」）。**それも入口を通る**（`adr/0008`「画面の先読みは素通ししない」）ため、期限が切れた直後は**同じセッションの更新が同時に走る。**

**飛ばされたときに見る場所は 2 つある。**

| 6 の値 | 疑うところ |
|---|---|
| 変わっていない | **素通しの条件が広すぎる。** 実際の遷移で更新が起きているかを `proxy.ts` の条件から確かめる |
| 変わっているのに飛ばされる | **同時に走った更新が互いを壊している。** 認証基盤が、同じトークンでの更新を一定時間まとめて扱う設定になっているかを確かめる |

### 確かめ方（Discord の 2 件）

**どちらも実物の往復が要る。** 手元のテストでは代わりにならない（テストは偽実装と手元の Postgres で回る）。

**① 認証基盤が保存する Discord のユーザー ID と、スラッシュコマンドで届くユーザー ID が同一か**

1. Web から Discord でログインする（またはログイン手段として追加する）
2. 認証基盤の `auth.identities` で、その人の `provider = 'discord'` の行の `provider_id` を控える
3. Discord で `/mmkn balance` を実行する（対応づけの済んだチャンネルで）
4. **案内ではなく収支が返れば同一である。** 「mmkn のアカウントが必要です」と返れば同一ではない
   - ホスティング環境のログで `usecase: "resolveActor"` の `outcome` を見れば、どこで分かれたかが分かる（`adr/0014`）
5. **外れていた場合の影響は「Discord 側が丸ごと動かない」。** 外部アカウントの読み方（`src/adapter/discord/context.ts` の `DISCORD_SERVICE` と、Interaction のどこからユーザー ID を取るか）を見直す

**② ホスティング環境で、応答を返したあとの処理継続が Discord の follow-up に間に合うか**

1. デプロイした環境で `npm run discord:diagnose <URL>` を通す（署名不正に 401 が返ること）
2. Discord で `/mmkn balance` を実行する
3. **「考え中」が結果に変われば間に合っている。** 「アプリケーションが応答しませんでした」のまま止まれば間に合っていない
4. ログに `usecase: "viewSettlement"` の行が出ているかを見る
   - **行が出ていて表示が変わらない** … follow-up の送信が届いていない（応答後の処理継続が途中で切られている）
   - **行も出ていない** … deferred の後で実行が終わっている
5. **外れていた場合の影響は「一律 deferred が成立しない」**（`adr/0003`・`adr/0006`）。ADR の前提そのものが崩れるため、接続方式の見直しになる
