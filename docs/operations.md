## 環境変数

**この一覧がこの事実の一次情報（正）。** 区分の定義と、分ける理由は `adr/0003` を正とする。

### アプリが実行時に読む（ホスティング環境）

| 値 | 用途 |
|---|---|
| DB の接続文字列 | データアクセス。Supavisor の transaction mode（`adr/0005`） |
| 認証基盤の URL と anon key | 認証・セッション管理（`adr/0012`） |
| Discord の署名検証用公開鍵 | Interaction の署名検証（`adr/0006`） |

### リリースの自動処理が読む（GitHub の秘密情報）

| 値 | 用途 |
|---|---|
| 本番 DB の接続文字列 | マイグレーションの適用（`adr/0011`） |
| Discord の Bot Token | スラッシュコマンドの登録（`adr/0006`） |
| Discord の Application ID | 同上 |

### 手元の作業だけが読む（ローカルのみ）

| 値 | 用途 |
|---|---|
| ローカル DB の接続文字列 | 開発サーバー・永続化テスト・E2E |
| 診断コマンドが使う値 | 下記「診断」 |

**アプリが実行時に使わない値をホスティング環境に置かない**（`adr/0011`）。Discord の Bot Token がこれにあたる。

テンプレートはこの 3 区分で分けて用意する。実体は**リポジトリ直下の `.env.example`**。値は空。**`.env.local` はコミットされない**（`.gitignore`）。

| 区分 | 置き場所 | 設定する場所 |
|---|---|---|
| アプリが実行時に読む | ホスティング環境 | Vercel のプロジェクト設定 |
| リリースの自動処理が読む | CI の秘密情報 | GitHub の Actions secrets |
| 手元の作業だけが読む | ローカルのみ | `.env.local` |

**上の 3 つの表は「値」を用途で並べたものであり、変数名を 3 組に分けろという意味ではない。** 名前は用途ごとではなく**読むコードごとに 1 つ**であり、同じ名前が環境ごとに違う値を持つ。DB の接続文字列は 3 区分すべてに現れるが、変数名はいずれも `DATABASE_URL` である（`adr/0005`）。区分が違えば置き場所が違うため、同じ名前でも値は衝突しない。

**用途ごとに別名を作らない。読むコードが存在しない変数を先に作らない。** 名前を増やすと、どれが実際に読まれているか分からなくなる（`adr/0003` が言う「設定したのに動かない」の別の形）。

## 手元の準備

```
npm ci        依存を入れる
npm run dev   開発サーバーを起動する
```

Postgres を使うものは、これに加えて次が要る。

```
docker compose up -d --wait   Postgres を起動する（Healthy になるまで待つ）
docker compose down           止める（データは残る）
docker compose down -v        止めて、データも捨てる
```

定義は**リポジトリ直下の `docker-compose.yml`**。`127.0.0.1:5432` にだけ bind し、利用者名・パスワード・DB 名はいずれも `mmkn`。**手元専用であり秘密情報ではない**ため、接続文字列は `.env.local` に次の形で書ける。

```
DATABASE_URL=postgresql://mmkn:mmkn@127.0.0.1:5432/mmkn
```

**手元の `DATABASE_URL` に本番を書かない**（`adr/0011`・`.env.example`）。永続化テストは回るたびに DB の中身を空にするため、接続先を間違えるとそこにあるデータを消す。**接続先がループバック以外なら永続化テストは落ちる**（`src/infra/db/test-support.ts`）。一度きり別の接続先を指したいときは `DATABASE_URL=… npm run test:db` で上書きする（実際の環境変数が `.env.local` より優先される）。

マイグレーションを適用する。

```
npm run db:generate   スキーマ定義から SQL を生成する（src/infra/db/migrations/ に出る）
npm run db:migrate    生成済みの SQL を DATABASE_URL の DB に当てる
```

**生成した SQL はコミットする**（`adr/0005`）。`db:generate` の出力を見てから PR に含める。永続化テストは**コミット済みの SQL をそのまま当てる**ため、生成し忘れるとテストが落ちる。

**本番（Supabase）とメジャーバージョンを合わせてある。** ずれると、本番でだけ通らない SQL に手元で気づけない。本番のバージョンは診断（下記「診断」）で確認する。

永続化テストと E2E は、この Postgres を使う（`adr/0010`）。**単体テストだけは何も起動せずに回る状態を保つ。**

## 検査の回し方

PR で回すものと同じものを、手元から単独で回せる（CI の構成は `adr/0011` を正とする）。

| 回すもの | コマンド |
|---|---|
| lint | `npm run lint` |
| 型検査 | `npm run typecheck` |
| 単体テスト | `npm run test:unit` |
| 永続化テスト | `npm run test:db`（先に `docker compose up -d --wait`） |
| 依存方向の検査 | `npm run check:deps` |

依存方向の検査の設定は `.dependency-cruiser.cjs` にあり、ルールの正は `adr/0008`「依存方向の機械検査のルール」。**検査が落ちたら、通すために設定を緩めない。** 直すのは import のほう。

## テストの回し方

| 回すもの | いつ | コマンド |
|---|---|---|
| 単体テスト | 手元で随時。外部依存なし | `npm run test:unit` |
| 永続化 | Postgres を起動してから | `npm run test:db` |
| クライアント間整合 | Postgres を起動してから | まだ無い |
| E2E（Playwright） | 手元では必要なときだけ。CI では main へのマージ時 | まだ無い |
| Storybook | 手元で表示を確認するとき | まだ無い |

種別ごとの対象と置き場は `adr/0010` を正とする。単体テストは対象の隣（`*.test.ts`）に、**永続化テストも対象の隣（`*.db.test.ts`）**に置く。名前を分けてあるのは、`npm run test:unit` の対象から外して**単体テストが何も起動せずに回る状態を保つ**ためで、設定も別（`vitest.config.ts` と `vitest.config.db.ts`）。

## リリース

main にマージすると、GitHub Actions が 4 段階で走る。**何をどの順で走らせるかと、その理由は `adr/0011` を正とする。** ここには持たない。

### 途中で失敗したときの確認

| どこで止まった | 状態 | やること |
|---|---|---|
| 1. E2E | 本番は変わっていない | 直して再度マージする |
| 2. マイグレーション | 本番のスキーマが中途半端な可能性がある | 適用状況を診断で確認してから対処する |
| 3. デプロイ | **スキーマだけ新しく、コードが古い** | 前方のみのマイグレーション（`adr/0011`）を守っていれば古いコードでも動く。デプロイを再実行する |
| 4. コマンド登録 | Web は正常、Discord だけ古い定義 | 登録の差分を診断で確認し、再実行する |

### スキーマを壊す変更を出すとき

**2 回のリリースに分ける**（`adr/0011`）。列の改名なら、1 回目で新しい列を足して両方に書き、2 回目で古い列を落とす。

## 診断

設定が正しいかを自力で確かめる手段。**テストは偽実装と手元の Postgres で回るため、本番の設定が正しいかは別に確かめる必要がある**（`adr/0005`・`adr/0006`）。

| 診断 | 見るもの |
|---|---|
| DB 疎通 | 本番 DB に接続できるか。Supavisor の transaction mode で prepared statement の無効化が効いているか |
| マイグレーション適用状況 | コミット済みの SQL のうち、どこまで本番に当たっているか |
| RLS の網羅 | 全テーブルで RLS が有効か。**テーブルを追加したときの付け忘れがここで出る**（`adr/0005`） |
| Discord コマンドの差分 | ソース上の宣言と、Discord に登録されている定義の差 |
| Discord エンドポイント疎通 | 署名付きリクエストに正しく応答するか。署名不正に 401 を返すか |

### ログを見るとき

障害の報告を受けたら、ホスティング環境のログを**相関 ID** で絞る（`adr/0014`）。記録の中身はログに出していないため、そこから先は DB を見る。

## 通貨表の更新

通貨の一覧と最小単位の桁数は、`src/domain/money/currency-table.ts` にコミットした表として持つ（`adr/0016`）。**生成器も定期実行も無い。表は人が直接編集する。**

### いつ直すか

**知らせは来ない。** ISO 4217 の改定に気づく仕組みを持たない（`adr/0016`）ため、直す場面は次のどちらかで訪れる。

| きっかけ | 何が起きている |
|---|---|
| **使いたい通貨が弾かれたと報告される** | 表に無い。新設された通貨か、書き写しの漏れ |
| 改定を知って、自分で確かめにいく | 上記以外に契機は無い |

**桁数の変更は、どちらのきっかけにも現れない**（`adr/0016`「改定に追随する仕組みを持たない」）。表を触る用事ができたときは、**ついでに桁数の差分も見ておく。** それがこの決定で唯一できる緩和である。

### 直す手順

1. 表の先頭に書かれた**取得元と公表日**を見る。取得元は `adr/0013`「取得元の形」に記録がある（維持機関が現行・廃止済みの一覧を XML で配っている）
2. 公表データと表を突き合わせ、**差分を手で当てる**
   - **新設された通貨** … 行を足す
   - **桁数が変わった通貨** … 桁数を直す。**過去の記録の解釈が変わる。** 影響する記録があるかを先に確かめる
   - **削除された通貨** … **行を消さず、廃止の印を立てる。** 桁数はそのまま残す。消すと既存の記録が読めなくなる（`domain/money.md`「廃止された通貨」）
   - **最小単位の桁数を持たないコード** … 入れない（`domain/money.md`「最小単位を持たない通貨コードは扱わない」）
3. 表の先頭の**公表日を、今回突き合わせた版に更新する**
4. `npm run test:unit` を回す。コードの重複と桁数の形は単体テストが見る（`adr/0016`）。**値が ISO 4217 と一致することはテストされない。そこはレビューが見る**
5. 通常どおり PR にして main へマージする。リリースに乗る

**行が消える差分を作らない。** これは自動でも手動でも変わらない唯一の禁止事項で、当てると既存の記録が読めなくなる。

**通貨の追加・廃止は、この手順でしか起きない。** 実行環境の更新では変わらない。

## 実装着手時に必ず確かめること

**決定済みだが、前提が外れると影響が大きく、確認が安いもの。** 未決ではないため `open-questions.md` には置かない。

| 確認すること | 外れたときの影響 | 決定の記録 |
|---|---|---|
| 認証基盤が保存する Discord のユーザー ID と、スラッシュコマンドで届くユーザー ID が同一か | Discord 側が丸ごと動かない | `adr/0012` |
| 同じ外部アカウントで再ログインしたとき、認証基盤が同じ user を返すか（実アカウント 1 件で 2 回ログインする） | 同じ人が毎回別の User になる | `adr/0012` |
| 最後の 1 つのログイン手段を削除しようとしたときに、認証基盤が拒むか | 拒まないなら mmkn 側で止める必要がある | `adr/0012` |
| ホスティング環境で、応答を返したあとの処理継続が Discord の follow-up に間に合うか | 一律 deferred が成立せず、Discord の返信が届かない | `adr/0003`・`adr/0006` |
| 認可画面をまたぐログイン手段の追加が実際に成立するか（自動化しないため手動） | ログイン手段を増やせない | `adr/0012`・`adr/0010` |

**残っている 5 行はいずれも、外部サービスの管理画面での作業（Vercel のプロジェクト・Discord のアプリケーション・Google の OAuth クライアント）が済んでいないと確かめられない。**
