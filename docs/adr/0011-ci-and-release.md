# ADR-0011: CI とリリースを GitHub Actions に集約し、Preview デプロイを持たない

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/features.md`, `adr/0003-tech-stack.md`, `adr/0004-layers-and-dependencies.md`, `adr/0005-data-access-and-authorization.md`, `adr/0006-discord-http-interactions.md`, `adr/0010-testing.md`, `adr/0014-logging.md`, `adr/0016-currency-table-committed.md`

## コンテキスト

複数の ADR が「CI で落とす」「リリース手順に組み込む」と個別に要求しているが、**その手順の正がどこにも無い。**

| 要求 | 出どころ |
|---|---|
| 依存方向の違反を CI で落とす。検査の CI 組み込みは後回しにできない | `adr/0004` |
| 生成した SQL をリリースの一部として適用する。push 型は使わない | `adr/0005` |
| スラッシュコマンドの登録をリリースの自動処理として走らせる | `adr/0006` |
| どのテストをいつ回すか | `adr/0010` |

加えて `adr/0006` は「コマンド登録がデプロイと独立しているため、**デプロイしたのに反映されない**状態が構造的に起こり得る」を留意点に挙げている。ここを人の記憶に任せないことが、この ADR の主目的になる。

制約は 2 つ。

- **個人開発であり、PR の待ち時間はそのまま自分の待ち時間になる**（`overview.md`）
- **DB は 1 つしか持たない。** 運用コストを無料枠に収める（`overview.md`「前提」）ため、環境ごとに Supabase プロジェクトを増やさない

## 決定

### GitHub Actions に集約する

CI もリリースも GitHub Actions で走らせる。Vercel の Git 連携による自動デプロイには任せない。マイグレーションの適用とコマンド登録をデプロイの前後に挟む必要があり、順序を自分で持つ必要があるため。

### PR で回すもの

| 内容 | 出どころ |
|---|---|
| lint / typecheck | — |
| 単体テスト | `adr/0010` |
| 永続化テスト（使い捨ての Postgres） | `adr/0010` |
| クライアント間整合のテスト | `adr/0010` |
| 依存方向の検査（`dependency-cruiser`） | `adr/0004` |
| Storybook のビルド | `adr/0010` |

**E2E は PR では回さない。** 最も遅く、ここまでの検査を通ったうえで落ちる頻度が低いため、待ち時間に見合わない。

### main へのマージ時に走らせるもの

**順序が意味を持つ。**

```
1. E2E（Playwright）          … 使い捨ての Postgres と、CI 内で起動したアプリに対して回す
2. マイグレーションの適用      … 本番 DB。失敗したら 3 以降に進まない
3. デプロイ                    … Vercel
4. スラッシュコマンドの登録    … 定義に差分があるときだけ実行する
```

- **E2E は本番に対して回さない。** DB が 1 つしか無いため、本番に回すと E2E が作ったグループと記録が実データに混ざる
- **E2E が使う認証基盤をどうするかは未決** `[保留]`（`open-questions.md` #14）。上の一文は DB についてのものであり、認証基盤には何も言っていない。**DB には「使い捨ての Postgres」という逃げ道があるが、認証基盤には対応する逃げ道が無い。** CI 内でアプリを起動する以上アプリは認証基盤に繋がり、本番の認証基盤に向ければ E2E が本物のアカウントを作る。`overview.md`「前提」の無料枠と、`adr/0015` が扱っているデータ保全の両方に触れるため、E2E を作る時点で決める
- **マイグレーションが失敗したらデプロイしない。** 逆順にすると、新しいコードが存在しない列を前提に動く時間が生まれる
- **コマンド登録が失敗してもデプロイは巻き戻さない。** Discord 側が古いコマンド定義のまま動くだけで、Web は正常に動く。検知は診断コマンドで行う（`docs/operations.md`）

### 定期実行するものを持たない

**時刻で起動するジョブを 1 つも持たない。** GitHub Actions が走るのは、**PR と main へのマージの 2 経路だけ**である。

2026-08-13 まで、この枠には「通貨表の生成と、差分があれば PR の作成」が週次で入っていた。**`adr/0016` が生成器も定期実行も持たないと決めたため、枠に入るものが無くなった。**

- **外部のネットワークに触れるジョブを持たない。** どちらの経路も、リポジトリの中にあるものだけで完結する
- 定期実行を足したくなったら、**`adr/0014` が監視も通知も持たないことを先に確かめる。** 時刻で走るジョブの失敗は、誰も見に行かなければ気づかれない

### マイグレーションは前方のみ

**戻すためのマイグレーションを持たない。** 代わりに、**既存のデータを壊す変更は 2 回のリリースに分ける。**

```
列の改名を行う場合

  リリース 1  新しい列を足し、両方に書く
  リリース 2  古い列を読まなくなったことを確認してから、古い列を落とす
```

個人開発で down を書いても、実際に使う場面で正しく動く保証がない（書いた時点でしか検証されないため）。それより、戻す必要が生じない形に変更を割る方を採る。

### Preview デプロイを持たない

**Vercel の Preview デプロイを無効にする。**

Preview 環境が本来効くのは、レビュアーに動くものを見せる場面である。個人開発でレビュアーがいない（`overview.md`）ため、その目的が成立しない。

そして DB は 1 つしか無い。Preview を残すと**未マージのコードが本番の金銭記録を書き換えられる状態**になり、マイグレーションを main マージ時に適用する構成（上記）と組み合わさると、Preview のコードだけが古いスキーマや新しいスキーマとずれて動く時間帯も生まれる。

動作確認は、手元の開発サーバーと本番デプロイで行う。

### 着手時の確認結果 [確定]

**マイグレーションの適用に、アプリと同じ接続設定が使える。** 確認日 2026-08-14。

`adr/0003`「環境変数の区分」は、DB 接続文字列が「アプリが実行時に読む」と「リリースの自動処理が読む」の両方に現れることを挙げ、**同じ値で足りるかは着手時に確かめるとしていた。** アプリ側は Supavisor の transaction mode（6543）を前提としており、そこでは prepared statement が使えない（`adr/0005`）ため、適用側だけ session mode（5432）が要る可能性があった。

**要らなかった。** transaction mode の接続文字列そのままで、コミット済みの SQL が適用できた。

- リリースの 2 段目に渡す接続文字列は、**アプリに渡すものと同じ形でよい**（置き場所が違うだけ）
- session mode を別に用意する必要はない。**IPv6 でしか名前が引けない直接接続（5432）を GitHub Actions から使う問題も、これで発生しない**

### 秘密情報の置き場

`adr/0003`「環境変数の区分」の 3 種別のうち、**「リリースの自動処理が読む」を GitHub の秘密情報に置く。** どの値がこの種別かの一覧は `docs/operations.md` を正とする。

**アプリが実行時に使わない値を、ホスティング環境に置かない。** Discord の Bot Token がこれにあたる（署名検証は公開鍵で行うため、アプリは Bot Token を必要としない。`adr/0006`）。置いても使われず、露出面だけが増える。

### 手順の正

**この ADR は「何をどの順で走らせるか」と「なぜそうするか」だけを持つ。** コマンドの実体、手元での実行方法、診断の手順は `docs/operations.md` を正とする。

## 結果

- 良い点：
  - `adr/0006` が留意点に挙げた「デプロイしたのにコマンドが反映されない」が、構造的に起こらなくなる
  - 依存方向の検査が PR で必ず走るため、`adr/0004` の境界が実際に守られる状態になる
  - 未マージのコードが本番データに到達する経路が存在しない
- 留意点：
  - **PR の CI に Postgres の起動が入るため、待ち時間が伸びる。** 単体テストだけを手元で先に回す運用と組み合わせる
  - **Preview が無いため、マージ前にブラウザで確認する手段は手元の開発サーバーだけになる**
  - **前方のみのマイグレーションは、壊す変更を 2 リリースに割る規律を要求する。** 1 回で済ませたくなる場面が必ず来る
  - リリースが 4 段階に分かれるため、途中で失敗したときにどこまで進んだかを確かめる必要がある（`docs/operations.md`）
  - **走るのが PR と main の 2 経路だけになったため、「誰も見ていないところで失敗しているジョブ」が存在しない。** どちらの経路も人が結果を見る場面と結びついている

## 検討した代替案

- **Vercel の Git 連携に任せ、CI はテストだけ回す**：設定が最も少ない。ただしマイグレーションの適用とコマンド登録をデプロイの前後に置けず、`adr/0005`・`adr/0006` の要求を満たせない。
- **Preview 用に別の Supabase プロジェクトを立てる**：未マージのコードを実データから隔離したうえで Preview を残せる。ただし無料枠のプロジェクト数と休止ルールを管理する対象が 1 つ増え（`overview.md`「前提」）、マイグレーションの適用先も 2 つになる。レビュアーがいない以上、得るものが見合わない。
- **Preview で本番 DB を共有する**：設定が最も軽い。ただし未マージのコードが他人の金銭記録を書き換え得る。個人開発で気をつければ避けられる、という前提に立つことになる。
- **コマンド登録を手元のスクリプトで行い、リリース手順に明記する**：Bot Token を CI に置かずに済む。ただし `adr/0006` が「PoC で最も時間を溶かした落とし穴」と書いた登録忘れを、人の記憶で防ぐことになる。
- **コマンドの差分検査だけ CI で行い、適用は手動**：検知は自動、適用は人。検知できても直す操作を忘れれば同じ状態になるため、間に人を挟む利点が無い。
- **マイグレーションを手元から適用する**：本番 DB を書き換える操作を常に人の手で行える。ただし適用忘れのままデプロイが通ってしまい、本番でだけ動かない状態を作れる。
- **down マイグレーションを持つ**：戻せる。ただし実際に使う場面まで検証されないコードを持つことになり、いざ使ったときに正しく戻る保証がない。壊す変更を 2 リリースに割る方が確実。
- **E2E を本番デプロイ後に本番へ向けて回す**：実環境そのものを検証できる。ただし DB が 1 つしか無いため、テストが作った記録が実データに混ざる。
- **E2E も PR で回す**：壊れたものが main に入らない。ただし PR ごとに最も遅い検査を待つことになり、個人開発では手が止まる時間が増える。
