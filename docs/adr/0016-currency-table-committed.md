# ADR-0016: 通貨表を直接コミットし、ISO 4217 の改定に追随する仕組みを持たない

- ステータス: 採用 [確定] — **`adr/0013` を廃止（supersede）する**
- 関連: `docs/domain/money.md`, `docs/operations.md`, `adr/0004-layers-and-dependencies.md`, `adr/0008-layer-internals.md`, `adr/0010-testing.md`, `adr/0011-ci-and-release.md`, `adr/0013-currency-data.md`（廃止）, `adr/0014-logging.md`, `adr/0015-backup.md`

## コンテキスト

`domain/money.md` は、通貨の一覧と最小単位の桁数について**ドメインとして要求すること**を定めている（定義の正は `domain/money.md`「扱う通貨」「実現方式」）。この ADR はその要求を、どの実現方式で満たすかだけを決める。

`adr/0013` はこれを **「公表データから生成器で表を作り、週次の定期実行で差分を PR にする」** で満たそうとした。その決定を撤回する。

### なぜ撤回するか

**抱える仕組みの量が、実際に得られるものに見合わない。**

- **生成器はアプリ本体と独立に保守する対象になる。** `adr/0013`「取得元の形」が挙げたとおり、生成器は「取得 → 通貨コードで畳む → コードを持たないエントリを落とす → 桁数を持たないエントリを扱う → 廃止済みの一覧と突き合わせて印を立てる → リテラルとして出力 → 既存との差分を終了コードで返す」まで書く必要がある。公表データの形式が変われば、この全部が壊れる
- **ISO 4217 の改定は数年に一度である。** 数年に一度の出来事のために、常時保守する仕組みを持ち続けることになる
- **「自動で追随している」と言えるのは PR が出るところまでである。** 定期実行もそこから出た PR も通知されない（`adr/0014` のとおり監視サービスを持たない）。マージは結局、人が GitHub を見に行って気づいたときに行う。**追随の最後の一歩は、どの案でも人の記憶に残る**

`adr/0015` が既に同じ形の判断をしている。**失敗に気づく手段を持てない仕組みは、「あるつもりで壊れている」状態を作る。** 無いと分かっている状態のほうが扱いやすい。

### 撤回によって満たせなくなる要求

`domain/money.md`「実現方式」は **「改定への追随が人の記憶に依存しないこと」** を `[確定]` の要求として挙げていた。**この決定はそれを満たさない。**

ADR だけを差し替えるとドメインの要求に反する ADR が残るため、**同じ PR で `domain/money.md` の側からこの 1 項目を落とした。** 残る 4 つの要求（ISO 4217 に従う / 桁数を独自に決めない / 同じ入力から同じ結果 / 一度扱った通貨と桁数が削除で失われない）は、この決定でもそのまま満たされる。

## 決定

### 表を直接コミットする

- 置き場は `src/domain/money/`（`adr/0008` のツリー）。**プレーンな TypeScript のリテラルであり、外部パッケージも `node:*` も参照しない**。ドメイン層の依存はゼロのまま（`adr/0004` の機械検査にそのまま通る）
- **実行時にもビルド時にも取得しない。** 手元・CI・本番のどこで動かしても同じ表を読む
- 表に無い通貨コードは受け付けない。**「知らない通貨は最小単位 2 桁とみなす」といった既定値を置かない**
- **表は人が直接編集する。** 生成器を持たないため、直す対象は表そのものになる（`adr/0013`「生成物を手で編集しない」は、ここで反転する）
- ファイルの先頭に、**取得元と、書き写した時点の公表日**を書く。値の由来がレビューの争点にならないようにする

表に何を入れるか（最小単位の桁数が ISO 4217 で定められていないコードを扱わないこと）は**ドメインの決定であり、正は `domain/money.md`「扱う通貨」**。この ADR はそれを定義しない。

### 生成器も定期実行も持たない

- `scripts/` に生成器を置かない
- `adr/0011` の定期実行の枠を使わない。**この決定により、`adr/0011` から定期実行そのものが無くなる**（枠に入っていたのは通貨表の生成 1 件だけだったため）

### 改定に追随する仕組みを持たない [確定]

**改定に気づく契機を持たない。** 必要になったときに人が表を直す。

改定の種類によって気づき方が非対称になる。**これがこの決定の代償であり、隠さずここに書く。**

| 改定 | 表を直すまでに起きること | 深刻さ |
|---|---|---|
| 通貨が**新設**される | 表に無いコードは受け付けないため、**使おうとした時点で弾かれる。気づける**（が、表を直すまでその通貨は使えない） | 気づける |
| 通貨が **ISO 4217 から削除**される | 何も壊れない。行は残り、桁数も残るため、記録の解釈は変わらない（`domain/money.md`「廃止された通貨」が要求するとおり）。**廃止の印が立つまで、その通貨が入力候補に現れ続ける**だけ | 選べてしまうだけ |
| 既存の通貨の**桁数が変わる** | **弾かれない。** 古い桁数のまま解釈が続き、金額がずれても誰も気づかない | **気づけない** |

**3 行目だけが緩和策を持たない。** 1 行目は弾かれることで気づき、2 行目は記録の解釈を壊さない。桁数の改定だけが、静かに間違った金額を作る。

`adr/0013` では、削除に対して「行を消さず廃止の印を立てる」を生成器が担っていた。**この決定では、印を立てるのは人になる。** 印が立っていない削除済み通貨は入力候補に残るが、`domain/money.md`「廃止された通貨」が守ろうとしている「過去の記録が読めなくなる」「桁数の解釈が変わる」はどちらも起きない。

### 表そのものの妥当性を単体テストで固定する

人が書く以上、書き写しの誤りが入り得る。**表の形が壊れていないことだけは機械で確かめる**（`adr/0010` の単体テスト。外部依存を持たない）。

- 通貨コードが重複しない
- 桁数が 0 以上の整数である（値が無い行が存在しない）

**「値が ISO 4217 と一致すること」はテストできない。** 一致を確かめるには公表データを取りに行くことになり、この決定が持たないと決めたものになる。テストが守るのは形だけであり、値の正しさはレビューが担保する。

### この決定を見直す契機 [確定]

**次のいずれかに達したら、この決定は成立しなくなる。**

| 契機 | 見直しの方向 |
|---|---|
| 桁数の改定が実際に起き、**それに気づけないまま金額がずれた** | 照合だけを定期実行に戻す（下記「検討した代替案」） |
| 表を直す作業が繰り返し発生し、改定が数年に一度と言えなくなる | 同上 |

**契機を検知する仕組みは持たない。** `adr/0014` が監視サービスも通知も持たないと決めており、ここだけ例外を作らない。気づくのは人であり、この節はそのための覚書である。

### 手順の正

**この ADR は「何をどうするか」と「なぜそうするか」だけを持つ。** 表を直す実際の手順は `docs/operations.md`「通貨表の更新」を正とする。

## 結果

- 良い点：
  - **抱える仕組みがゼロになる。** 生成器も定期実行も無く、そのどちらかが失敗している状態も存在しない
  - ドメイン層が依存をまったく持たないまま、金額の解釈を完結できる（`adr/0004` の機械検査にそのまま通る）
  - Web と Discord、手元と本番で結果が一致する。実行環境のバージョン差で通貨の一覧や桁数が変わる経路が存在しない。テストも決定的になる
  - **「実行時に取得しない」が、取得の経路そのものを持たない形で成立する。** ネットワークに触れるコードがリポジトリから消える
  - `adr/0011` から定期実行が無くなり、CI で走るのが PR と main の 2 経路だけになる
- 留意点：
  - **桁数の改定に気づく手段が無い。緩和策は無い。** 上の表の 3 行目がこの決定の代償であり、その全体である
  - **新設された通貨は、表を直すまで使えない。** エラーとして出るため気づけるが、その場では回避できない
  - 削除された通貨は、廃止の印を立てるまで入力候補に残る
  - **表を最初に 1 回、人が書き写す。** 数百行になり、その値の正しさはレビューでしか担保されない（形だけは単体テストで固定する。上記）
  - **この決定は「改定が数年に一度だから成立している」。** 前提が変わっても自動では警告が出ない（上記「この決定を見直す契機」）

## 検討した代替案

- **照合だけを定期実行に残す**：公表データと表を突き合わせ、差分があれば報告するだけの検査を持つ。表を直すのは人。生成器（畳み込み・廃止の印・出力の組み立て）を書かずに済み、**ドメインの要求「追随が人の記憶に依存しないこと」を撤回せずに済んだ**。ただし外部の公表データを定期的に取りに行く経路は残り、「取得しない」が取得先を持たない形では成立しなくなる。加えて差分は通知されない（`adr/0014`）ため、**結局 GitHub を見に行った人が気づく**ことになり、仕組みを 1 つ抱えた対価が「気づきの契機が人から外れる」ところまで届かない。**上記「この決定を見直す契機」に達した時点で、これが第一の選択肢になる。**
- **生成器と週次の定期実行を持つ（`adr/0013` の決定）**：何も撤回せずに済み、ドメインの要求もそのまま満たされる。不採用の理由は上記「なぜ撤回するか」がすべてである。**`adr/0013` は廃止するが削除しない。** 生成器を書く場合に必要な事情（取得元の形・エントリの重複・桁数を持たないコード）は、そちらに残っている
- **公表データを手で書き写す（`adr/0013` の初版であり、同日に撤回された）**：この決定は、実質的にその判断に戻るものである。**当時の撤回理由「追随の契機が人の記憶になる」は、今も正しい。** 変わったのは理由の側ではなく、その代償を**明示して受け入れるかどうか**である。今回は上記「改定に追随する仕組みを持たない」の表として代償を書き出したうえで受け入れた
- **`Intl` から得る / 通貨データのライブラリを入れる / DB のテーブルとして持つ / 使う通貨だけを列挙する**：いずれも「表を直接持つかどうか」とは独立に不採用であり、評価は `adr/0013`「検討した代替案」がそのまま成立する。**ここには再掲しない**（`RULES.md` §7）
