# ADR-0006: Discord には HTTP Interactions で接続し、常駐 Bot を持たない

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/features.md`, `docs/domain/settlement.md`, `docs/domain/group.md`, `adr/0003-tech-stack.md`, `adr/0004-layers-and-dependencies.md`, `adr/0007-external-account-linking.md`, `adr/0008-layer-internals.md`

## コンテキスト

`overview.md` は「Discord アプリとしても同じ機能を提供する」「2 つの提供形態で機能に差を設けない」を確定させている。その接続方式と、Discord 側の制約に起因する実装要件をここで決める。

Discord への接続には 2 通りある。常駐プロセスが WebSocket で Gateway に接続し続ける方式と、Discord からの HTTP リクエストを受ける方式（HTTP Interactions）である。PoC では後者を実装し、署名検証・スラッシュコマンド・メッセージコンポーネントまで動作を確認した。

## 決定

### 接続方式

**HTTP Interactions を使う。常駐 Bot を持たない。** サーバーレス関数 1 本で完結し、スケール・死活監視・再起動の考慮が要らない（`adr/0003`）。

### エンドポイントの要件

- **Ed25519 署名検証が認証そのもの。** これが通ることで「Discord から来たこと」と、リクエストに含まれるユーザー ID が保証される。署名不正時は **401 を返す**（Discord がエンドポイント登録時に要求する）
- **3 秒以内に応答する。** これを満たすため、**すべての Interaction で一律に deferred response を返し、本文は follow-up で送る**。サーバーレスのコールドスタートと Supavisor 経由の接続確立が 3 秒に収まる保証はなく、収まらなかったときの失敗が「無反応」という最も分かりにくい形で出るため。応答が速い処理でも分岐を持たない
  - deferred response の時点で可視性が決まるため、**そのコマンドの可視性は defer の時点で確定させる**（後述「返信の可視性」）
  - **deferred を返したあとに本処理を続ける手段が要る。** 応答を返した時点で実行が終わる形では follow-up を送れない。実現方式は `adr/0003` を正とする
- 署名検証に標準の暗号 API を使うため、**Node.js ランタイムを明示指定する**（Edge ランタイム不可）
- **Interaction のペイロードの型は既製の型定義パッケージを使い、自前で書かない。** 型のみでランタイム依存を持たないものに限る（`adr/0008`）

### 扱う Interaction 種別

`PING` / `APPLICATION_COMMAND` / `MESSAGE_COMPONENT` / `APPLICATION_COMMAND_AUTOCOMPLETE` / `MODAL_SUBMIT` の 5 種を扱う。

**モーダルはメッセージとは別種の応答である。** 返信を表す型は、メッセージとモーダルの両方を表現できる必要がある。

### コマンド登録の運用

**スラッシュコマンドの登録はデプロイと別作業である。** コマンド定義はソースコード上に存在するだけでは何も起きず、Discord の API へ登録して初めてクライアントに表示される。PoC で最も時間を溶かした落とし穴。

- **コマンドの宣言（名前・説明・引数・可視性）をソース上の 1 か所に置き、それを唯一の正とする。** 登録スクリプトも、受信時の分岐も、可視性の決定も同じ宣言を読む。定義との差分を出す診断もそこから作れる（置き場は `adr/0008`）
- ギルド単位の登録は**即時反映**、グローバル登録は**最大 1 時間**かかる
- インストール URL には `scope` を明示する。省略すると必要な権限が付かないままインストールされ得る
- **CI/CD に登録ステップを組み込むか、リリース手順に明記する**
- **コマンド登録状況・定義との差分・エンドポイント疎通を確認する診断手段を用意する。** 設定が正しいかを自力で確かめる手段が無いと、原因不明の状態に陥る

### 対象 Group の解決

`domain/group.md` の「場」に、**Discord のチャンネルを対応させる。** Interaction に含まれるチャンネルの識別子から、対応する Group を引く。

- 解決はアダプタ層で行い、**ユースケースには Group を渡す**（`adr/0004`）。ユースケースがチャンネルを知ることはない
- 対応の参照・記録はユースケース層が定義するポート越しに行う。ポートが受け取るのは「サービスの種別」と「そのサービス上の場の識別子」であり、Discord 固有の型ではない。Slack を足すときはサービスの種別が増えるだけで、ポートは変わらない
- 対応づけられていないチャンネルからの操作には案内を返す（振る舞いは `domain/group.md`「対応づけられていない場から操作したとき」を正とする）。可視性は実行者のみ

チャンネルを場としたのは、mmkn のターゲットが「その場限りのイベント」（`overview.md`）であり、イベントごとにチャンネルを立てる運用が Discord では自然なため。ギルド単位にすると、既存のサーバーで 2 回目のイベントを扱えない。

### 表示

**Embed（色帯・タイトル・フィールド）を使う。** プレーンテキストにしない。

組み立ては Presenter に閉じる。他のクライアントは同じデータを別形式で描画する（`adr/0004`）。

### 返信の可視性

Discord の返信は既定で全員に見えるが、`ephemeral` を立てると実行者だけに見える。

**可視性は、defer を開始する単位（スラッシュコマンド／メッセージ部品）ごとに宣言として持たせ、defer の時点でそれを使う。**

deferred response の可視性は**後から変えられない**。一律 deferred（前述）を採る以上、1 つの Interaction の中で返信ごとに可視性を選ぶことはできない。

> **旧記述の撤回。** 初版はここを「エントリポイントで一律に決めず、返信ごとに指定できる構造にする」としていたが、上の制約により同 ADR の「そのコマンドの可視性は defer の時点で確定させる」と両立しない。撤回し、上の決定に差し替える。

mmkn での使い分け:

| 返信の種別 | 可視性 |
|---|---|
| 支払い・送金の登録結果 | 公開 |
| 差額・清算案 | 公開 |
| 入力途中のやり取り | 実行者のみ |
| 場と Group の対応づけ・解除の結果 | 実行者のみ |

**この使い分けは、宣言の単位を分けることで実現する。** 選択を提示するコマンドと、選択を受けて結果を返す部品は別の Interaction であり、それぞれが自分の defer を持つ。したがって「入力途中は実行者のみ、確定した結果は公開」は成立する。

**エラー・操作案内・未連携の案内（`adr/0007`）は、それが起きた単位の可視性で返る。** 公開として宣言した単位で失敗すれば、案内も公開になる。実行者だけに返すことはできない。

差額と清算案を公開にするのは、mmkn がオーナー・管理者を持たず全 Member を同等に扱う（`features.md`）ことと、グループ内のお金の動きは全員が把握している状態を目指す（`overview.md`）ことによる。

### メッセージコンポーネント（ボタン・セレクト）

**返信に添えたボタンから、ユースケースを実行できる。** 押下は同じ署名付きエンドポイントに届き、Interaction には押下者のユーザー ID が含まれる。`UPDATE_MESSAGE` で、新規投稿せず元のメッセージを更新できる。

`domain/settlement.md`「清算案の送金を記録する」を、清算案の返信に添えたボタンで実現する。

設計上の要件:

- **ボタンは全員に見えて全員が押せる。押下者の検査は必須。** Discord は押した人の ID を渡すが、権限判定はこちら側の責務
- **`custom_id` は 100 文字が上限。操作対象の情報を持たせすぎない。** 清算案の「送金した」ボタンでは、**送り手を押下者に固定し、受け手と通貨だけを載せる**。結果として他人の操作を代行する経路が構造的に消える
  - なお `domain/record.md` は Transfer の送り手と登録者を別のものとして扱っており、送り手が登録者に一致することを要求していない。**送り手を押下者に固定するのはこのボタン導線だけの制約**であり、ドメインの制限ではない
- **メッセージに埋めた値を信じない。** Discord のメッセージは消えないため、古いボタンに書かれた金額は実行時点で誤っている可能性がある。`domain/settlement.md` が「登録時点で導出し直す」と定めているのはこのため。ユースケースは金額を引数に取らない
- **メッセージ差し替えでは、省いたフィールドは変更されない。** 操作が不要になった場合は、部品を空で明示的に送らないと古いボタンが残り、再実行できてしまう

### ユーザー選択 UI

複数の Member を選ばせる操作（Payment の負担者など）では、**セレクトメニューの複数選択を使う。**

前提として、**スラッシュコマンドの引数にチェックボックスは存在しない。** 引数で使えるのは STRING / INTEGER / NUMBER / BOOLEAN / USER / CHANNEL / ROLE / MENTIONABLE / ATTACHMENT の 9 種で、BOOLEAN が 2 択として最も近いにとどまる。複数選択はメッセージコンポーネントのセレクトメニューで実現し、`min_values` / `max_values` で選択数を制御する。

**mmkn では `STRING_SELECT` を自前で構築する。** `USER_SELECT` は Discord のサーバーメンバーを候補に出すが、**Discord のサーバーメンバーと mmkn の Member は別物**である（`domain/group.md`）。選ばせるのは mmkn の Member であり、Discord のメンバーではない。

- 選択結果は **ID の配列**で届く。名前は Interaction に同梱される `resolved` から引ける（別途 API を呼ぶ必要はない）
- `default: true` を指定した項目は初期状態で選択済みにできる。既定値の提示に使う
- **中間状態を持たない設計にする。** セレクトメニューは選び終えて閉じた時点で、選択値をすべて含んだ Interaction が飛ぶ。金額や内容はスラッシュコマンドの引数で受け、選択はその返信のセレクト 1 回で確定させることで、保存すべき状態が発生しない
  - HTTP Interactions は状態を持たず、サーバーレスではプロセス内メモリにも置けない（`adr/0003`）。中間状態を持つと実質的にセッションを自前で持つことになり、期限切れの掃除まで抱える
  - **確定用のボタンをセレクトと別に置かない。** 別に置くと選択値をボタンの押下まで運ぶ必要が生じ、`custom_id` の 100 文字に収まらないか、メッセージに埋めた値を信じることになる（下の「メッセージに埋めた値を信じない」と衝突する）

### 構造上の制約

Discord は上限違反を**メッセージ単位で拒否**し、原因が分かりにくい。**表示を組み立てる側で切り詰め、テストで固定する。**

- 部品は必ず ActionRow に入れる。**1 メッセージ 5 行**、1 行にボタン 5 個 / セレクト 1 個
- Embed は**フィールド 25 個**、フィールド値 1024 文字、説明 4096 文字
- `custom_id` は 100 文字、オートコンプリートの候補は 25 件
- `TEXT_INPUT` はモーダル専用。通常のメッセージには置けない
- Link ボタンは `url` を持ち `custom_id` を持たない（押しても Interaction は飛ばない）

## 結果

- 良い点：
  - 常駐プロセスが無く、Vercel 上のエンドポイント 1 本で完結する
  - 署名検証が認証を兼ねるため、Discord 側の入口に独自の認証機構を持たなくてよい
  - ボタンから直接ユースケースを実行できるため、`overview.md` のコアループ（清算案 → 送金 → 記録）が Discord 内で閉じる
- 留意点：
  - **リアクション（スタンプ）を操作のトリガーにできない。** 後述
  - コマンド登録がデプロイと独立しているため、**デプロイしたのに反映されない**状態が構造的に起こり得る
  - **一律 deferred のため、どのコマンドも一瞬「考え中」を経由する。** 応答が速い処理でも即答には見えない。無反応で失敗するよりは良い、という判断
  - **公開として宣言した単位で失敗すると、エラーや未連携の案内も全員に見える。** 一律 deferred を保ったまま避ける方法は無い。目立って困る場面が出たら、下の代替案（常に実行者のみで defer する案）を再検討する
  - 中間状態を持たないため、**セレクト 1 回で確定できない操作は組めない。** 必要になった時点でこの決定を見直す（メッセージ自身を状態にする案・保存する案は下の代替案にある）

## 検討した代替案

- **Gateway に常駐接続する Bot（別サーバー）**：リアクションなど Gateway イベント全般を扱えるようになる。ただし常駐サーバーが必要になり、スケール・死活監視・再起動を個人開発で抱えることになる。`adr/0003` の「常駐プロセスを持たない」前提そのものを覆すため採らない。
- **リアクション（スタンプ）を操作のトリガーにする**：直感的だが、**リアクションは Interaction ではなく Gateway イベント**であり、常駐 WebSocket 接続を張ったプロセスにしか届かない。HTTP Interactions のエンドポイントには飛んでこないため、採用した構成と両立しない。ボタンで代替する。
- **プレーンテキストで返信する**：実装が軽い。ただし差額・清算案は「誰が・いくら・どの通貨」の三つ組が並ぶ表であり、テキストでは可読性が落ちる。Presenter に閉じている以上、Embed にするコストは 1 か所に収まる。
- **返信ごとに可視性を指定する**（初版の記述）：同じコマンドでも成功と失敗で可視性を変えられる。ただし deferred response の可視性は後から変えられないため、一律 deferred と両立しない。撤回した。
- **常に実行者のみで defer し、公開したい結果だけをチャンネルへ別メッセージとして投稿する**：エラーと案内を必ず実行者だけに返せる。ただし 1 つの操作で送信が 2 回になり、実行者の手元には「考え中」から変化した実行者専用の返信が、チャンネルには公開の投稿が、それぞれ残る。表示が二重になる分かりにくさに見合わない。
- **常に公開で defer する**：最も単純。ただし入力途中のやり取りや未連携の案内まで全員に見えることになり、上の使い分けが成立しない。
- **`USER_SELECT` で Discord のサーバーメンバーから選ばせる**：候補を Discord が用意してくれるため実装が軽い。ただし選ばれるのは Discord のユーザーであって mmkn の Member ではなく、未参加・未連携の人を選べてしまう。
- **ギルド（サーバー）を場とする**：対応が 1 サーバー 1 グループになり最も単純。ただしイベントごとに Discord サーバーを作る運用を強いる。既存のサークルのサーバーに mmkn を入れると、そのサーバーで一生に 1 イベントしか扱えない。ターゲット（`overview.md`）と合わない。
- **場という概念を持たず、毎回コマンド引数で Group を指定させる**：紐づけの仕組みが要らず、DM でも使える。ただし記録のたびに対象を選ぶ手間がかかり、返信を公開する意味も薄れる。なお `adr/0004` により、後からこの入口を足してもユースケースは変わらない。
- **原則は即時応答とし、重い処理だけ deferred にする**：応答が 1 段階で済み体感が速い。ただし「どれが重いか」をコールドスタート込みで見極める必要があり、外したときの失敗が無反応になる。分岐を持つ価値がない。
- **メッセージ自身を中間状態にする（`UPDATE_MESSAGE` で選択状態を描き直す）**：サーバーに状態を置かず多段階にできる。ただし「メッセージに埋めた値を信じない」と正面から衝突し、古いメッセージから実行できてしまう。
- **中間状態を期限付きで DB に保存する**：どんな多段階フローでも組める。ただし実質的にセッションを自前で持つことになり、掃除の仕組みまで必要になる。セレクト 1 回で足りるうちは持たない。
