# ADR-0006: Discord には HTTP Interactions で接続し、常駐 Bot を持たない

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/features.md`, `docs/domain/settlement.md`, `docs/domain/group.md`, `docs/domain/record.md`, `adr/0002-invite-code.md`, `adr/0003-tech-stack.md`, `adr/0004-layers-and-dependencies.md`, `adr/0007-external-account-linking.md`, `adr/0008-layer-internals.md`, `adr/0009-web-ui.md`, `adr/0010-testing.md`, `adr/0011-ci-and-release.md`

## コンテキスト

`overview.md` は「Discord アプリとしても同じ機能を提供する」「2 つの提供形態で機能に差を設けない」を確定させている。その接続方式と、Discord 側の制約に起因する実装要件をここで決める。

Discord への接続には 2 通りある。常駐プロセスが WebSocket で Gateway に接続し続ける方式と、Discord からの HTTP リクエストを受ける方式（HTTP Interactions）である。PoC では後者を実装し、署名検証・スラッシュコマンド・メッセージコンポーネントまで動作を確認した。

## 決定

### 接続方式

**HTTP Interactions を使う。常駐 Bot を持たない。** サーバーレス関数 1 本で完結し、スケール・死活監視・再起動の考慮が要らない（`adr/0003`）。

### エンドポイントの要件

- **Ed25519 署名検証が認証そのもの。** これが通ることで「Discord から来たこと」と、リクエストに含まれるユーザー ID が保証される。署名不正時は **401 を返す**（Discord がエンドポイント登録時に要求する）
- **3 秒以内に応答する。** これを満たすため、**メッセージで応答する Interaction は一律に deferred response を返し、本文は follow-up で送る**。サーバーレスのコールドスタートと Supavisor 経由の接続確立が 3 秒に収まる保証はなく、収まらなかったときの失敗が「無反応」という最も分かりにくい形で出るため。応答が速い処理でも分岐を持たない
  - deferred response の時点で可視性が決まるため、**そのコマンドの可視性は defer の時点で確定させる**（後述「返信の可視性」）
  - **deferred を返したあとに本処理を続ける手段が要る。** 応答を返した時点で実行が終わる形では follow-up を送れない。実現方式は `adr/0003` を正とする
- 署名検証に標準の暗号 API を使うため、**Node.js ランタイムを明示指定する**（Edge ランタイム不可）
- **Interaction のペイロードの型は既製の型定義パッケージを使い、自前で書かない。** 型のみでランタイム依存を持たないものに限る（`adr/0008`）

### 扱う Interaction 種別と、defer の適用範囲

`PING` / `APPLICATION_COMMAND` / `MESSAGE_COMPONENT` / `APPLICATION_COMMAND_AUTOCOMPLETE` / `MODAL_SUBMIT` の 5 種を扱う。

**一律 deferred は「メッセージで応答するもの」に限る。** Discord の仕様上、defer できない応答があるため、無条件の「すべての Interaction で defer」は成立しない。

| 種別 | 応答 | defer |
|---|---|---|
| `PING` | `PONG` のみ | **できない**。即座に返す |
| `APPLICATION_COMMAND` | メッセージ、またはモーダルを開く | メッセージならする。モーダルは**できない** |
| `MESSAGE_COMPONENT` | メッセージ、またはモーダルを開く | 同上 |
| `APPLICATION_COMMAND_AUTOCOMPLETE` | 候補リストのみ | **できない**（deferred 形が存在しない） |
| `MODAL_SUBMIT` | メッセージ | する |

- **オートコンプリートは 3 秒以内に候補を返しきる必要がある。** したがって、**候補の生成に永続化への問い合わせを含む設計にしない。** 必要になったら、その入力はオートコンプリートではなくセレクトメニュー（後述）で受ける

### モーダル

**モーダルを使う。** 長い自由入力や複数項目の入力をスラッシュコマンドの引数に並べる形は、実際に打つ側の負担が大きい。`MODAL_SUBMIT` を扱う種別に含める。

Discord の仕様上、**モーダルを開く応答は `APPLICATION_COMMAND` か `MESSAGE_COMPONENT` への初回応答としてしか送れない。** defer したあとには送れず、`MODAL_SUBMIT` への応答としても送れない（モーダルからモーダルは開けない）。一方、**`MODAL_SUBMIT` はメッセージで応答するため defer できる**。したがって重い処理はすべて submit 側に置き、3 秒の枠に入るのは「モーダルの定義を返すこと」だけになる。

守る規則は 2 つ。

- **モーダルを開く応答は、永続化に問い合わせずに組み立てられるものに限る。** オートコンプリートに課した制約（上記）と同じもので、理由も同じ。3 秒の枠に DB への往復を入れない。初期値を埋める場合、値は Interaction のペイロードに同梱されているものか、宣言に書いた静的な値から取る
- **1 つの操作の入力を 1 つのモーダルで完結させる。モーダルとセレクトを直列に繋がない。** 直列にすると前段の入力値を次の Interaction まで運ぶ必要が生じ、`custom_id` の 100 文字に収まらないか、メッセージに埋めた値を信じることになる（後述「中間状態を持たない設計」と同じ理由）

**モーダルの初期値に、メッセージや `custom_id` に埋まっていた値を使うのは許す。** 後述の「メッセージに埋めた値を信じない」が禁じているのは、埋まっていた値をそのまま**書き込みの入力にする**ことである。モーダルの初期値は操作者が見て直せるものであり、実際に書き込まれるのはモーダルから返ってきた値のほうになる。古い値が初期表示されても、`domain/record.md`「同じ記録に同時に手が入ったとき」が定める失敗が最後の砦として効く（実現方式は `adr/0005`。版は `custom_id` に載せる。記録の ID と合わせて 100 文字に収まる）。

> **旧記述の撤回。** 初版はここを「モーダルは使わない」とし、その理由を「そのコマンドだけ 3 秒以内に即答する例外を作ることになり、一律 deferred でわざわざ消したはずのコールドスタートのリスクを戻すことになる」としていた。**この理由は誤りである。** deferred response 自体も 3 秒以内に返す必要があり、一律 deferred がコールドスタートを 3 秒の枠から外したことは一度もない。外したのは応答の**中身を作る処理**（DB への往復）だけである。モーダルを開く応答は中身を作る処理を持たないため、遅延の性質は deferred response と変わらない。撤回し、上の決定に差し替える。

### コマンド登録の運用

**スラッシュコマンドの登録はデプロイと別作業である。** コマンド定義はソースコード上に存在するだけでは何も起きず、Discord の API へ登録して初めてクライアントに表示される。PoC で最も時間を溶かした落とし穴。

- **コマンドの宣言（名前・説明・引数・可視性）をソース上の 1 か所に置き、それを唯一の正とする。** 登録スクリプトも、受信時の分岐も、可視性の決定も同じ宣言を読む。定義との差分を出す診断もそこから作れる（置き場は `adr/0008`）
  - **メッセージ部品とモーダルの宣言（`custom_id` と可視性）も同じ場所に置く。** こちらは Discord への登録を伴わないが、可視性の宣言単位（後述「返信の可視性」）であることは同じであり、宣言を 2 か所に割らない
- ギルド単位の登録は**即時反映**、グローバル登録は**最大 1 時間**かかる
- インストール URL には `scope` を明示する。省略すると必要な権限が付かないままインストールされ得る
- **登録はリリースの自動処理として走らせる。** 人が思い出して実行する手順にしない。走らせ方は `adr/0011-ci-and-release.md` を正とする
- **コマンド登録状況・定義との差分・エンドポイント疎通を確認する診断手段を用意する。** 設定が正しいかを自力で確かめる手段が無いと、原因不明の状態に陥る（手順は `docs/operations.md`）

### 対象 Group の解決

`domain/group.md` の「場」に、**Discord のチャンネルを対応させる。** Interaction に含まれるチャンネルの識別子から、対応する Group を引く。

- 解決はアダプタ層で行い、**ユースケースには Group を渡す**（`adr/0004`）。ユースケースがチャンネルを知ることはない
- 対応の参照・記録はユースケース層が定義するポート越しに行う。ポートが受け取るのは「サービスの種別」と「そのサービス上の場の識別子」であり、Discord 固有の型ではない。Slack を足すときはサービスの種別が増えるだけで、ポートは変わらない
- 対応づけられていないチャンネルからの操作には案内を返す（振る舞いは `domain/group.md`「対応づけられていない場から操作したとき」を正とする）。可視性は実行者のみ

チャンネルを場としたのは、mmkn のターゲットが「その場限りのイベント」（`overview.md`）であり、イベントごとにチャンネルを立てる運用が Discord では自然なため。ギルド単位にすると、既存のサーバーで 2 回目のイベントを扱えない。

### 表示

**Embed（色帯・タイトル・フィールド）を使う。** プレーンテキストにしない。

組み立ては Presenter に閉じる。他のクライアントは同じデータを別形式で描画する（`adr/0004`）。

### 返信の可視性

Discord の返信は既定で全員に見えるが、`ephemeral` を立てると実行者だけに見える。

**可視性は、defer を開始する単位（スラッシュコマンド／メッセージ部品／モーダル）ごとに宣言として持たせ、defer の時点でそれを使う。**

deferred response の可視性は**後から変えられない**。一律 deferred（前述）を採る以上、1 つの Interaction の中で返信ごとに可視性を選ぶことはできない。

**モーダルそのものは可視性を持たない。** モーダルは開いた本人にしか見えないため、宣言が要るのは `MODAL_SUBMIT` の deferred response の側である。これをモーダルの宣言に持たせる。

> **旧記述の撤回。** 初版はここを「エントリポイントで一律に決めず、返信ごとに指定できる構造にする」としていたが、上の制約により同 ADR の「そのコマンドの可視性は defer の時点で確定させる」と両立しない。撤回し、上の決定に差し替える。

mmkn での使い分け:

| 返信の種別 | 可視性 |
|---|---|
| 支払い・送金の登録結果 | 公開 |
| 収支・清算案 | 公開 |
| 入力途中のやり取り | 実行者のみ |
| 場と Group の対応づけ・解除の結果 | 実行者のみ |
| グループの作成結果 | 実行者のみ [確定] |

**グループの作成結果を実行者のみにするのは、そこに参加リンクが含まれるためである** [確定]。参加コードは知っていれば参加できる鍵そのものであり（`adr/0002`）、**誰に渡すかは作成者が決める。** チャンネルに公開すると、その場にいる全員に渡したことになる。

**この使い分けは、宣言の単位を分けることで実現する。** 選択を提示するコマンドと、選択を受けて結果を返す部品は別の Interaction であり、それぞれが自分の defer を持つ。したがって「入力途中は実行者のみ、確定した結果は公開」は成立する。

**エラー・操作案内・アカウントを持たない人への案内（`domain/group.md`）は、それが起きた単位の可視性で返る。** 公開として宣言した単位で失敗すれば、案内も公開になる。実行者だけに返すことはできない。

収支と清算案を公開にするのは、mmkn がオーナー・管理者を持たず全 Member を同等に扱う（`features.md`）ことと、グループ内のお金の動きは全員が把握している状態を目指す（`overview.md`）ことによる。

### メッセージコンポーネント（ボタン・セレクト）

**返信に添えたボタンから、ユースケースを実行できる。** 押下は同じ署名付きエンドポイントに届き、Interaction には押下者のユーザー ID が含まれる。`UPDATE_MESSAGE` で、新規投稿せず元のメッセージを更新できる。

`domain/settlement.md`「清算案の送金を記録する」を、清算案の返信に添えたボタンで実現する。

設計上の要件:

- **ボタンは全員に見えて全員が押せる。押下者の検査は必須。** Discord は押した人の ID を渡すが、権限判定はこちら側の責務
- **`custom_id` は 100 文字が上限。操作対象の情報を持たせすぎない。** 清算案の「送金した」ボタンでは、**送り手を押下者に固定し、受け手と通貨だけを載せる**
  - なお `domain/record.md` は Transfer の送り手と登録者を別のものとして扱っており、送り手が登録者に一致することを要求していない。**送り手を押下者に固定するのはこのボタン導線だけの制約**であり、ドメインの制限ではない
  - **これは「機能の差」にはあたらない**（`overview.md`）。このボタンは `domain/settlement.md`「清算案の送金を記録する」への**ショートカット**であり、呼ぶユースケースは他のクライアントと同じ、できあがる Transfer も同じである。押下者以外を送り手とする登録は、Discord にも用意する通常の送金の記録（`features.md` #6）でそのまま行える。**ショートカットで届かない範囲が、通常の導線で必ず届く**ことをもって差が無いとする
- **メッセージに埋めた値を信じない。** Discord のメッセージは消えないため、古いボタンに書かれた金額は実行時点で誤っている可能性がある。`domain/settlement.md` が「登録時点で導出し直す」と定めているのはこのため。ユースケースは金額を引数に取らない
- **メッセージ差し替えでは、省いたフィールドは変更されない。** 操作が不要になった場合は、部品を空で明示的に送らないと古いボタンが残り、再実行できてしまう
- **押した時点の清算案にその送金が無かった場合は、`UPDATE_MESSAGE` で最新の清算案に描き直す。** `domain/settlement.md` が「登録されず、清算案が変わったことが操作者に伝わる」までを定めており、その伝え方をここで決める。案内文を出すだけにしないのは、古いボタンがそのまま残って何度でも同じ失敗を踏めるため（上記の「省いたフィールドは変更されない」がそのまま効く）
  - **登録できた場合も同じように描き直す** [確定]。清算案が変わるのはどちらの場合も同じであり、送るお金が無くなればボタンも空になる。**結果によって描き直すかどうかを分けない**
  - 一律 deferred と両立させるため、実際に使うのは**メッセージを差し替える形の deferred**（`DEFERRED_UPDATE_MESSAGE`）である [確定]。これは**それ自身の可視性を持たない**（差し替える先が既にあるメッセージであるため）。可視性の宣言が要るのは新しいメッセージを送る単位だけになる
- **押下者を Member として解決できなかったときは、元のメッセージに触れず、押下者だけに返す** [確定]。清算案の返信は公開であり、Member でない人が押したことで全員の見ている清算案がエラーに差し替わると、**押した人以外にとっては情報が消えたことになる。** メッセージを差し替える形の deferred は、差し替えの代わりに実行者のみの別メッセージを足すことができ、これはその 1 用途に限る（新しいメッセージを送る単位の可視性を後から変えるものではない）

### ユーザー選択 UI

複数の Member を選ばせる操作（Payment の負担者など）では、**セレクトメニューの複数選択を使う。**

前提として、**スラッシュコマンドの引数にチェックボックスは存在しない。** 引数で使えるのは STRING / INTEGER / NUMBER / BOOLEAN / USER / CHANNEL / ROLE / MENTIONABLE / ATTACHMENT の 9 種で、BOOLEAN が 2 択として最も近いにとどまる。複数選択はメッセージコンポーネントのセレクトメニューで実現し、`min_values` / `max_values` で選択数を制御する。

**mmkn では `STRING_SELECT` を自前で構築する。** `USER_SELECT` は Discord のサーバーメンバーを候補に出すが、**Discord のサーバーメンバーと mmkn の Member は別物**である（`domain/group.md`）。選ばせるのは mmkn の Member であり、Discord のメンバーではない。

- 選択結果は **ID の配列**で届く。名前は Interaction に同梱される `resolved` から引ける（別途 API を呼ぶ必要はない）
- `default: true` を指定した項目は初期状態で選択済みにできる。既定値の提示に使う
- **中間状態を持たない設計にする。** セレクトメニューは選び終えて閉じた時点で、選択値をすべて含んだ Interaction が飛ぶ。選択をセレクト 1 回で確定させることで、保存すべき状態が発生しない
  - HTTP Interactions は状態を持たず、サーバーレスではプロセス内メモリにも置けない（`adr/0003`）。中間状態を持つと実質的にセッションを自前で持つことになり、期限切れの掃除まで抱える
  - **確定用のボタンをセレクトと別に置かない。** 別に置くと選択値をボタンの押下まで運ぶ必要が生じ、`custom_id` の 100 文字に収まらないか、メッセージに埋めた値を信じることになる（下の「メッセージに埋めた値を信じない」と衝突する）

#### 負担者の選択とモーダルを直列にしない

Payment は「金額・内容・負担者」を一度に受ける操作であり、**モーダル → セレクトの 2 段に割ると前段の入力値を運ぶことになる**（上記「モーダル」の 2 つ目の規則）。Member の識別子は `adr/0002` と同じ生成方法（cuid2・24 文字）であるため、複数人分を `custom_id` の 100 文字に載せることもできない。したがって Payment の入力導線は次のどちらかに倒し、間を取らない。

**モーダルに選択部品を置けることを確認した。したがって Payment の入力導線は「モーダル 1 枚で完結させる」（金額・内容・負担者）に確定する。** [確定]

`STRING_SELECT` はモーダルの中に置ける。`min_values` / `max_values` による複数選択も同じように使える（上限は 25 件）。**モーダルの中では `ACTION_ROW` ではなく `LABEL` に入れる**（メッセージの中では `ACTION_ROW`）。加えて `required` はモーダルの中の `STRING_SELECT` でのみ効き、メッセージでは無視される。

これにより、`adr/0006` が採る 2 つの規則（「モーダルを開く応答は永続化に問い合わせずに組み立てられるものに限る」「1 つの操作の入力を 1 つのモーダルで完結させる」）を保ったまま Payment を組める。負担者の候補は Interaction のペイロードから作れないため、**候補となる Member の一覧をモーダルの組み立て時に永続化から引かない形にする必要がある**。

**候補は 1 つ前の Interaction で引いておき、その返信に載せて運ぶ。** [確定]

```
/mmkn payment          … deferred（実行者のみ）。ここで Member の一覧を引く
  └ 返信：押せないセレクト（候補の実体）＋「入力する」ボタン
       └ ボタン押下      … Interaction に元のメッセージが同梱される
            └ 応答：そこから候補を取り出して組み立てたモーダル（永続化に触れない）
                 └ MODAL_SUBMIT … deferred（公開）→ 登録
```

- **セレクトは押せない状態で置く。** 選んでも Interaction は飛ばないため、「モーダルとセレクトを直列に繋がない」に触れない。運んでいるのは**選択肢であって、書き込みの入力にする値ではない**
- **`custom_id` には載せない。** Member の識別子は 24 文字であり、複数人分は 100 文字に収まらない（上記）。載せるのは通貨・発生日の初期値・操作者自身の Member だけで、これらはいずれも 1 つずつしかない
- **対象の Group も載せない。** 場からその都度解決するため（後述「対象 Group の解決」）、運ぶ必要がない
- 押下時に届く候補が古くなっていることはあり得るが、**実際に書き込まれるのはモーダルから返ってきた値**であり、その Member がそのグループにいるかはドメイン層が判定する（`domain/record.md`）

**通貨はモーダルではなくコマンドの引数で受ける。** モーダルの枠が 5 つしかなく、Payment は「支払った人・負担する人・金額・発生日・内容」で埋まるため。引数の候補はオートコンプリートで返すが、**通貨表はコミット済みの静的な表であり**（`adr/0016`）、永続化への問い合わせを含まない。これは上記「オートコンプリートは…静的に絞り込める場面に限られる」に当たる唯一の用途である。

**Member を選ばない入力（記録の編集、グループ設定の変更、表示名の変更など）も、これまでどおりモーダルで受ける。** ここが今回モーダルを採る主な動機であり、Payment の導線とは独立している。

### 構造上の制約

Discord は上限違反を**メッセージ単位で拒否**し、原因が分かりにくい。**表示を組み立てる側で切り詰め、テストで固定する。**

- 部品は必ず ActionRow に入れる。**1 メッセージ 5 行**、1 行にボタン 5 個 / セレクト 1 個
- Embed は**フィールド 25 個**、フィールド値 1024 文字、説明 4096 文字
- `custom_id` は 100 文字、オートコンプリートの候補は 25 件
- **モーダルは 1 枚あたり 5 部品まで**（1 部品 1 スロット）。`TEXT_INPUT` はモーダル専用で、通常のメッセージには置けない
  - **モーダルの中の入力部品は `LABEL` に入れる。** メッセージ側の `ACTION_ROW` とは包み方が違う（上記「負担者の選択とモーダルを直列にしない」）
  - セレクトの候補は 25 件まで。**Member が 25 人を超えるグループでは負担者を選びきれない。** 上限に達したときの振る舞いは `domain/` に無く、必要になった時点で決める
- `TEXT_INPUT` の入力長の上限は Discord 側で 4000 文字まで指定できるが、**mmkn が指定する値は `domain/` から取る**（内容は `domain/record.md`、グループ名・表示名は `domain/group.md` を正とする）。**画面側で独自の数値を打たない**
- Link ボタンは `url` を持ち `custom_id` を持たない（押しても Interaction は飛ばない）

## 結果

- 良い点：
  - 常駐プロセスが無く、Vercel 上のエンドポイント 1 本で完結する
  - 署名検証が認証を兼ねるため、Discord 側の入口に独自の認証機構を持たなくてよい
  - ボタンから直接ユースケースを実行できるため、`overview.md` のコアループ（清算案 → 送金 → 記録）が Discord 内で閉じる
  - 複数項目の入力をモーダル 1 枚で受けられるため、Web のフォームと Discord の入力の形が近くなる（`adr/0009`）
- 留意点：
  - **リアクション（スタンプ）を操作のトリガーにできない。** 後述
  - コマンド登録がデプロイと独立しているため、**デプロイしたのに反映されない**状態が構造的に起こり得る
  - **メッセージで応答するコマンドは、一律 deferred のため一瞬「考え中」を経由する。** 応答が速い処理でも即答には見えない。無反応で失敗するよりは良い、という判断（モーダルを開くコマンドはこの経路を通らない）
  - **オートコンプリートだけは 3 秒の制約を正面から受ける。** 永続化への問い合わせを含められないため、`domain/` の値（Member や通貨）から候補を出す入力には使えない。使うとすれば、入力済みの文字列から静的に絞り込める場面に限られる
  - **モーダルを開く応答だけは、3 秒の枠を「中身を作る処理」抜きで受ける。** コールドスタートが 3 秒に収まらなければ無反応になる点は deferred response と変わらず、モーダルによって増えたリスクではない。ただし**この経路だけは defer による救済が効かない**ため、モーダルの組み立てに永続化を混ぜないという規則を破ると、そこだけ壊れる
  - **モーダルからモーダルを開けない。** 2 枚目が要る操作は組めない。必要になった時点でこの決定を見直す
  - **モーダルの初期値に、保存済みの値をそのまま出せない。** 永続化に問い合わせられないため、記録の編集で現在の値を初期表示するには、その値をボタンを載せたメッセージ側から運ぶ必要がある
  - **負担者を選ぶセレクトの候補が 25 件までであるため、Member が 25 人を超えるグループでは Payment の登録が Discord から行えない**（上記「構造上の制約」）。`domain/` は Member 数の上限を定めていないため、この差はクライアント側の制約として残る
  - **公開として宣言した単位で失敗すると、エラーやアカウントを持たない人への案内も全員に見える。** 一律 deferred を保ったまま避ける方法は無い。目立って困る場面が出たら、下の代替案（常に実行者のみで defer する案）を再検討する
  - **Discord は操作した人の手元の日付を伝えない。** `domain/record.md`「発生日」は、入力欄の初期値に出す「今日」を操作者の手元の日付としているが、Interaction にその手がかりが無い。**初期値としては実行環境の日付を出し、モーダルで直せる**。ただし清算案のボタンはモーダルを経由しないため、そこだけは直す機会が無い。`[保留]`（`open-questions.md` #17）
  - 中間状態を持たないため、**モーダル 1 枚かセレクト 1 回で確定できない操作は組めない。** 必要になった時点でこの決定を見直す（メッセージ自身を状態にする案・保存する案は下の代替案にある）

## 検討した代替案

- **Gateway に常駐接続する Bot（別サーバー）**：リアクションなど Gateway イベント全般を扱えるようになる。ただし常駐サーバーが必要になり、スケール・死活監視・再起動を個人開発で抱えることになる。`adr/0003` の「常駐プロセスを持たない」前提そのものを覆すため採らない。
- **リアクション（スタンプ）を操作のトリガーにする**：直感的だが、**リアクションは Interaction ではなく Gateway イベント**であり、常駐 WebSocket 接続を張ったプロセスにしか届かない。HTTP Interactions のエンドポイントには飛んでこないため、採用した構成と両立しない。ボタンで代替する。
- **プレーンテキストで返信する**：実装が軽い。ただし収支・清算案は「誰が・いくら・どの通貨」の三つ組が並ぶ表であり、テキストでは可読性が落ちる。Presenter に閉じている以上、Embed にするコストは 1 か所に収まる。
- **返信ごとに可視性を指定する**（初版の記述）：同じコマンドでも成功と失敗で可視性を変えられる。ただし deferred response の可視性は後から変えられないため、一律 deferred と両立しない。撤回した。
- **常に実行者のみで defer し、公開したい結果だけをチャンネルへ別メッセージとして投稿する**：エラーと案内を必ず実行者だけに返せる。ただし 1 つの操作で送信が 2 回になり、実行者の手元には「考え中」から変化した実行者専用の返信が、チャンネルには公開の投稿が、それぞれ残る。表示が二重になる分かりにくさに見合わない。
- **常に公開で defer する**：最も単純。ただし入力途中のやり取りやアカウントを持たない人への案内まで全員に見えることになり、上の使い分けが成立しない。
- **`USER_SELECT` で Discord のサーバーメンバーから選ばせる**：候補を Discord が用意してくれるため実装が軽い。ただし選ばれるのは Discord のユーザーであって mmkn の Member ではなく、グループに参加していない人や mmkn のアカウントを持たない人を選べてしまう。
- **ギルド（サーバー）を場とする**：対応が 1 サーバー 1 グループになり最も単純。ただしイベントごとに Discord サーバーを作る運用を強いる。既存のサークルのサーバーに mmkn を入れると、そのサーバーで一生に 1 イベントしか扱えない。ターゲット（`overview.md`）と合わない。
- **場という概念を持たず、毎回コマンド引数で Group を指定させる**：紐づけの仕組みが要らず、DM でも使える。ただし記録のたびに対象を選ぶ手間がかかり、返信を公開する意味も薄れる。なお `adr/0004` により、後からこの入口を足してもユースケースは変わらない。
- **原則は即時応答とし、重い処理だけ deferred にする**：応答が 1 段階で済み体感が速い。ただし「どれが重いか」をコールドスタート込みで見極める必要があり、外したときの失敗が無反応になる。分岐を持つ価値がない。
- **メッセージ自身を中間状態にする（`UPDATE_MESSAGE` で選択状態を描き直す）**：サーバーに状態を置かず多段階にできる。ただし「メッセージに埋めた値を信じない」と正面から衝突し、古いメッセージから実行できてしまう。
- **モーダルを使わず、入力をすべてスラッシュコマンドの引数とセレクトで受ける**（初版の記述）：扱う Interaction 種別が 1 つ減り、初回応答が常にメッセージになる。ただし長い自由入力と複数項目の入力をコマンドの引数に並べることになり、実際に打つ側の負担が大きい。撤回の理由は上記「モーダル」の引用を正とする。
- **すべての Interaction を無条件に deferred にする（初版の記述）**：分岐が一切要らない。ただし `PING` は `PONG` しか返せず、`APPLICATION_COMMAND_AUTOCOMPLETE` には deferred 形が存在しないため、そもそも実装できない。撤回した。
- **中間状態を期限付きで DB に保存する**：どんな多段階フローでも組める。ただし実質的にセッションを自前で持つことになり、掃除の仕組みまで必要になる。セレクト 1 回で足りるうちは持たない。
