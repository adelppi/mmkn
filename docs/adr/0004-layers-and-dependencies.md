# ADR-0004: 層を単一パッケージ内で分け、依存方向を CI で機械検査する

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/domain/settlement.md`, `adr/0003-tech-stack.md`, `adr/0008-layer-internals.md`, `adr/0009-web-ui.md`, `adr/0010-testing.md`, `adr/0011-ci-and-release.md`

## コンテキスト

mmkn は Web と Discord の 2 つの提供形態を持ち、機能に差を設けない（`overview.md`）。差を設けないためには、**クライアントごとに増えるコードを業務ロジックから物理的に切り離す**必要がある。

**Discord は数あるクライアントの 1 つとして扱う。** Slack や CLI を後から足しても、アダプタ層と合成ルートの追加だけで済む状態を設計目標に置く（それらを作る予定は現時点ではない）。この目標は「クライアント固有のものを内側に持ち込まない」という形で、以下の原則すべてに効いている。

加えて `domain/settlement.md` が定める収支・清算案の導出は mmkn の中心にある考え方であり、フレームワークや DB の都合で書き換わってはいけない。

PoC ではこの構成で 6 種類の変更（クライアント追加・表示形式の変更・永続化の 3 段階の差し替え・Discord 返信の可視性制御の追加・アカウント連携方式の変更・返信ボタンからのユースケース実行）を実際に行い、**いずれもドメイン層が無変更で済むこと**を確認した。既存テストがそのまま回帰テストとして機能した。

## 決定

クリーンアーキテクチャを採る。**構造と命名は実装時に定めてよいが、以下の依存の向きと責務の分離は変えない。**

### 層と依存の向き

| 層 | 責務 | 依存してよい先 |
|---|---|---|
| ドメイン | エンティティ・値オブジェクト。`domain/` が定めるルールの実装 | なし（言語標準のみ） |
| ユースケース | 手続きの組み立て。**ポート（インターフェース）を定義する** | ドメインのみ |
| アダプタ | クライアント固有の変換器。フレームワーク非依存 | ドメイン・ユースケース |
| インフラ | ポートの実装。ドライバ・永続化 | ドメイン・ユースケース |
| アプリ | フレームワーク。UI・エンドポイント・合成ルート | すべて |

**依存は常に外から内へ向く。内側の層は外側の層を知らない。**

### 守る原則

- **ポートは内側が定義し、実装は外側が持つ。** ユースケース層がリポジトリのインターフェースを定義し、インフラ層が実装する。永続化を差し替えてもポートが変わらないため、内側は影響を受けない
- **外部 ID からアプリの ID への変換は入口だけで行う。** クライアント固有の識別子はアダプタと認証系で吸収し、内側にはアプリの ID だけを流す。これによりクライアントが増えても内側は増えない（`adr/0007-external-account-linking.md`）
- **ユースケースは対象を常にアプリの ID で受け取る。** 「操作の文脈から対象を推測する」ことをユースケースにさせない。`domain/group.md` の「場」から Group を解決するのはアダプタの責務であり、解決手段はポート越しに呼ぶ。場を持たないクライアント（CLI など）は同じユースケースを別の入力から呼べる
- **ドライバ・SDK を業務コードから直接呼ばず、一段挟む。** ORM や外部サービスの SDK はインフラ層の実装の中に閉じ込め、その外から呼ばない。PoC ではこの分離により、実 DB なしで永続化ロジックを（競合時の挙動を含めて）テストできた

### 層の表現とディレクトリ構造

**単一パッケージの中でディレクトリとして分ける。** ワークスペースを分割したパッケージ境界にはしない。

境界の強制は次項の機械検査が担う。パッケージ境界にすると Next.js / Vercel でのビルド構成とパッケージ間参照の設定を個人開発で保守し続けることになり、得られる保証の差に見合わない。

構造については、次の 3 つの規則だけをここで定める。

1. **トップレベルを層で切る。** 機能で切らない。依存検査のルールがパスでそのまま書けるため（`src/domain/**` は `src/**` を import しない、など）。機能を先に切ると、機能を足すたびに検査設定を直すことになる
2. **`src/domain/` の直下を `docs/domain/` の分割に対応させる。** ルールの正（`docs/domain/`）と実装が 1 対 1 で追える状態を保つ。文書を足したらディレクトリを足す
3. **クライアントごとに増える場所を `adapter/` と `infra/` の直下に限る。** ここ以外はクライアントが増えても増えない。クライアント固有でないものを置く例外は `adapter/shared/` だけ

**ディレクトリ構造そのものは `adr/0008-layer-internals.md` を正とする。** 上の 3 規則を満たす具体的なツリーはあちらにあり、ここには再掲しない。`app/` 配下の Web の画面構成は `adr/0009-web-ui.md` を正とする。

### 依存方向の機械検査

**依存方向は目視レビューに頼らず、CI で機械検査する。** 検査するのは 2 つ。

1. 内側の層が外側の層を参照していないこと
2. 層ごとの禁止モジュール（フレームワーク・ランタイム API など）を含まないこと

2 について、**アダプタ層はフレームワークもランタイム API も禁止する。** 「フレームワーク非依存」は言葉での約束ではなく検査で守る。ドメイン層でランタイム API まで禁止することは、識別子の生成をドメインの外に出す根拠にもなっている（`adr/0008`）。

**層ごとの具体的な許可・禁止の一覧は `adr/0008-layer-internals.md` を正とする。**

**検査は既製のツールで宣言的に定義し、検査ロジック自体を自作しない。** 具体的には `dependency-cruiser` を使う。上の 2 つを 1 つの設定で表現でき、CI から実行できることが選定の条件であり、同条件を満たす他のツールへの差し替えはこの ADR の再検討にあたらない。

### テスト

層の分離が守られていれば、内側は外部依存なしでテストできる。**この性質を前提にテストを組む**というのが、この ADR が要求する唯一のことである。

- ドメイン・ユースケースの単体テストは、実 DB・実 HTTP を使わずポートの偽実装で回す
- **クライアントをまたいだ整合**（Web と Discord が同じユースケースを通ること）をテストで固定する。「機能に差を設けない」を守る主たる手段はこれ

**どのツールで何をどこまでテストするかは `adr/0010-testing.md` を正とする。** ここには再掲しない。

## 結果

- 良い点：
  - クライアントの追加・表示の変更・永続化の差し替えが、いずれも内側に波及しない（PoC で実証済み）
  - 「機能に差を設けない」がレビューではなく構造とテストで守られる
  - 依存方向の違反が CI で落ちるため、AI に実装させたときも向きが壊れない
- 留意点：
  - 単一パッケージであるため、**検査が無い状態では境界は何も守られない**。検査の CI 組み込みは後回しにできない
  - 層をまたぐ変換コードが増える。特に小さなユースケースでは冗長に見えるが、それが 2 クライアント分の差を吸収している対価である
  - `docs/domain/` の分割を変えたら `src/domain/` も追随させる。片方だけ変えると対応が崩れる

## 検討した代替案

- **ワークスペースを分割したパッケージ境界（PoC の構成）**：違反がインポート時点で確実に落ちる点は優れる。ただし Next.js + Vercel でのビルド構成が一段複雑になり、個人開発で払うコストとして重い。機械検査があれば向きは同等に守れると判断した。
- **ディレクトリ分割のみ（検査なし）**：最も軽いが、境界が本人の記憶だけで維持される。PoC が実際に否定した案。
- **依存方向の検査を自作スクリプトで書く**（PoC の実装、100 行程度）：依存が増えず規則を完全に把握できるが、その検査自体を自分で保守することになる。既製ツールで同じことが宣言的に書けるため利点がない。
- **層を持たず Next.js の規約に素直に従う**：Server Actions の中に業務ロジックを直接書く形。Web だけなら成立するが、Discord から同じロジックを呼ぶ手段が無くなり、`overview.md` の前提と衝突する。
- **機能を先に切り、その中を層で分ける**：1 つの機能に関わるファイルが近くに集まる。ただし依存検査のルールが全機能分の組み合わせになり、機能を足すたびに検査設定を直すことになる。守りたいのは機能の凝集ではなく依存の向きであるため、向きが素直に書ける方を採る。
