# ADR-0010: テストを Vitest で層ごとに組み、クライアント間の整合とブラウザ経路だけを外に出す

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/features.md`, `docs/domain/record.md`, `docs/domain/settlement.md`, `adr/0004-layers-and-dependencies.md`, `adr/0005-data-access-and-authorization.md`, `adr/0008-layer-internals.md`, `adr/0009-web-ui.md`, `adr/0011-ci-and-release.md`

## コンテキスト

`adr/0004` は「層の分離が守られていれば内側は外部依存なしでテストできる」という性質と、守るべき 3 点だけを定めて、道具と範囲を空けている。加えてテストの前提が各 ADR に散っている。

- Presenter は Controller が呼ぶ純関数（`adr/0008`）
- ビューモデルはシリアライズ可能な素の値だけで構成する（`adr/0009`）
- `presentation.stories.tsx` がディレクトリ構造に組み込まれている（`adr/0009`）
- 実 DB に対する疎通と整合を確認する手段が要る（`adr/0005`）

実装に入る前にここを一本化する。

制約は 3 つ。

- **個人開発であり、CI の待ち時間はそのまま自分の待ち時間になる**（`overview.md`）
- **「2 つの提供形態で機能に差を設けない」を守る主たる手段がテストである**（`adr/0004`）。ここだけは削れない
- **`adr/0005` は RLS を保険としてすら業務ルールで書かないと決めている。** その結果「アプリのバグがそのままデータの誤りになる。テストで守る」を留意点に挙げており、その約束をここで具体化する義務がある

## 決定

### 道具

| 用途 | 採用 |
|---|---|
| 単体・統合 | Vitest |
| ブラウザ経路の E2E | Playwright |
| 表示のカタログ | Storybook |

Vitest は Next.js + TypeScript での設定が軽く、`src/` の内側から React の描画まで同じランナーで回せる。ランナーを 2 つ持たないことを条件に選んだ。

### テストの種別と置き場

**テストは対象の隣に置く**（`src/domain/record/payment.test.ts` の形）。`adr/0009` が `presentation.stories.tsx` で既に採っている形に揃える。

| 種別 | 対象 | 外部依存 | 置き場 |
|---|---|---|---|
| 単体 | domain / usecase / presenter / controller | なし（ポートは偽実装） | 対象の隣 |
| 永続化 | `infra/db` のリポジトリ | ローカル Postgres | 対象の隣 |
| クライアント間整合 | Web と Discord の入口 | ローカル Postgres | `tests/` |
| E2E | 起動したアプリ | ローカル Postgres | `tests/` |

**下 2 つだけを `tests/` に出すのは、依存方向の検査と衝突するためである。** クライアント間整合のテストは `adapter/web` と `adapter/discord` の両方を import する。これを `src/usecase/` の隣に置くと、`adr/0008` が禁止した「ユースケース層からアダプタ層への参照」に該当してしまう。**テストファイルも依存検査の対象に含め、検査を通すために規則を緩めない**（`CLAUDE.md`）。したがって、対象が 1 つの層に定まらないテストだけを層の外に置く。

### クライアント間の整合をどう固定するか

**同じシナリオを Web と Discord の両方から流し、できあがった記録が一致することを検証する。** 入口だけを差し替え、以降は同じユースケースを通ることを結果で確かめる。

```
グループを作る → 支払いを記録する → 収支を見る → 清算案から送金を記録する

  ① Server Action 経由で一巡させる
  ② 署名付き Interaction 経由で同じ操作を一巡させる
  ③ ①と②の結果できた記録が一致することを検証する
```

呼び先の一致を型やスパイで見るのではなく**結果で見る**のは、「機能に差を設けない」が守りたいのは呼び出し構造ではなくユーザーから見える振る舞いだからである。

### 実 DB を使うテスト

**ローカルの Postgres にマイグレーションを当て、`infra/db` のリポジトリをそこに対してテストする。** Supabase のローカル環境は使わない。検証したいのは永続化の振る舞いであり、アプリは PostgREST を経由しない（`adr/0005`）ため、Supabase 固有の層を挟む必要がない。

ここで固定するもの:

- マッパーが ORM の推論型をリポジトリの外へ漏らさないこと（`adr/0008`）
- 集約単位の保存が成立すること。**Group の保存で、追加された Member だけが書き込まれること**（`adr/0008`）
- 同じ Group・同じ User の Member を 2 つ作れないこと（`adr/0005`）
- 同じログイン識別子の User を 2 つ作れないこと（`domain/group.md`・`adr/0012`）
- **楽観ロックが実際に競合を弾くこと。** 古い版で更新・削除を試みると失敗する（`domain/record.md`「同じ記録に同時に手が入ったとき」）
- **すべてのテーブルで RLS が有効であること。** `adr/0005` は「テーブルを追加したら全拒否ポリシーも必ず追加する。付け忘れたテーブルだけが anon key に露出する」を留意点に挙げている。付け忘れを人の注意力に任せず、スキーマを走査して検証する

### E2E の範囲

**自分の管理下にある画面と自分のエンドポイントに限る。**

- Web：グループ作成 → 参加 → 支払いの記録 → 清算案の表示 → 清算案からの送金記録
- Discord：自分で署名したリクエストをエンドポイントへ投げ、**署名検証が入口として効いていることを確認する**（正しい署名は通り、署名の対象と違う本文や、ヘッダの無いものは通らない）

**外部サービスへ出ていく通信は、E2E の対象から外す。** 2 か所ある。

- **認可画面をまたぐ往復は自動化しない。** Discord 側の画面の変更で壊れ続け、壊れても mmkn 側には何の情報も無い。ログイン手段の追加が成立するかは `docs/operations.md`「実装着手時に必ず確かめること」に手動確認の対象として登録してあり、そちらを正とする
- **follow-up が届いたことも確かめない。** 送信先は Discord の API であり、確かめるには外部のネットワークに触れることになる（`adr/0011` は「どちらの経路も、リポジトリの中にあるものだけで完結する」と定めている）。**送信が間に合うかは `docs/operations.md`「実装着手時に必ず確かめること」の手動確認が正**であり、E2E はその代わりにならない

### E2E が使う認証基盤 [確定]

**持たない。E2E の間だけ、アプリが繋ぐ先を偽の認証に差し替える。**

CI 内でアプリを起動する以上、アプリは認証基盤に繋がる。**DB には「使い捨ての Postgres」という逃げ道があるが、認証基盤には対応するものが無い。** 本番の認証基盤に向ければ E2E が本物のアカウントを作り、`overview.md`「前提」（無料枠）と `adr/0015`（バックアップを持たない）の両方に触れる。

- **差し替えるのは、外部の認可画面の代わりをする部分だけである。** 画面もユースケースも永続化も、本物と同じものが動く
- **切り替わるのは環境変数が立っているときだけで、既定は本物である。** その変数をホスティング環境に置かない（置き場の正は `docs/operations.md`「環境変数」）
- **この差し替えは本番にも出るコードの中にある。** 偽の認証を持つこと自体が代償であり、**「既定で切り替わらないこと」がその安全性のすべてである**（そのための検査を単体テストに持つ）

**代償として、認証基盤そのものの挙動は E2E では何一つ確かめられない**（同じ外部アカウントで再ログインしたときに同じ user が返るか、ログイン手段の追加が成立するか）。それらは `adr/0012` が「着手時に必ず確かめること」に挙げており、**手動確認が正である。E2E があることでその確認を省けるようにはならない。**

### Storybook

**持つ。ただしスナップショット比較は持たない。**

`adr/0009` が「失敗時の表示も props だけで確認できる」を利点に挙げており、それを実際に使うための道具として置く。ビューモデルがタグ付き union になっている（`{ kind: 'ok' | 'empty' | 'notMember' }`）ため、失敗形を含む全分岐をカタログとして並べられる。

見た目の差分検出まで持たないのは、個人開発で判定のぶれを引き取る余裕がないため。**CI ではビルドが通ることだけを確認する**（`adr/0011`）。

### カバレッジ

**数値目標を持たない。** `overview.md`「成功の見方」と同じ理屈で、追って意思決定を変える場面がないため。

代わりに、レビューの観点を 1 つ置く。

> **`docs/domain/` の各文書の「起きないこと」と「境界・例外ケース」に、対応するテストがあるか。**

mmkn のドメイン文書は「起きないこと」を明示する形で書かれている。そこがそのままテストの一覧になるため、網羅の基準を行数ではなく文書に置ける。

### 実行のタイミング

どのテストを PR で回し、どれを main へのマージ時に回すかは `adr/0011-ci-and-release.md` を正とする。

## 結果

- 良い点：
  - 「機能に差を設けない」が結果の一致という形で固定され、構造の変更で壊れない
  - `adr/0005` が RLS を書かないと決めた分の穴（付け忘れたテーブルの露出・競合の取りこぼし）が、テストで塞がる
  - 網羅の基準が `docs/domain/` にあるため、仕様を足したときにテストの不足が文書から分かる
- 留意点：
  - **ローカル Postgres が要るテストが増えるため、手元に Docker が必要になる。** 単体テストだけは何も無しで回る状態を保つ
  - クライアント間整合のテストは 1 シナリオでも重い。**シナリオを増やしすぎない。** 差が出るのは入口だけなので、通す経路の種類を増やすより 1 本を確実に保つ
  - `tests/` と対象の隣の 2 か所にテストが分かれる。分ける基準は「層をまたぐか」だけであり、それ以外の理由で `tests/` に置かない
  - **Storybook の部品は自分で保守する**（`adr/0009` が既に受け入れているコストと同種）
  - **偽の認証が本番のコードの中にある。** 環境変数が立っているときだけ切り替わるが、**立ててしまえばログインを迂回できる**。守るのは「置かない」という運用ひとつだけである
  - **E2E は認証基盤について何も言わない。** ログインの往復が本物として成立するかは、引き続き人が確かめる（`docs/operations.md`）

## 検討した代替案

- **`node:test`（標準）を使う**：依存が増えない。`src/` の内側はこれで十分だが、React の描画テストと Storybook の連携に別の仕組みが要る。ランナーを 2 つ持たないという条件で外した。
- **Jest を使う**：資料が最も多い。ただし ESM と TypeScript の設定が重く、起動も遅い。個人開発では待ち時間が直接効く。
- **テストをすべて `tests/` に集約する**：本体と混ざらない。ただし層の構造を `src/` と `tests/` の 2 か所で保守することになり、`adr/0004` が「文書を足したらディレクトリを足す」で保っている 1 対 1 の対応が 3 者関係になる。
- **テストファイルを依存検査の対象から外す**：クライアント間整合のテストを `src/usecase/` の隣に置ける。ただし検査を通すために規則側を緩めることになり、テストを経由した依存の逆流を許す穴が開く。
- **クライアント間の整合を「両クライアントに入口があるか」の網羅表で見る**：軽く、入口の作り忘れを確実に落とせる。ただし入口があることしか分からず、同じ操作が別の結果になる場合を拾えない。守りたいのは振る舞いの一致であるため、結果で見る方を採る。
- **実 DB を使わず偽実装だけでテストする**：Docker が要らず最も速い。ただし楽観ロックが実際に競合を弾くか、RLS の付け忘れが無いかを確かめる手段が消える。`adr/0005` がテストで守ると約束した部分がそのまま空く。
- **Supabase のローカル環境を使う**：本番に近い形で検証できる。ただし起動が重く、検証したい永続化の振る舞いに Supabase 固有の層は関与しない。
- **外部サービスの認可画面まで E2E で自動化する**：ログインとログイン手段の追加の経路全体を機械で守れる。ただし他社の画面の変更で壊れ続け、壊れた原因が mmkn 側に無い状態を CI が報告することになる。
- **本物の認証基盤を CI の中に立てる（コンテナ、またはローカルスタック）**：偽物を持たずに済み、認証基盤の挙動も確かめられる。ただし認証基盤の API の経路を CI 内で組み直す必要があり、起動と保守の対象が増える。**E2E から本物のログインを通せない**（認可画面を自動化しないため）以上、立てても確かめられるのは認証基盤の一部だけになる。
- **E2E 専用の認証基盤のプロジェクトを、本番とは別に用意する**：本物に向けたまま、本番のデータから隔離できる。ただし無料枠で管理する対象が 1 つ増え（`overview.md`「前提」）、やはり認可画面をまたげないため E2E からログインできない。
- **アプリの外に、認証基盤の API を真似たスタブを置く**：アプリのコードに分岐が入らず、迂回できる経路が本番のコードに残らない。ただし認証基盤の API の形（トークンの発行と検証の往復）を自分で真似ることになり、**壊れ方が分かりにくいものを増やす。** 個人開発で背負う量として、アプリ側の分岐 1 か所より重い。
- **ログインの要らない範囲だけを E2E で見る**：偽の認証を持たずに済む。ただし mmkn の画面はほぼすべてログイン済みであることを前提としており、**E2E の対象が実質的に無くなる。**
- **Storybook を持たず、コンポーネントテストだけにする**：保守する部品が 1 つ減る。ただし失敗時の表示を目で確認する経路が無くなり、`adr/0009` が Container/Presentational を分けた利点の半分が使われないままになる。
- **カバレッジの下限を CI で強制する**：抜けが機械的に落ちる。ただし数値を満たすためのテストが増え、`docs/domain/`「起きないこと」との対応という本来見たい基準がぼやける。
