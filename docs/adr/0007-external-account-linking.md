# ADR-0007: 外部アカウントの連携は、ログイン済みの Web から OAuth で行う

- ステータス: 採用 [確定]
- 関連: `docs/domain/group.md`, `docs/features.md`, `adr/0003-tech-stack.md`, `adr/0004-layers-and-dependencies.md`, `adr/0005-data-access-and-authorization.md`

## コンテキスト

`domain/group.md` は、User が「グループをまたいで変わらない同一性」を持つこと、外部サービスのアカウントは User に紐づく**連携**として扱うこと（ログイン手段そのものにはしないこと）を定めている。**その実現方式**をここで決める。

Discord から届くスラッシュコマンドには、Discord のユーザー ID が含まれる。この ID から mmkn の User を引けなければ、Discord 側からは何も操作できない。したがって「どの Discord ユーザーがどの User か」を、なりすませない形で記録する手段が要る。

PoC では 2 方式を実装した。ワンタイムの連携コードを人が運ぶ方式と、ログイン済みの Web から OAuth の認可コードフローで連携する方式である。後者は動作確認まで済んでいる。

## 決定

### 連携の方式

**ログイン済みの Web から、OAuth 2.0 の認可コードフローで連携する。**

```
1. Web でログイン（mmkn のアカウント）
2. 「Discord を連携」→ Discord の認可画面へリダイレクト
3. 承認 → コールバック → (discord, Discord のユーザー ID) → User の対応を記録
4. 以降、スラッシュコマンドで届いたユーザー ID でこの対応を引く
```

Discord が「このブラウザの持ち主がこの Discord アカウントの持ち主である」ことを保証し、その証明をリダイレクト経由でサーバーへ直接渡す。CSRF は `state` パラメータで防ぐ。

**この方式の要点は、共有秘密を人間が運ばないことにある。** 連携コード方式は「コードを知っている人 = 本人」という仮定に乗るため、コードが漏れれば第三者が自分のアカウントを紐付けられる。有効期限と 1 回限りの消費は緩和策にすぎず、仮定そのものは消せない。OAuth 方式にはこの経路が存在しない。

### 実装

**Supabase Auth の identity linking に委譲する。** 認可コードフローを自前で実装しない。

セッション管理を Supabase Auth に寄せる方針（`adr/0003`）と一貫させるための選択であり、実装量による選択ではない。PoC は認可コードフローを直接実装しており、必要だったのはポート 1 つとその実装、エンドポイント 2 本だけだった。**どちらを選んでも方式そのものは変わらない。**

### 着手時に必ず確認すること

**この方式は「連携時に記録される Discord のユーザー ID」と「スラッシュコマンドで届くユーザー ID」が同一である前提に乗っている。**

PoC では認可コードフローを直接実装した経路でこの前提を確認した。**認証基盤に委譲する場合は、基盤が保存する値について改めて確認する**（間に 1 層挟まるため、同じ値である保証が自前実装より弱い）。

**実アカウントを 1 件連携して突き合わせれば数分で終わり、外れたときの影響は Discord 側が丸ごと動かないことである。実装の最初に行う。**

### 運用上の要件

- **要求するスコープは ID の取得に必要な最小限（`identify`）にとどめる。** メールを取得すると、認証基盤によっては「検証済みメールが一致する identity を自動統合する」挙動を誘発し、**意図しないアカウント統合**につながる。メールが必要になった時点で、統合の挙動と併せて決める
- **アクセストークンを保存しない。** 必要なのは「この Discord ユーザーの ID」という一度きりの事実だけで、Discord API を代理で叩き続ける必要はない。保存しなければ漏洩も失効管理も発生しない
- **認証基盤のスキーマへの依存をポートで隔離する。** 連携情報の参照は認証基盤の内部テーブルを読む形になるため、リポジトリのポートを挟み、**その実装の中だけで参照する**（`adr/0004`）。将来スキーマが変わった場合や、自前の射影テーブルに切り替える場合も、実装の差し替えだけで済む
- **外部 ID からアプリの ID への変換は入口で閉じる**（`adr/0004`）。内側には mmkn の User の ID だけを流す
- **未連携のまま Discord から操作された場合の案内をアダプタ側で返す。** 振る舞いは `domain/group.md`「連携していない状態で外部サービスから操作したとき」を正とする。可視性は実行者のみ（`adr/0006`）

## 結果

- 良い点：
  - 共有秘密を人間が運ぶ経路が存在しない
  - `domain/group.md` の「連携」の実現に必要なのがエンドポイント 2 本とポート 1 つで済む。連携コード方式が必要としたエンティティ・発行と引き換えの手続き・保存・スラッシュコマンド・期限管理がまるごと不要になる
  - PoC で層の構造に収まることを確認済み（ユースケース層にポート 1 つ、インフラ層に実装 1 つ。ドメインは無変更）
- 留意点：
  - **Discord から入ってきた人も、まず Web でアカウントを作る必要がある。** 導線を用意しないと、Discord しか使わない人が入口で詰まる
  - 認証基盤に委譲する分、保存される値の形を自分で決められない（上記「着手時に必ず確認すること」）
  - `domain/group.md` は連携の解除を認めている。**認証基盤側の identity 削除が、最後の 1 つになったときにどう振る舞うかを確認する**（アカウント自体が消える基盤もある）

## 検討した代替案

- **連携コード方式（PoC 初期の実装）**：Web と Discord のどちら側からでも開始できる利点がある。ただし「コードを知っている人 = 本人」という仮定に乗り、コードが漏れれば第三者が自分のアカウントを紐付けられる。有効期限と 1 回限りの消費は緩和策にすぎず、仮定は消せない。実装量も、エンティティ・発行と引き換えの手続き・保存・スラッシュコマンド・期限管理と大きい。
- **Discord をログイン手段そのものにする**：Discord から入ってきた人が Web でアカウントを作らずに済み、上の留意点が消える。ただし `domain/group.md` が「User は mmkn 自身のアカウントとして成立する」と定めており、Discord アカウントを失った時点で User に到達できなくなる。ドメインの決定と衝突するため採らない。
- **認可コードフローを自前で実装する（PoC の実装）**：保存される値を自分で決められるため、上の「着手時に必ず確認すること」のリスクが消える。ただしセッション管理を Supabase Auth に寄せる方針（`adr/0003`）とは別経路になり、セッションの発行元が 2 つある状態を保守することになる。
- **Discord のユーザー ID をユーザー自身に入力させる**：実装は最小だが、他人の ID を入力すればそのまま他人になりすませる。検討に値しない。
