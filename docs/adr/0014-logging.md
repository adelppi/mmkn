# ADR-0014: ログを標準出力への構造化ログに限り、監視サービスを持たない

- ステータス: 採用 [確定]
- 関連: `docs/overview.md`, `docs/domain/record.md`, `adr/0003-tech-stack.md`, `adr/0006-discord-http-interactions.md`, `adr/0008-layer-internals.md`, `adr/0011-ci-and-release.md`

## コンテキスト

`adr/0008` は「ログ・計測は合成ルートで包む」と一行だけ触れ、**何を出すかを決めていない**。決めないまま実装すると、出す場所も形式も実装のたびに変わる。

この構成では、障害が特に分かりにくい形で出る。

- **常駐プロセスが無い**（`adr/0003`）。リクエストが来ていないときに見るものが存在しない
- **Discord は「無反応」という形で失敗する**（`adr/0006`）。一律 deferred のため、失敗しても「考え中」のまま止まる
- **応答を返したあとに処理を続ける**（`adr/0003`）。follow-up の送信に失敗しても、利用者からは何も見えない
- 記録は金銭の情報であり、ログに出してよい値と出してはいけない値がはっきり分かれる

制約は 1 つ。**個人開発であり、通知の設定・ノイズの調整・サービスの管理を抱える余裕がない**（`overview.md`）。

## 決定

**標準出力に構造化ログ（1 行 1 JSON）を出し、ホスティング環境のログに集約させる。監視サービス・エラー通知を持たない。**

### 必ず出すもの

| 項目 | 内容 |
|---|---|
| 相関 ID | 1 リクエスト（1 Interaction）で一貫する識別子。応答後に続く処理も同じ ID で出す |
| クライアント | `web` / `discord` |
| ユースケース名 | 呼んだユースケース |
| 結果 | 成功か、失敗ならその種類（`adr/0008` の失敗の union のタグ） |
| 所要時間 | ユースケースの実行にかかった時間 |

失敗については、`Result` が `ok: false` を返したもの（想定された失敗）と、例外として抜けたもの（想定していない失敗）を**区別して出す**。前者は通常の結果であり、後者だけが調べる対象になる。

### 絶対に出さないもの

- **金額・通貨・内容（`description`）・表示名・グループ名** — 記録の中身そのもの
- メールアドレス、パスワード、認証基盤のトークン、Discord の Bot Token
- 参加コード（知っていれば参加できるため。`adr/0002`）

**対象を指すときは ID だけを出す。** ID から中身を引くには DB に触る必要があり、その経路はユースケースを通る（`adr/0005`）。

### どこで出すか

**ユースケースを包む形で、合成ルートに置く**（`adr/0008` の `wire()`）。ドメイン層・ユースケース層はログの存在を知らない。出力の実装は `infra/log`。

**ドメイン層とユースケース層に `console` を書かない。** `adr/0004` の依存方向の検査で禁止モジュールとして扱えるため、目視ではなく検査で守る。

### 気づき方

**能動的な通知を持たない。** 障害の検知は次の 2 つで行う。

1. **利用者からの報告**（自分と周囲が使っているため。`overview.md`「成功の見方」）
2. **`docs/operations.md` の診断コマンド** — 報告を受けてから、設定と疎通を確かめる

相関 ID をログに出しているのは、**この 2 つを繋ぐため**である。「◯時ごろ Discord が無反応だった」から該当の実行を特定できる状態を作る。

## 結果

- 良い点：
  - 抱える部品が増えない。ホスティング環境が既に持っているログ機構だけで完結する
  - 「何を出すか」が決まっているため、実装ごとにログの形が変わらない
  - 応答後に続く処理（`adr/0003`）を相関 ID で追えるため、`adr/0006` の「無反応」が調べられる状態になる
  - 記録の中身を出さないと決めておくことで、ログの保存先が信頼境界の外にあっても問題にならない
- 留意点：
  - **自分が見に行くまで、障害は誰にも気づかれない。** 利用者が黙って使うのをやめた場合、何も残らない
  - **ホスティング環境の無料枠では、ログの保持期間が短い。** 報告が遅れると該当の実行が既に消えている
  - 記録の中身を出さないため、「この記録がおかしい」という報告に対してログだけでは追えない。DB を見ることになる
  - 通知を持たない判断は、利用者が自分と周囲に閉じている前提に乗っている。**その前提が外れたらこの ADR を見直す**

## 検討した代替案

- **エラー通知を足す（Discord の Webhook や メールに飛ばす）**：ログを見に行かなくても気づける。ただし「何を通知に値する失敗とするか」を決め続けることになり、想定された失敗（Member でない、清算案が変わった）が大量に飛ぶ状態と、絞りすぎて何も飛ばない状態の間で調整を抱える。利用者が自分と周囲である以上、報告の方が速い。**通知が必要になるのは、知らない人が使い始めたときである**。
- **エラー監視サービス（Sentry 等）を入れる**：スタックトレースと発生頻度がまとまり、通知の調整も既製のものに乗る。ただし個人情報と金額を送らない設定を自分で維持することになり、無料枠の制限（イベント数・保持期間）も管理対象に増える。上と同じく、利用者の規模が前提を満たしていない。
- **ログを DB に書く**：保持期間を自分で決められ、診断コマンドから引ける。ただし金銭記録と同じ DB に書き込みが増え、`adr/0011` が「DB は 1 つしか持たない」と決めた制約の中で容量を食う。障害時に DB 自体が原因だと何も残らない。
- **何も決めず、実装しながら必要に応じて出す**：着手が最も速い。ただし出す場所と形式が実装ごとに変わり、「金額を出してしまった」ことに後から気づく形になる。出してはいけないものを先に決めておく価値の方が大きい。
- **構造化せずプレーンテキストで出す**：読みやすい。ただし相関 ID での絞り込みが文字列検索になり、応答後に続く処理を追う用途で弱い。
