# ADR-0012: ログインを外部サービスの OAuth に委ね、1 User が複数のログイン手段を持てるようにする

- ステータス: 採用 [確定] — 2026-08-14 改訂（2 度目）
- 関連: `docs/domain/group.md`, `docs/features.md`, `docs/overview.md`, `adr/0003-tech-stack.md`, `adr/0006-discord-http-interactions.md`, `adr/0007-external-account-linking.md`（廃止）, `adr/0008-layer-internals.md`

**この ADR は 2 度改訂している。** 撤回した決定と理由は次のとおり。

| 版 | 決定 | 撤回の理由 |
|---|---|---|
| 2026-08-12 | メールアドレス + パスワード | 既定のメール送信サービスがチーム外に配信しない（下記「着手時の確認結果」） |
| 2026-08-13 | **Google 単独**でログインし、Discord は**連携**として別の役割に置く | 役割を 2 つ持つ必要が無く、Google を持たない人が使えず、失ったときの復旧手段も無かった（下記「2 版目を撤回した理由」） |

## コンテキスト

`domain/group.md` は User について次を定め、**何をログイン手段にでき、本人であることをどう確かめ、追加をどう成立させるかは規定していない。**

- User は**ログイン手段を 1 つ以上持ち**、後から追加・削除できる（最後の 1 つは削除できない）
- ログイン識別子は mmkn 全体で重複せず、**ログイン手段を増やしても変わらない**
- 1 つの外部アカウントは、同時に 2 人の User のログイン手段にならない

`adr/0003` は認証基盤に Supabase Auth を採ることまでを決めており、その上でどの方式を使うかが空いている。

制約は 3 つ。

- **mmkn は Discord に依存しない**（`overview.md`）。Discord は提供形態の 1 つであり、それを持たない人も Web だけで完結して使える必要がある
- 個人開発であり、認証まわりの画面と文言を自分で保守することになる（`overview.md`）
- **運用コストも無料枠に収める**（`overview.md`「前提」[確定]）

### 着手時の確認結果 [確定]

**既定のメール送信サービスでは、組織のチームに属さないアドレスにメールが届かない。** 確認日 2026-08-13。

- 既定の送信サービスは試用のためのもので、**本番向けではない**（"not meant for production use"）
- **カスタム SMTP を設定しない限り、プロジェクトのチームに属さないアドレスへの配信を拒否する**（"will refuse to deliver messages to addresses that are not part of the project's team"）
- 加えて時間あたりの送信数に上限があり、可用性はベストエフォート

初版はメールアドレスの確認を必須にし、パスワードの再設定もメール経由としていた。**その構成では利用者が 1 人も登録できなかった。** メールを送り続けるにはカスタム SMTP が要り、それは外部サービスを 1 つ増やすこと（無料枠に依存する対象が増え、送信ドメインの SPF / DKIM を自分で持つ）を意味する。

**この結果は今も生きている。** 下記の決定が「メールを送らない」を保っているのは、この確認があるためである。

### 2 版目を撤回した理由 [確定]

2 版目は Google 単独でログインし、Discord を**連携**（ログインには使えないが、Discord から届いた操作の主を解決するための対応）として別の役割に置いていた。**役割を 2 つ持つ必要が無かった。**

- **どちらも「外部サービスが本人であることを保証し、その結果から User を解決する」で、同じ仕組みで足りる。** 役割を 2 つに分けると、解除できるか・一覧に出るか・どちらの規則が効くかを取り違える設計を保守し続けることになる
- **Google 単独は 2 つの弱点を抱えていた。** Google アカウントを持たない人は使えず、そのアカウントを失うと User に二度と到達できなかった。**ログイン手段を複数持てる形にすると、この 2 つが同時に解ける**
- **Discord から入ってきた人の導線が 2 往復あった。** Web で Google のアカウントを作り、そのうえで Discord 連携の OAuth を踏む必要があった。ログイン手段なら 1 往復で済む
- Discord を唯一のログイン手段にする案は採らない。**`overview.md` の「mmkn は Discord に依存しない」に正面から当たる**

## 決定

**ログインを外部サービスの OAuth に委ね、1 User が複数のログイン手段を持てるようにする。** 実装は Supabase Auth の OAuth プロバイダと identity linking に乗せる。

- **mmkn はパスワードを持たない。** 強度・保管・照合・再設定のいずれも存在しない
- **mmkn はメールを送らない。** 確認メールも再設定メールも発生しないため、上記「着手時の確認結果」の制約が効かなくなる
- **当面のログイン手段は Google と Discord の 2 つ。** 増やせる形にしておき、増やすときにこの ADR を書き換える
- **ログイン識別子は、認証基盤が持つ user の識別子とする**（後述「provider が返す ID を識別子にしない理由」）
- **OAuth の認可コードフローを自前で実装しない。** ログインは OAuth プロバイダに、ログイン手段の追加は identity linking に委譲する
- **Discord に要求するスコープは `identify` にとどめ、メールを取得しない**（後述「自動統合に頼らない」）
- **アクセストークンを保存しない。** 必要なのは「この外部ユーザーの ID」という一度きりの事実だけで、外部サービスの API を代理で叩き続ける必要はない。保存しなければ漏洩も失効管理も発生しない
- **認証基盤のスキーマへの依存は、ポートの実装の中だけに閉じる。** ログイン手段の参照は認証基盤の内部テーブルを読む形になるため、リポジトリのポートを挟む（`adr/0004`）。将来スキーマが変わった場合や、自前の射影テーブルに切り替える場合も、実装の差し替えだけで済む
- **外部 ID からアプリの ID への変換は入口で閉じる**（`adr/0004`）。内側には mmkn の `UserId` だけを流す

`domain/group.md`「User と外部アカウント」が定めるログイン手段の規則を、この構成で実現する。**規則そのものはあちらを正とし、ここには持たない。**

### provider が返す ID を識別子にしない理由

ログインすると、その provider における一意な ID（OpenID Connect の `sub` にあたるもの）が得られる。**これを mmkn のログイン識別子にはしない。**

- **ログイン手段が複数になると、その ID は「どの入口から入ったか」でしかない。** User を一意に指せず、`domain/group.md` が要求する「ログイン手段を増やしても変わらない」を満たさない
- 認証基盤の user は、複数の identity をまとめた 1 つの単位であり、**ログイン手段を増やしても変わらない。** 要求にそのまま対応する

**メールアドレスも識別子に使わない。**

- **メールアドレスは変わる。** アカウントは同じままアドレスだけ変更でき、そのとき識別子が変わると別人になる
- 検証済みメールが一致する identity を自動統合する挙動を誘発する（次項）

### 自動統合に頼らない

認証基盤は「**検証済みメールが一致する identity を自動統合する**」挙動を持つ。

**ログイン手段の追加は、必ず本人の明示的な操作でだけ成立させる。** 自動統合は mmkn が意図しないタイミングで User の入口を増やし、`domain/group.md`「ログイン手段を追加する」の前提条件（ログイン済みであること）を通らない経路になる。

そのため **Discord から メールを取得しない**（スコープを `identify` にとどめる）。Google のログインでは検証済みのメールアドレスが必ず認証基盤に入るため、Discord 側でも同じアドレスを取得すると、自動統合が成立する条件がそろう。

### mmkn が Discord に依存しないこと

**ログイン手段はサービスをまたいで置き換えられる。** Discord が使えなくなっても、他のログイン手段を持つ User は影響を受けない。User の同一性は mmkn が持ち（`domain/group.md`）、ログイン手段は入口にすぎない。

**これは Discord に限らない。** Google についても同じで、どの 1 つのサービスも mmkn の前提にならない。

### 着手時に必ず確かめること

**この決定は、認証基盤の次の挙動に乗っている。**

| 確かめること | 外れたときの影響 |
|---|---|
| 同じ外部アカウントで再ログインしたとき、認証基盤が同じ user を返すか | 同じ人が毎回別の User になる |
| 認証基盤が保存する Discord のユーザー ID と、スラッシュコマンドで届くユーザー ID が同一か | Discord 側が丸ごと動かない |
| 最後の 1 つのログイン手段を削除しようとしたときに、認証基盤が拒むか | 拒まないなら mmkn 側で止める。`domain/group.md` の規則が実現方式に依存しない形になっているかの確認 |
| 認可画面をまたぐログイン手段の追加が実際に成立するか（自動化しないため手動。`adr/0010`） | ログイン手段を増やせない |

**間に認証基盤が 1 層挟まるため、基盤が保存する値の側で確かめる。** 手順は `docs/operations.md`「実装着手時に必ず確かめること」を正とする。

## 結果

- 良い点：
  - **「連携」という役割が消える。** 外部アカウントの扱いが 1 つの規則に収まり、解除できるかどうかを取り違える余地が無くなる
  - **1 つのサービスを失っても User に到達できる。** 2 版目が受け入れていた「アカウントを失うと二度と到達できない」が、手段を複数持つことで緩和される
  - **Discord から入ってきた人の導線が 1 往復になる。** Web で別のアカウントを作ってから連携する必要がない
  - **どの 1 つのサービスも mmkn の前提にならない**（`overview.md`）
  - メールを送る必要が無く、送信サービスも送信ドメインの設定も迷惑メール判定も関心事から外れる
  - パスワードを保管も照合もしないため、強度・漏洩対応・再設定の導線がまるごと存在しない
- 留意点：
  - **どのログイン手段も持たない人は mmkn を使えない。** 使えるサービスを増やすほど緩和されるが、ゼロにはならない
  - **すべてのログイン手段を失った利用者は、その User に二度と到達できない**（`domain/group.md`「境界・例外ケース」）。**複数持つよう促すのは画面の責務**であり、mmkn 側に復旧手段は無い
  - **ログインの可用性が外部サービスに依存する。** ある provider の障害中は、その手段でのログインだけが止まる（他の手段を持つ人は入れる）
  - 認証基盤が保存する値の形を自分で決められない（上記「着手時に必ず確かめること」）
  - **E2E から本物の OAuth を通せない。** その結果、E2E は認証基盤に繋がず偽の認証を使うことになった（`adr/0010`「E2E が使う認証基盤」）。**ここに挙げた「着手時に必ず確かめること」は、E2E があっても人が確かめる**

## 検討した代替案

- **メールアドレス + パスワード（初版の決定）**：Google アカウントを持たない人も使える。ただし**成立させるにはカスタム SMTP が要る**（上記「着手時の確認結果」）。外部サービスが 1 つ増え、送信ドメインの SPF / DKIM を自分で持ち、迷惑メール判定のリスクが残り、認証の画面を 4 枚保守することになる。撤回した。
- **Google 単独 + Discord は連携（2 版目の決定）**：`domain/group.md` の改訂が 1 度で済んだ。ただし役割が 2 つに分かれ、Google を持たない人が使えず、Discord から入る導線が 2 往復になった。撤回の詳細は上記「2 版目を撤回した理由」。
- **Discord 単独**：Discord から入ってきた人の導線が最短になり、実装も最小になる。ただし **Discord を持たない人が使えず、`overview.md` の「mmkn は Discord に依存しない」に正面から当たる。**
- **プロバイダごとに別の User を許す（ログイン手段は 1 User に 1 つのまま、選べるだけ）**：`domain/group.md` の改訂が小さく済む。ただし同じ人が別のプロバイダで入ると**別の User になり**、Member も記録も引き継がれない。利用者から見て事故にしか見えない。
- **Apple も使えるようにする**：利用者の選択肢が広がる。ただし Sign in with Apple を Web で使うには Services ID と秘密鍵の発行が要り、それには Apple Developer Program（年 $99）への加入が要る。`overview.md`「運用コストも無料枠に収める」[確定] に当たる。**無料で足せる provider から先に足す。**
- **パスキー**：スマホ前提（`overview.md`）では体験が最も良く、送信の問題も消える。ただし機種変更・端末紛失時の復旧経路を自分で設計することになり、個人開発の最初の版で背負う量ではない。**ログイン手段の 1 つとして後から足せるため、この ADR を覆さずに追加できる。**
- **認可コードフローを自前で実装する（PoC の実装）**：保存される値を自分で決められるため、上の「着手時に必ず確かめること」のリスクが消える。ただしセッション管理を Supabase Auth に寄せる方針（`adr/0003`）とは別経路になり、セッションの発行元が 2 つある状態を保守することになる。
- **ワンタイムの連携コードを人が運ぶ（PoC 初期の実装）**：Web と外部サービスのどちら側からでも開始できる。ただし「コードを知っている人 = 本人」という仮定に乗り、コードが漏れれば第三者が自分のアカウントを紐付けられる。有効期限と 1 回限りの消費は緩和策にすぎず、仮定は消せない。**OAuth にはこの経路が存在しない。**
- **外部サービスのユーザー ID を本人に入力させる**：実装は最小だが、他人の ID を入力すればそのまま他人になりすませる。検討に値しない。
