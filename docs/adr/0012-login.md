# ADR-0012: mmkn のログインをメールアドレスとパスワードで行う

- ステータス: **見直し中 [保留]** — 着手時の確認（下記「着手時の確認結果」）で**前提が外れた**。識別子と認証手段の決定（メールアドレス + パスワード）は有効なまま、それを成立させる**メール送信の手当てが決まっていない**
- 関連: `docs/domain/group.md`, `docs/features.md`, `adr/0003-tech-stack.md`, `adr/0007-external-account-linking.md`

## コンテキスト

`domain/group.md` は User について「ログイン識別子を 1 つ持ち、mmkn 全体で重複しない」「本人であることが確かめられること」までを定め、**何を識別子とし、どう確かめるかは規定していない**。`adr/0003` は認証基盤に Supabase Auth を採ることまでを決めており、その上でどの方式を使うかが空いている。

制約は 3 つ。

- **外部サービスのアカウントをログイン手段にはできない**（`domain/group.md`）。Discord アカウントを失っても mmkn の User に到達できる状態を保つと決めている
- **Discord から入ってきた人も、まず Web でアカウントを作る必要がある**（`adr/0007`）。ここが詰まると Discord しか使わない人が入口で止まる
- 個人開発であり、認証まわりの画面と文言を自分で保守することになる（`overview.md`）

## 決定

**ログイン識別子はメールアドレスとし、パスワードと組で認証する。** 実装は Supabase Auth のメール + パスワードに委譲する。

- メールアドレスは mmkn 全体で重複しない。既に使われているアドレスでのアカウント作成は失敗する（`domain/group.md`「アカウントを作成する」）
- **パスワードの強度・保管・照合を自前で実装しない。** 認証基盤に委ねる
- **メールアドレスの確認（verification）を必須にする。** 未確認のアドレスでアカウントを作れる状態にしない。パスワードの再設定がメールに依存する以上、到達しないアドレスで登録できると復旧できない User が生まれる
- **パスワードの再設定はメール経由で行う。** 再設定の導線を持たないと、パスワードを忘れた時点で User に到達できなくなる
- メールアドレスの変更は**持たない**。必要になった時点でこの ADR を見直す

### 外部アカウント連携との関係

`adr/0007` は Discord の OAuth で要求するスコープを `identify` にとどめ、**メールを取得しない**と決めている。理由は「検証済みメールが一致する identity を自動統合する」挙動を誘発するためであり、**この ADR でメール + パスワードを採ったことでその危険が現実のものになる**。

- Discord から取得したメールで User を自動的に結びつけることはしない
- 連携は常に `adr/0007` の経路（ログイン済みの Web から OAuth）だけで成立する

### 着手時の確認結果 [確定]

**既定のメール送信サービスでは、組織のチームに属さないアドレスにメールが届かない。** 確認日 2026-08-13。

認証基盤側の記述は次のとおり。

- 既定の送信サービスは試用のためのもので、**本番向けではない**（"not meant for production use"）
- **カスタム SMTP を設定しない限り、プロジェクトのチームに属さないアドレスへの配信を拒否する**（"will refuse to deliver messages to addresses that are not part of the project's team"）
- 加えて時間あたりの送信数に上限があり、可用性はベストエフォート

この ADR の留意点は「迷惑メール判定を含めて、届くかどうか」を心配していた。**実際はその手前で、送信自体が行われない。**

影響はこの ADR の中心にある 2 つの決定に直接あたる。

| この ADR の決定 | 既定の送信サービスでの状態 |
|---|---|
| メールアドレスの確認を必須にする | **チーム外の人はアカウントを作れない**（確認メールが届かないため） |
| パスワードの再設定はメール経由で行う | **チーム外の人はパスワードを忘れると復旧できない** |

つまり、この構成のままでは利用者が 1 人も登録できない。**カスタム SMTP を用意するまで、この ADR の決定は成立しない。** それは外部サービスを 1 つ増やすことであり、`overview.md`「前提」（運用コストも無料枠に収める）に触れる。どう手当てするかは未決 #15。

## 結果

- 良い点：
  - 再訪時にメールを開く必要がなく、`adr/0007` が留意点に挙げた「Discord から入ってきた人が Web で詰まる」導線を最も短くできる
  - 認証基盤の標準機能に収まり、パスワードの保管と照合を自分で持たない
  - `domain/group.md` が要求する「重複しない識別子」がメールアドレスの一意性でそのまま満たされる
- 留意点：
  - **パスワード再設定の画面と文言を自分で保守することになる。** ログイン・登録・再設定要求・再設定実行で 4 画面
  - **メールが届くかどうかに、アカウント作成と復旧の両方が依存する。** 送信元の設定（迷惑メール判定を含む）は着手時に実物で確かめる（`docs/operations.md`）。**2026-08-13 に確認し、既定の送信サービスでは届かないことが分かった**（上記「着手時の確認結果」）
  - 認証基盤が既定で用意する画面ではなく mmkn の画面から呼ぶため、失敗の表し方を `adr/0009` のビューモデルに載せる必要がある
  - `adr/0007` が禁じたメールスコープの取得を、後から「便利だから」と有効にすると意図しないアカウント統合が起きる。**この ADR がその危険を増やしている**ことを覚えておく

## 検討した代替案

- **メールのマジックリンク**：パスワードを持たないため、強度・再設定・漏洩対応がまるごと不要になり、保守する画面も減る。ただし**ログインのたびにメールを開く**ことになり、`adr/0007` が留意点に挙げた「Discord から入ってきた人が Web でアカウントを作る」導線の摩擦がそのまま増える。その場限りのイベントで数分だけ使う場面（`overview.md` のターゲット）で、毎回メールアプリを往復させる形は取りたくない。
- **パスキー**：スマホ前提（`overview.md`）では体験が最も良く、パスワードの問題が根本から消える。ただし機種変更・端末紛失時の復旧経路を自分で設計することになり、認証基盤側の対応状況も確かめる必要がある。個人開発の最初の版で背負う量ではない。将来、メール + パスワードに**足す**形なら矛盾しないため、この ADR を覆さずに追加できる。
- **メールのマジックリンクとパスワードの両方を用意する**：どちらでも入れる。ただし導線と検証の対象が 2 つになり、`adr/0009` のフォームも 2 系統になる。片方で足りる。
- **Discord をログイン手段そのものにする**：Discord から入ってきた人が Web でアカウントを作らずに済む。ただし `domain/group.md` が「User は mmkn 自身のアカウントとして成立する」と定めており、ドメインの決定と正面から衝突する（`adr/0007` で既に退けた案）。
- **ログイン識別子をメール以外（ユーザー名など）にする**：メールを持たない人でも使える。ただしパスワードを忘れたときの復旧手段が消え、本人であることを確かめる経路が他に無い。
