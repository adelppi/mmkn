# ADR-0012: mmkn のログインを Google アカウントで行う

- ステータス: 採用 [確定] — 2026-08-13 改訂。**ログイン識別子をメールアドレスとし、パスワードと組で認証するとした 2026-08-12 の決定は撤回した**（下記「着手時の確認結果」で前提が外れたため）
- 関連: `docs/domain/group.md`, `docs/features.md`, `docs/overview.md`, `adr/0003-tech-stack.md`, `adr/0007-external-account-linking.md`

## コンテキスト

`domain/group.md` は User について「ログイン識別子を 1 つ持ち、mmkn 全体で重複しない」「本人であることが確かめられること」までを定め、**何を識別子とし、どう確かめるかは規定していない**。`adr/0003` は認証基盤に Supabase Auth を採ることまでを決めており、その上でどの方式を使うかが空いている。

制約は 3 つ。

- **Discord から入ってきた人も、まず Web でアカウントを作る必要がある**（`adr/0007`）。ここが詰まると Discord しか使わない人が入口で止まる
- 個人開発であり、認証まわりの画面と文言を自分で保守することになる（`overview.md`）
- **運用コストも無料枠に収める**（`overview.md`「前提」[確定]）

初版はここでメールアドレス + パスワードを採った。**その決定は、着手時の確認で前提が外れて成立しなくなった。**

### 着手時の確認結果 [確定]

**既定のメール送信サービスでは、組織のチームに属さないアドレスにメールが届かない。** 確認日 2026-08-13。

認証基盤側の記述は次のとおり。

- 既定の送信サービスは試用のためのもので、**本番向けではない**（"not meant for production use"）
- **カスタム SMTP を設定しない限り、プロジェクトのチームに属さないアドレスへの配信を拒否する**（"will refuse to deliver messages to addresses that are not part of the project's team"）
- 加えて時間あたりの送信数に上限があり、可用性はベストエフォート

初版の留意点は「迷惑メール判定を含めて、届くかどうか」を心配していた。**実際はその手前で、送信自体が行われない。**

影響は初版の中心にある 2 つの決定に直接あたっていた。

| 初版の決定 | 既定の送信サービスでの状態 |
|---|---|
| メールアドレスの確認を必須にする | **チーム外の人はアカウントを作れない**（確認メールが届かないため） |
| パスワードの再設定はメール経由で行う | **チーム外の人はパスワードを忘れると復旧できない** |

つまり、その構成のままでは利用者が 1 人も登録できなかった。**メールを送り続けるにはカスタム SMTP が要り、それは外部サービスを 1 つ増やすこと**（無料枠に依存する対象が増え、送信ドメインの SPF / DKIM を自分で持つ）を意味する。

## 決定

**ログインを Google アカウントで行う。** 認証は Google の OAuth に委譲し、実装は Supabase Auth の OAuth プロバイダに乗せる。

- **ログイン識別子は、Google が返す一意な ID**（OpenID Connect の `sub`）とする。**メールアドレスは識別子に使わない**（後述「メールアドレスを識別子にしない理由」）
- **mmkn はパスワードを持たない。** 強度・保管・照合・再設定のいずれも存在しない
- **mmkn はメールを送らない。** 確認メールも再設定メールも発生しないため、上記「着手時の確認結果」の制約が効かなくなる
- **ログインに使えるサービスは Google 1 つに絞る**（後述「プロバイダを増やさない理由」）

`domain/group.md` は、これを受けて**ログインに使う外部アカウントと、連携する外部アカウントを別の役割として定めた**（「User と外部アカウント」）。解除の可否・失ったときに何が起きるかは、その文書を正とする。**この ADR はそれを Google の OAuth で実現する側だけを持つ。**

### ドメインの決定を改訂したこと

**初版まで `domain/group.md` は「外部サービスのアカウントを、ログイン手段そのものにはしない」と定めていた。** この ADR の採用にあたり、その決定を改訂した。**ADR がドメインを覆したのではなく、ドメインの側を先に改訂したうえで、この ADR がその実現を担う**（`RULES.md` §3）。

改訂の根拠は 2 つ。

- **元の決定の根拠が、Google に対しては当たらない。** 「Discord アカウントを失っても mmkn の User に到達できる状態を保つ」が理由だったが、Google アカウントは Discord アカウントより失われにくく、プロバイダ側に復旧手段がある
- **メール + パスワードの耐久性は、見た目ほど高くない。** 再設定がメールに依存する以上、そちらもメールアドレスの生存に依存している。Google アカウントを失う人は、その Gmail も同時に失う

**ただし「失ったら到達できない」こと自体は消えていない。** これは受け入れた代償であり、`domain/group.md`「境界・例外ケース」に明記した。

### メールアドレスを識別子にしない理由

Google はメールアドレスも返すため、それを識別子にすることもできる。**採らない。**

- **メールアドレスは変わる。** Google アカウントは同じままアドレスだけ変更でき、そのとき識別子が変わると別人になる。`sub` は変わらない
- **検証済みメールが一致する identity を自動統合する挙動を誘発する**（`adr/0007`）。識別子として持つと、その挙動に依存した設計になる

### プロバイダを増やさない理由

- **Apple は無料枠の前提と衝突する。** Sign in with Apple を Web で使うには Services ID と秘密鍵の発行が要り、それには Apple Developer Program（年 $99）への加入が要る。`overview.md`「運用コストも無料枠に収める」[確定] に正面からあたる。**メール送信サービスを避けた理由が、そのまま戻ってくる**
- **プロバイダが 2 つ以上あると「同じ人が 2 つの User」が起きる。** 別々のプロバイダで登録すれば別の識別子になる。認証基盤は検証済みメールの一致で自動統合するが、Apple の Hide My Email はリレーアドレスを返すため一致せず、統合されない。しかも `adr/0007` はその自動統合そのものを**危険として避けている**。頼るのも避けるのも設計が要る
- **Discord をログインにも使うのは採らない。** 利用者が Discord から入ってくるとは限らず（`overview.md` は Web を主の提供形態としている）、Discord アカウントは Google アカウントより失われやすい。Discord は連携の役割のまま置く（`adr/0007`）

### 外部アカウント連携との関係

`adr/0007` は Discord の OAuth で要求するスコープを `identify` にとどめ、**メールを取得しない**と決めている。理由は「検証済みメールが一致する identity を自動統合する」挙動を誘発するためである。

**この決定によって、その禁止はより重要になった。** Google のログインでは検証済みのメールアドレスが必ず認証基盤に入るため、Discord 側でも同じアドレスを取得すると、**自動統合が成立する条件がそろう**。

- Discord のスコープは `identify` のまま。**メールを取りに行かない**
- 連携は常に `adr/0007` の経路（ログイン済みの Web から OAuth）だけで成立する

### 着手時に必ず確かめること

**この決定は「Google が返す一意な ID が、再ログインしても同じ値である」前提に乗っている。** 変われば、同じ人が毎回別の User になる。

`adr/0007` が Discord のユーザー ID について同じ確認を要求しているのと同じ理由であり、**間に認証基盤が 1 層挟まるため、基盤が保存する値の側で確かめる**。実アカウント 1 件で 2 回ログインすれば済む。

## 結果

- 良い点：
  - **メールを送る必要が消える。** 送信サービスも、送信ドメインの設定も、迷惑メール判定も、この決定の関心事から外れる
  - **外部サービスを増やさずに済む。** カスタム SMTP を入れる案が触れていた `overview.md`「無料枠に収める」に、この決定は触れない
  - **保守する画面が 4 枚から 1 枚に減る。** ログイン・登録・再設定要求・再設定実行のうち、残るのは実質ログインだけになる
  - パスワードを保管も照合もしないため、強度・漏洩対応・再設定の導線がまるごと存在しない
  - `domain/group.md` が要求する「重複しない識別子」を、Google の `sub` の一意性がそのまま満たす
- 留意点：
  - **Google アカウントを失った利用者は、その User に二度と到達できない。** mmkn 側に復旧手段は無い（`domain/group.md`「境界・例外ケース」）
  - **Google アカウントを持たない人は mmkn を使えない。** 初版のメール + パスワードには無かった制約である
  - **ログインの可用性が Google に依存する。** Google の障害中は誰もログインできない
  - E2E から本物の Google ログインを通すのは容易でない。**未決 #14（E2E が使う認証基盤）の難度が上がった**
  - 認証基盤が保存する値の形を自分で決められない（上記「着手時に必ず確かめること」）

## 検討した代替案

- **メールアドレス + パスワード（初版の決定）**：`domain/group.md` を改訂せずに済み、Google アカウントを持たない人も使える。ただし**成立させるにはカスタム SMTP が要る**（上記「着手時の確認結果」）。外部サービスが 1 つ増え、送信ドメインの SPF / DKIM を自分で持ち、迷惑メール判定のリスクが残り、認証の画面を 4 枚保守することになる。撤回した。
- **メール確認を必須にするのをやめる**：設定 1 つで登録はできるようになる。ただし再設定メールも届かないため、**パスワードを忘れた全員が復旧できなくなる**。単独では成立しない。
- **メールのマジックリンク**：パスワードの問題が消える。ただし**送信の問題は消えない**。この ADR が外そうとしている依存そのものに、より強く依存する形になる。
- **パスキー**：スマホ前提（`overview.md`）では体験が最も良く、送信の問題も消える。ただし機種変更・端末紛失時の復旧経路を自分で設計することになり、個人開発の最初の版で背負う量ではない。**将来 Google ログインに足す形なら矛盾しない**ため、この ADR を覆さずに追加できる。
- **Google に加えて Apple も使えるようにする**：利用者の選択肢が広がる。ただし Apple Developer Program の費用と「同じ人が 2 つの User」の両方を抱える（上記「プロバイダを増やさない理由」）。
- **Discord をログイン手段そのものにする**：Discord から入ってきた人が最も短い導線で入れる。ただし Web を主の提供形態とする `overview.md` と噛み合わず、Discord アカウントは失われやすい。連携の役割のまま置く。
