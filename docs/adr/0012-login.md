# ADR-0012: ログインを Discord の OAuth だけに委ねる

- ステータス: 採用 [確定] — 2026-11-24 改訂（3 度目）
- 関連: `docs/domain/group.md`, `docs/features.md`, `docs/overview.md`, `adr/0003-tech-stack.md`, `adr/0007-external-account-linking.md`（廃止）, `adr/0008-layer-internals.md`, `adr/0017-web-only.md`

**この ADR は 3 度改訂している。** 撤回した決定と理由は次のとおり。

| 版 | 決定 | 撤回の理由 |
|---|---|---|
| 2026-08-12 | メールアドレス + パスワード | 既定のメール送信サービスがチーム外に配信しない（下記「着手時の確認結果」） |
| 2026-08-13 | **Google 単独**でログインし、Discord は**連携**として別の役割に置く | 役割を 2 つ持つ必要が無かった |
| 2026-08-14 | **Google と Discord の 2 つ**をログイン手段とし、1 User が複数持てるようにする | 使われないまま、保守する対象だけが残った（下記「3 版目を撤回した理由」） |

## コンテキスト

`domain/group.md` は User について次を定め、**何をログイン手段にでき、本人であることをどう確かめるかは規定していない。**

- ログイン識別子は mmkn 全体で重複せず、変わらない
- 1 つの外部アカウントは、同時に 2 人の User のログイン手段にならない

`adr/0003` は認証基盤に Supabase Auth を採ることまでを決めており、その上でどの方式を使うかが空いている。

制約は 2 つ。

- 個人開発であり、認証まわりの画面と文言を自分で保守することになる（`overview.md`）
- **運用コストも無料枠に収める**（`overview.md`「前提」[確定]）

### 着手時の確認結果 [確定]

**既定のメール送信サービスでは、組織のチームに属さないアドレスにメールが届かない。** 確認日 2026-08-13。

- 既定の送信サービスは試用のためのもので、**本番向けではない**（"not meant for production use"）
- **カスタム SMTP を設定しない限り、プロジェクトのチームに属さないアドレスへの配信を拒否する**（"will refuse to deliver messages to addresses that are not part of the project's team"）
- 加えて時間あたりの送信数に上限があり、可用性はベストエフォート

**この結果は今も生きている。** 下記の決定が「メールを送らない」を保っているのは、この確認があるためである。

### 3 版目を撤回した理由 [確定]

- **既存の利用者は全員 Discord でログインしている**（`adr/0017`）。Google を選べることも、2 つ目を追加できることも使われていなかった
- **複数持てることの代償が、得られるものに見合わなかった。** 一覧・追加・削除のために認証基盤の内部テーブルを直接読み、追加が認められなかったときの後始末を持ち、認可画面をまたぐため自動テストもできない経路を抱えていた
- **内部テーブルを読むもう 1 つの理由（外部サービスから届いた操作の主の解決）は、Discord クライアントの廃止で無くなった**（`adr/0017`）

## 決定

**ログインを Discord の OAuth だけに委ねる。** 実装は Supabase Auth の OAuth プロバイダに乗せる。

- **ログイン手段の追加・削除を持たない。** identity linking を使わず、認証基盤の `auth.identities` を読む経路も持たない
- **mmkn はパスワードを持たない。** 強度・保管・照合・再設定のいずれも存在しない
- **mmkn はメールを送らない。** 確認メールも再設定メールも発生しないため、上記「着手時の確認結果」の制約が効かなくなる
- **ログイン識別子は、認証基盤が持つ user の識別子とする**（後述「provider が返す ID を識別子にしない理由」）。3 版目から変えていない
- **OAuth の認可コードフローを自前で実装しない**
- **アクセストークンを保存しない。** 必要なのは「この外部ユーザーである」という一度きりの事実だけで、外部サービスの API を代理で叩き続ける必要はない。保存しなければ漏洩も失効管理も発生しない
- **外部 ID からアプリの ID への変換は入口で閉じる**（`adr/0004`）。内側には mmkn の `UserId` だけを流す

### provider が返す ID を識別子にしない理由

ログインすると、その provider における一意な ID が得られる。**これを mmkn のログイン識別子にはしない。**

- **その ID は「どの入口から入ったか」でしかない。** 将来サービスを替えるときに識別子ごと変わり、`domain/group.md` が要求する「変わらない」を満たさない
- 認証基盤の user は、入口が替わっても変わらない単位であり、要求にそのまま対応する

**メールアドレスも識別子に使わない。** アカウントは同じままアドレスだけ変更でき、そのとき識別子が変わると別人になる。

### Discord に要求するスコープ

**mmkn からはスコープを渡さない。** 認証基盤は Discord に対して常に `email` と `identify` を要求し、渡したスコープはそれに足されるだけである。**減らす手段が無いため、Discord のメールアドレスは認証基盤に入る。** mmkn はそれを読まず、何にも使わない。

3 版目は「`identify` だけを渡せばメールを取得しない」としていたが、実態と合っていなかった。

### 自動統合

認証基盤は「**検証済みメールが一致する identity を自動統合する**」挙動を持つ。メールの取得を避けられない以上、スコープでは防げない。

**代わりに、有効なプロバイダを Discord だけにする**（認証基盤の設定。手順は `docs/operations.md`「認証基盤のプロバイダ」）。異なるサービスの間での統合は、相手が無いため起きない。

### 着手時に必ず確かめること

| 確かめること | 外れたときの影響 |
|---|---|
| 同じ外部アカウントで再ログインしたとき、認証基盤が同じ user を返すか | 同じ人が毎回別の User になる |

**間に認証基盤が 1 層挟まるため、基盤が保存する値の側で確かめる。** 手順は `docs/operations.md`「実装着手時に必ず確かめること」を正とする。

## 結果

- 良い点：
  - 認証基盤の内部テーブルへの依存が無くなる
  - 認可画面をまたぐ往復がログインの 1 種類になり、人が確かめる対象が減る
  - メールを送る必要が無く、送信サービスも送信ドメインの設定も迷惑メール判定も関心事から外れる
  - パスワードを保管も照合もしないため、強度・漏洩対応・再設定の導線がまるごと存在しない
- 留意点：
  - **Discord のアカウントを持たない人は mmkn を使えない**
  - **Discord のアカウントを失った利用者は、その User に二度と到達できない**（`domain/group.md`「境界・例外ケース」）。mmkn 側に復旧手段は無い
  - **Discord の障害中は、新しくログインできない**
  - **同じメールアドレスの持ち主が Discord 側で入れ替わると、自動統合の条件がそろい得る。** プロバイダを 1 つに絞っても、これは防げない
  - 認証基盤が保存する値の形を自分で決められない（上記「着手時に必ず確かめること」）
  - **E2E から本物の OAuth を通せない。** E2E は偽の認証を使う（`adr/0010`「E2E が使う認証基盤」）

## 検討した代替案

- **Google と Discord の 2 つを、複数持てる形で残す（3 版目の決定）**：Discord を持たない人も使え、1 つを失っても到達できる。ただし使われないまま保守する対象だけが残っていた（上記「3 版目を撤回した理由」）。
- **2 つから選べるが、1 User に 1 つとする**：内部テーブルを読まずに済む。ただし同じ人が別のサービスで入ると**別の User になり**、Member も記録も引き継がれない。
- **Google 単独**：アカウントを持つ人は多い。ただし既存の利用者が自分の User に到達できなくなる。
- **メールアドレス + パスワード（初版の決定）**：外部サービスのアカウントが要らない。ただし成立させるにはカスタム SMTP が要り（上記「着手時の確認結果」）、外部サービスが 1 つ増え、認証の画面を 4 枚保守することになる。
- **Apple**：Services ID と秘密鍵の発行に Apple Developer Program（年 $99）への加入が要り、無料枠の前提に当たる。
- **パスキー**：スマホ前提（`overview.md`）では体験が最も良い。ただし機種変更・端末紛失時の復旧経路を自分で設計することになり、個人開発で背負う量ではない。
- **認可コードフローを自前で実装する（PoC の実装）**：保存される値を自分で決められる。ただしセッション管理を Supabase Auth に寄せる方針（`adr/0003`）とは別経路になり、セッションの発行元が 2 つある状態を保守することになる。
- **外部サービスのユーザー ID を本人に入力させる**：他人の ID を入力すればそのまま他人になりすませる。検討に値しない。
