# ADR-0013: 通貨の一覧と最小単位を、公表データから生成した表としてドメイン層に持つ

- ステータス: **廃止（superseded by `adr/0016-currency-table-committed.md`）** — 2026-08-13
- 関連: `docs/domain/money.md`, `docs/operations.md`, `adr/0004-layers-and-dependencies.md`, `adr/0008-layer-internals.md`, `adr/0010-testing.md`, `adr/0011-ci-and-release.md`, `adr/0016-currency-table-committed.md`

> **この ADR はもう有効な決定ではない。** 通貨表の持ち方と追随のさせ方の正は `adr/0016` である。
>
> 覆されたのは **「生成器を持つ」と「週次の定期実行で追随する」** の 2 点で、`adr/0016` はそのどちらも持たない。撤回の理由は `adr/0016`「なぜ撤回するか」を正とする。
>
> **この文書を残すのは、生成器を書く場合に必要な事情がここにしか無いためである。** 「取得元の形」（維持機関が現行と廃止済みの一覧を XML で配っていること、エントリが国単位で通貨コードが重複すること）と「検討した代替案」（`Intl`・ライブラリ・DB・使う通貨だけの列挙）は、`adr/0016` が再掲せずここを参照している。**`adr/0016`「この決定を見直す契機」に達したときは、まずここを読む。**

## コンテキスト

`domain/money.md` は次を確定させている。

- 扱う通貨は **ISO 4217 の現行通貨**。通貨コードと最小単位の桁数は ISO 4217 に従う
- **最小単位の桁数を mmkn 側で独自に決めることはしない**
- 金額は「整数 + 通貨」で持つ（上限は `domain/money.md`「金額の上限」）
- 一度扱った通貨とその桁数は、ISO 4217 からの削除によって失われない（`domain/money.md`「廃止された通貨」）

つまり「どの通貨が存在するか」と「その通貨の最小単位が何桁か」を、実装が**どこかから得る必要がある**。ここが決まっていないと、金額の解釈そのものが実装ごとにぶれる。

制約は 3 つ。

- **この判定はドメイン層で要る。** 金額の妥当性（整数であること・上限）と負担額の配分（`domain/record.md`）が最小単位を前提にしている。`adr/0004` はドメイン層の依存先を「なし（言語標準のみ）」と定め、機械検査で外部パッケージと `node:*` を禁止している
- **同じ入力が常に同じ結果になる必要がある。** `adr/0010` はクライアント間で結果が一致することをテストで固定すると決めている
- **ISO 4217 の改定に、人が気づかなくても追随できる必要がある。** 気づく契機を人の記憶に置くと、放置されたことにも気づけない

## 決定

**ISO 4217 の公表データから表を生成し、生成物をドメイン層にコミットする。生成は実行時ではなくリポジトリ側で行う。**

### 表そのもの

- 置き場は `src/domain/money/`（`adr/0008` のツリー）。**プレーンな TypeScript のリテラルであり、外部パッケージも `node:*` も参照しない**。ドメイン層の依存はゼロのまま（`adr/0004` の機械検査にそのまま通る）
- 生成物は**コミットする。** 実行時にも、ビルド時にも取得しない。手元・CI・本番のどこで動かしても同じ表を読む
- 表に無い通貨コードは受け付けない。**「知らない通貨は最小単位 2 桁とみなす」といった既定値を置かない**
- **生成物を手で編集しない。** 直すべきは生成器のほう。ファイルの先頭に、生成物であることと取得元を書く

### 生成器

- 置き場は `scripts/`。**`src/` の外に置く**（`adr/0008` のツリーと import 規則）。ドメイン層にネットワークやパーサへの依存を持ち込まないため、生成器の依存はドメイン層の検査対象に一切入らない
- 取得元は **ISO 4217 の維持機関が公表している現行通貨の一覧**（通貨コードと minor unit）。**URL は生成器の中に 1 か所だけ書く**
- 出力が既存のコミット済みファイルと一致するかを、生成器自身が判定できるようにする（差分の有無を終了コードで返す）

#### 取得元の形 [確定]

**着手時に確認した**（2026-08-12。手順は `docs/operations.md`）。維持機関は**現行の一覧と廃止済みの一覧を、それぞれ XML で配っている。** どちらもルート要素に発行日の属性を持つ。機械的に読める形で公開されており、この ADR の追随の仕組みは成立する。

**廃止済みの一覧が別に配られているため、「行を消さず廃止の印を立てる」（下記「廃止された通貨の表し方」）はこの一覧から作れる。** コミット済みの表と突き合わせて印を立てる形になり、桁数を推測する必要はない。

生成器が扱わなければならない、取得元の形に由来する事情が 3 つある。**いずれも生成器の実装（別 Issue）で処理する。**

| 事情 | 生成器がすること |
|---|---|
| **エントリが国単位であり、通貨コードが重複する**（現行の一覧は 280 エントリで、通貨コードは 178 種） | 通貨コードで畳む。同じコードのエントリは桁数も一致する |
| **通貨コードを持たないエントリがある**（通用する通貨が無い地域。現行の一覧に 3 件） | 落とす |
| **最小単位が数値でないエントリがある**（`N.A.`。現行の一覧に 13 件。貴金属・特別引出権・テスト用のコードなど） | 下記のとおり、扱いが未決 |

**最小単位を持たないコードを表に入れるかは未決**（`open-questions.md` #13）。`domain/money.md` は「扱う通貨は ISO 4217 の現行通貨」「最小単位の桁数も ISO 4217 に従う」と定めているが、これらのコードには従うべき桁数が存在しない。この ADR は「既定値を置かない」（上記）と決めているため、**桁数を 2 と仮定して入れることはしない。** ドメインの決定を待つ。

> **決着済み（2026-08-13）。扱わない**（表に入れない）。正は `domain/money.md`「扱う通貨」。この決着は、この ADR の廃止とは独立に有効である。

### 追随の仕方

**生成器を定期実行し、差分があれば PR を作る。** 周期・走らせ方・自動マージしないことは `adr/0011` を正とする。

この ADR が要求するのは次の 2 点だけである。

- **追随の契機を人の記憶に置かない。** 改定に気づくことを手順に頼ると、数年後にはその手順の存在ごと忘れられている
- **取得の失敗がアプリに波及しない。** 取得できない間は既にコミットされた表がそのまま使われ、動きは何も変わらない

### 廃止された通貨の表し方

削除をそのまま表に当てると、過去の記録が「知らない通貨」になる。`domain/money.md`「廃止された通貨」がその振る舞いを定めているため、表の側はそれを満たす形にする。

- **生成器は行を消さない。** 公表データから消えた通貨は、表から削除するのではなく**廃止の印を立てる**。**桁数はコミット済みの値をそのまま残す**（削除後の公表データには桁数が無いため、ここで消すと過去の金額の解釈が失われる）
- **印は表が持つ 1 つの値でしかない。** 現行と廃止のどちらをいつ出すかを決めるのはドメイン層であり、表はその判断材料を渡すだけ
- 結果として、生成の差分に現れるのは「印が立った」ことだけになる。**行が消える差分は出ない**

削除の差分は依然として人のレビューを通る（自動マージしない。`adr/0011`）が、**マージを止める理由ではなくなった。** 印が立つだけで、既存の記録は何も変わらない。

## 結果

- 良い点：
  - ドメイン層が依存をまったく持たないまま、金額の解釈を完結できる（`adr/0004` の機械検査にそのまま通る）
  - Web と Discord、手元と本番で結果が一致する。実行環境のバージョン差で通貨の一覧や桁数が変わる経路が存在しない
  - テストが決定的になる。「この環境ではこの通貨が無い」という形の失敗が起きない
  - **改定に気づく契機が人の記憶から外れる。** 差分は PR として出るため、放置されていることも見て分かる
  - 値の由来が生成器の取得元として 1 か所に明示され、「どこから写したか」がレビューの争点にならなくなる
- 留意点：
  - **生成器そのものを保守することになる。** 公表データの URL や形式が変われば、定期実行が失敗して気づく形になる
  - **表は数百行の生成物としてリポジトリに残る。** 差分は自動生成の PR でしか動かないため、手で読むのは差分だけでよい
  - 表に無い通貨を弾く以上、**新設された通貨は生成の PR がマージされるまで使えない**。エラーとして出るため気づけるが、その場では回避できない
  - **定期実行は放っておくと通知されない**（`adr/0014` のとおり監視サービスを持たない）。失敗もマージ待ちも、GitHub 上で見に行くまで分からない

## 検討した代替案

- **公表データを手で書き写す**（初版の決定）：仕組みが何も要らず、生成器も定期実行も持たなくてよい。ただし ISO 4217 の改定に**人が気づいて手を動かすこと**が追随の唯一の契機になる。改定は数年に一度であり、そのころには手順の存在自体が忘れられている。生成物が同じである以上、実行時の性質は何も変わらないため、手作業を残す利点が無い。撤回した。
- **言語標準の `Intl` から得る（`Intl.supportedValuesOf('currency')` と `Intl.NumberFormat`）**：依存が増えず、言語標準なのでドメイン層でも使え、改定への追随も実行環境の更新に乗る。ただし内実は CLDR であり **ISO 4217 と完全には一致しない**うえ、**実行環境のバージョンで一覧が変わり得る**。`domain/money.md` が「ISO 4217 に従う」と明記している以上、CLDR の内容がそのまま仕様になる状態は取れない。手元と本番でランタイムが違えば結果が変わる可能性も、`adr/0010` の「結果の一致で守る」方針と相性が悪い。**追随は自動になるが、追随先が仕様と違う。**
- **通貨データのライブラリを入れる**：一覧と桁数が固定され、改定への追随もライブラリの更新に乗る。ただし `adr/0004` がドメイン層の外部パッケージを機械検査で禁止しているため、インフラ層から値を渡す形になる。**金額の妥当性判定というドメインの中心的な処理が、外から注入された表に依存する**構造になり、ポートが 1 つ増える。採用案は生成の時点でだけ外部を触るため、この構造上の代償を払わずに追随を自動化できる。
- **ビルド時に取得して生成する（生成物をコミットしない）**：リポジトリに生成物が残らない。ただしビルドがネットワークに依存し、取得元が落ちていればデプロイできなくなる。表が変わったことに誰も気づかないまま本番の挙動が変わる経路も生まれる。
- **DB のテーブルとして持つ**：管理画面から更新できる。ただし通貨の一覧は業務データではなく仕様であり、環境ごとに中身が違い得る状態を作る。ドメイン層が DB を知らない構造（`adr/0004`）とも衝突する。
- **使う通貨だけを列挙する（JPY・USD・EUR など数種類）**：表が小さく保守が軽い。ただし `domain/money.md` が「ISO 4217 の現行通貨」「特定の通貨を優遇しない」と確定させており、ドメインの決定を実装の都合で狭めることになる。海外旅行で使う通貨は事前に列挙できない。
