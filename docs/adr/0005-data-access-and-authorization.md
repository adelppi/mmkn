# ADR-0005: データアクセスは `DATABASE_URL` 経由で行い、認可の正本をドメイン層に置く

- ステータス: 採用 [確定]
- 関連: `docs/domain/group.md`, `docs/domain/record.md`, `adr/0003-tech-stack.md`, `adr/0004-layers-and-dependencies.md`, `adr/0008-layer-internals.md`, `adr/0010-testing.md`, `adr/0011-ci-and-release.md`

## コンテキスト

`domain/group.md` と `domain/record.md` は、操作の前提条件を「操作する User が、その Group の Member であること」と定めている。この判定を**どこで行うか**を決める必要がある。

DB に Supabase Postgres を採用した（`adr/0003`）ため、選択肢として **行レベルセキュリティ（RLS）を認可の正本にする**道がある。Supabase の標準的な使い方はむしろそちらであるため、採らない理由を明示しておく必要がある。

また `domain/record.md` は「グループの Member であれば、他の Member が登録した記録も編集・削除できる」と定めており、**同じ記録を複数人が同時に編集し得る**。その扱いも決める。

## 決定

### データアクセス経路

**アプリのデータアクセスは `DATABASE_URL` + 通常の Postgres ドライバ + ORM で行う。** Supabase の SDK（PostgREST 経由のクライアント直接アクセス）はデータアクセスに使わない。認可をサーバー側のユースケースで通すため。

環境変数は用途の異なる 2 系統になる。混同しないこと（区分の考え方は `adr/0003` の「環境変数の区分」）。

| 変数 | 用途 |
|---|---|
| `DATABASE_URL` | サーバー側のデータアクセス（ORM が使う） |
| `SUPABASE_URL` / anon key | 認証・セッション管理（`adr/0007`）。データアクセスには使わない |

接続の要件:

- **Supavisor の transaction mode（ポート 6543）に接続する。** サーバーレスから直接接続（5432）するとコネクションが枯渇する
- **transaction mode では prepared statement が使えない。** ドライバ側で prepared statement を無効化する
- ORM は `adr/0004` の原則どおりインフラ層の実装の中に閉じ込め、その外から呼ばない

### ORM とドライバ

**Drizzle を使う。** スキーマを TypeScript で書き、生成ステップが軽く、サーバーレスでのコールドスタートに不利にならないことを条件に選んだ。

**ドライバは `postgres.js` を使う。** 上の「接続の要件」が要求する prepared statement の無効化を、接続オプション 1 つ（`prepare: false`）で満たせることを条件に選んだ。**接続文字列に付ける `?pgbouncer=true` は別の ORM 固有のフラグであり、Drizzle も `postgres.js` も読まない。** 付けると「無効化した」と誤解するだけなので付けない。

### 着手時の確認結果 [確定]

**Drizzle が Supavisor の transaction mode（6543）で動く。** 確認日 2026-08-14。本番の接続文字列に対して、アプリと同じ設定（`prepare: false`）で次を確認した。

| 確かめたこと | 結果 |
|---|---|
| 同じパラメータ付きクエリの繰り返し | 通る |
| トランザクション | 通る |
| 接続に prepared statement が残っていないこと | 残っていない |

**無効化しなかった場合は、応答が返らなくなる。** `prepare: true` のまま複数接続で同時にクエリを投げると、そのまま止まった（エラーとして返らない）。**「動かないときに気づきにくい形で壊れる」ため、無効化は必須である。**

なおこの確認では、コミット済みのマイグレーションを本番に当てて全テーブルの RLS が有効になることまで見たうえで、**確認後にすべて削除して確認前の状態に戻した**（スキーマの適用はリリースの一部として行う。`adr/0011`）。

### マイグレーション

**生成した SQL をリポジトリにコミットし、リリースの一部として適用する。**

- スキーマ定義から SQL を生成し、その SQL を git の履歴に残す。適用内容を事前にレビューできる状態を保つ
- **本番にスキーマを直接反映する経路（push 型）は使わない**
- **適用をいつ・どこで走らせるかは `adr/0011-ci-and-release.md` を正とする。** ここが決めるのは「コミットした SQL を適用する」という形式までで、実行の仕組みは規定しない
- RLS の全拒否ポリシー（後述）も同じマイグレーションで管理し、テーブル追加時に付け忘れが起きないようにする
- **スキーマ定義と生成した SQL は、どちらもインフラ層の永続化のディレクトリに置く**（`adr/0008`）。ORM の設定ファイルだけはリポジトリ直下に置き、出力先をそこへ向ける

テーブル設計そのものは `docs/domain/` から起こす実装作業であり、決定を要する論点ではない。ただし次の 1 点だけは、実装の裁量に委ねると振る舞いが変わるため決めておく。

**Member には「同じ Group・同じ User の組が 2 つ存在しない」制約を DB 側にも置く。** `domain/group.md` は二重の参加で新しい Member を作らないこと、および 2 人が同時に参加した場合はどちらも Member になることを定めている。制約で弾く形にすることで、リポジトリが現在の Member 一覧を読んでから書き戻す必要がなくなる（`adr/0008`）。

**「ドメインにしか置かないもの」と「DB にも置くもの」の線引きはこうする。**

| 種類 | 置き場 | 例 |
|---|---|---|
| **判断**（誰が何をしてよいか、値が妥当か） | ドメイン層だけ | Member であること、金額の上限、負担者が 1 人以上 |
| **一意性・参照の整合**（同じものが 2 つ存在しない、指す先が存在する） | ドメイン層 **+ DB の制約** | Member の重複、ログイン識別子の重複、記録が指す Member の存在 |

分ける理由は、後者が**同時実行でしか壊れない**種類のものだからである。ドメイン層の判定は「読んだ時点で正しい」ことしか保証できず、2 つの処理が同時に走ると両方が判定を通り抜ける。これは判断の重複ではなく、判断を実際に成立させる手段にあたる。前者にはこの事情がないため、DB へ写す理由がない（後述「認可の置き場所」）。

### 認可の置き場所

**認可の正本はドメイン層に置く。** `domain/` が定める前提条件は、エンティティが自身の不変条件として判定する。DB を差し替えても認可が壊れない状態を保つ。

**RLS を認可の正本にはしない。** ただし**全テーブルで RLS を有効化し、「誰も通さない」ポリシーだけを置く。**

3 つの事情がこの形に落ちる。

1. **同じルールが 2 か所に存在すると事故になる。** 認可のルールがエンティティと SQL ポリシーの両方にあると、片方だけ修正した状態が生まれる
2. **業務ルールが DB に染み出すのは依存方向の逆流である。** `adr/0004` が機械検査で防いでいる「内側が外側を知らない」の裏返しにあたり、採用したアーキテクチャの前提と衝突する
3. **一方で「RLS を何も書かない」は Supabase では選べない。** anon key はブラウザに露出する。**RLS を有効化していないテーブルは PostgREST 経由で誰でも読み書きできてしまう**

全拒否ポリシーはアプリに影響しない。サーバーは `DATABASE_URL` で直接接続し、PostgREST を経由しないため。

RLS が本来強いのは「クライアントが DB を直接叩き、DB が信頼境界になる」設計である。本アプリはサーバー側でユースケースを通すため、その前提が成立しない。

### 同時書き込みの競合

`domain/record.md`「同じ記録に同時に手が入ったとき」を、**記録単位の楽観ロック**で実現する。記録ごとにバージョンを持ち、更新・削除の時点で値が変わっていたらその操作を失敗させる。

**バージョンはドメインのエンティティに持たせない。ユースケースの入出力とポートで受け渡す。** 楽観ロックはここで選んだ実現方式にすぎず、別の方式に替えたときにドメインのエンティティが書き換わる状態を作らないため。取得側は記録とバージョンを組で返し、更新・削除側は操作者が見ていたバージョンを引数で受ける（ポートの形は `adr/0008`）。

**楽観ロックを持つのは Payment と Transfer だけとする。Group には持たせない。** `domain/group.md`「境界・例外ケース」は、グループ名・既定通貨・表示名・場の対応づけの同時変更をいずれも**後勝ち**と定めている。版を持たせると、ドメインが失敗させないと決めたものを実現方式の側で失敗させることになる。

**自動再試行はしない。** 最新を読み直して再試行する実装は、`domain/record.md` が要求するものを満たさない。読み直した先は操作者が見ていない内容であり、そこへ変更を適用するのは操作者が意図していないため。

なお PoC は状態全体を 1 つの JSON として保持していたため、全体の読み直しと再試行が必須だった。**本開発ではテーブルを正しく設計するため、競合は記録単位に閉じる。**

### 診断手段

**実 DB に対する疎通と整合を確認する手段を用意する。** PoC では設定不備の切り分けにこれが効いた。ドメイン・ユースケースのテストは偽実装で回るため（`adr/0004`）、本番の接続設定が正しいかは別途確かめる手段が要る。

診断コマンドの中身と実行手順は `docs/operations.md` を、リポジトリ実装を実 DB に対してテストする方針は `adr/0010-testing.md` を正とする。

## 結果

- 良い点：
  - 認可のルールが 1 か所（ドメイン層）にしか存在しない
  - anon key が露出しても、テーブルに直接到達する経路が無い
  - 永続化の差し替えがポートの実装 1 つの入れ替えで済む（`adr/0004`）
- 留意点：
  - **ユースケースを通さないデータアクセス経路を作った瞬間に認可が消える。** 管理用スクリプトを含め、この原則から外れる経路を作らない
  - RLS を「保険」としてすら業務ルールで書かないため、アプリのバグがそのままデータの誤りになる。テストで守る
  - **テーブルを追加したら全拒否ポリシーも必ず追加する。** 付け忘れたテーブルだけが anon key に露出する

## 検討した代替案

- **RLS を認可の正本にし、Supabase SDK でクライアントから直接アクセスする**：Supabase の標準的な使い方で、サーバーを薄くできる。ただし `domain/` が定めるルールを SQL ポリシーとして書き直すことになり、ドメインの定義が 2 か所に分裂する。`adr/0004` の依存方向とも衝突する。
- **RLS を正本にしないが、多層防御として業務ルールを写した最小限の RLS も書く**：安全側に倒れる案で、PoC も「許容する」としていた。採らないのは、写した時点でルールが 2 か所になり、上と同じ事故が起きるため。クライアントが DB に到達できない以上、防いでいる相手が存在しない。
- **RLS を一切設定しない**：anon key 経由で全テーブルが露出する。選べない。
- **楽観ロックを持たず、DB のトランザクションと制約だけに任せる**：実装は最小だが、後から書いた側が黙って勝つ。`domain/record.md`「同じ記録に同時に手が入ったとき」が明示的に否定した振る舞いであり、選べない。
- **悲観ロック（行ロック）で編集中を排他する**：確実だが、Web と Discord をまたいだ操作でロックの保持者を追跡することになり、サーバーレスの前提（`adr/0003`）と相性が悪い。
- **ORM に Prisma を使う**：マイグレーションの体験が最も整っており、スキーマ定義も読みやすい。ただし生成物とクライアントが重く、サーバーレスのコールドスタートに不利。ORM をインフラ層に閉じ込める（`adr/0004`）以上、開発体験の差より実行時の軽さを取る。
- **ORM を使わず Kysely 等のクエリビルダにする**：SQL に最も近く、抽象が薄い分「一段挟む」方針とは相性がよい。ただしマイグレーションの仕組みを別途用意することになり、個人開発で持つ部品が増える。
- **Supabase CLI のマイグレーション機構に乗せる**：RLS のポリシーも同じ仕組みで扱える。ただしスキーマの正が ORM と Supabase の 2 か所に分かれ、どちらを直すべきかが曖昧になる。
